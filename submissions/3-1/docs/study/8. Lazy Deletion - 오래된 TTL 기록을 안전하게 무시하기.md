# 8. Lazy Deletion - 오래된 TTL 기록을 안전하게 무시하기

## 학습 목표

- lazy deletion이 해결하는 문제를 설명할 수 있다.
- TTL을 다시 설정했을 때 오래된 힙 기록이 생기는 이유를 설명할 수 있다.
- `version`을 이용해 최신 TTL 기록을 구별하는 방법을 설명할 수 있다.
- `SET`, `DEL`, `EXPIRE`가 오래된 TTL 기록에 어떤 영향을 주는지 설명할 수 있다.
- lazy deletion의 장점과 비용을 설명할 수 있다.

---

## 1. 문제: 힙에서 특정 기록만 지우기 어렵다

최소 힙은 맨 위의 최솟값을 빠르게 꺼내는 데 특화되어 있다.

```text
peek() -> 맨 위 최솟값 확인: O(1)
pop()  -> 맨 위 최솟값 제거: O(log n)
```

하지만 힙의 중간에 있는 특정 항목을 찾아서 삭제하려면 먼저 그 항목을 찾아야 한다. 일반적인 힙에서는 이 작업이 O(n)이 될 수 있다.

TTL을 다시 설정하거나 키를 삭제할 때마다 이전 TTL 티켓을 힙에서 즉시 찾아 지우면, 최소 힙을 사용하는 장점이 줄어든다.

```text
힙: [(10, user:1), (20, user:2), (60, user:1)]
                  ↑
            중간 또는 아래의 특정 티켓을 바로 찾아 지우기 어려움
```

lazy deletion은 이 문제를 "지금 지우지 말고, 나중에 맨 위로 올라왔을 때 유효한지 확인하자"라는 방식으로 해결한다.

---

## 2. Lazy Deletion이란?

Lazy deletion은 직역하면 "게으른 삭제"다.

하지만 데이터를 방치한다는 뜻은 아니다. 실제 의미는 다음과 같다.

> 오래된 힙 기록을 즉시 물리적으로 삭제하지 않고, 나중에 꺼낼 때 최신 기록인지 검사해 무시하는 전략

이 프로젝트에서는 현재 키의 TTL 상태를 `CacheEntry`에 저장하고, 힙에는 그 상태를 확인하기 위한 티켓을 저장한다.

```text
CacheEntry
- expire_at: 실제 최신 만료 시각
- ttl_version: 현재 TTL의 버전 번호

최소 힙 티켓
- (expire_at, key, version)
```

---

## 3. TTL을 다시 설정하는 예시

다음 상황을 생각해 보자.

```text
현재 시각: 0초
EXPIRE session:1 10
```

`session:1`의 실제 상태와 힙 티켓은 다음과 같다.

```text
CacheEntry
expire_at = 10
ttl_version = 1

힙
(10, "session:1", 1)
```

5초 뒤, 같은 키에 TTL을 다시 설정한다.

```text
현재 시각: 5초
EXPIRE session:1 60
```

이제 최신 만료 시각은 65초다. 힙에는 새 티켓을 추가한다.

```text
CacheEntry
expire_at = 65
ttl_version = 2

힙
(10, "session:1", 1)  <- 오래된 티켓, 즉시 삭제하지 않음
(65, "session:1", 2)  <- 최신 티켓
```

10초가 되면 오래된 티켓이 힙의 맨 위에 온다. 이때 Mini Redis는 다음을 비교한다.

```text
티켓 version: 1
현재 엔트리 version: 2

1 != 2
-> 오래된 티켓이므로 삭제하지 않고 무시
```

따라서 `session:1`은 10초에 삭제되지 않고, 최신 만료 시각인 65초까지 살아 있다.

---

## 4. `SET`, `DEL`, `EXPIRE`와 TTL 버전

### 4.1 `EXPIRE`를 다시 호출하는 경우

새 만료 시각과 새 버전을 만든 뒤 힙에 새 티켓을 넣는다.

```text
EXPIRE key 10
  -> version 1, 티켓 추가

EXPIRE key 60
  -> version 2, 새 티켓 추가
  -> version 1 티켓은 나중에 무시
```

### 4.2 `SET`으로 덮어쓰는 경우

`SET`은 기존 TTL을 초기화한다.

```text
SET key "new value"
  -> ttl_version 증가
  -> expire_at = None
```

기존 티켓이 나중에 힙의 맨 위로 와도 현재 엔트리의 버전이 다르거나 `expire_at`이 없으므로 무시된다.

### 4.3 `DEL`로 삭제하는 경우

`DEL`은 키를 해시맵과 LRU에서 제거하고 TTL 상태도 무효화한다.

```text
DEL key
  -> 해시맵에서 key 제거
  -> ttl_version 증가
  -> expire_at = None
```

기존 티켓이 나중에 힙에서 나오더라도, 해시맵에 키가 없으므로 아무 작업 없이 넘어간다.

---

## 5. 만료 티켓을 처리하는 실제 흐름

Mini Redis는 명령 시작 시 `_purge_expired()`를 호출한다.

```text
1. 힙의 맨 위 티켓을 peek한다.
2. 티켓의 expire_at이 아직 미래라면 종료한다.
3. 만료 시각이 지났다면 pop한다.
4. 해시맵에서 key의 현재 CacheEntry를 찾는다.
5. 키가 없으면 오래된 티켓이므로 무시한다.
6. version과 expire_at이 최신 상태인지 확인한다.
7. 최신 상태이고 실제로 만료됐다면 키를 삭제한다.
```

의사 코드로 표현하면 다음과 같다.

```text
while 힙의 맨 위 티켓이 만료됨:
    ticket = pop()
    entry = 해시맵에서 ticket.key 조회

    if entry가 없음:
        continue
    if ticket.version != entry.ttl_version:
        continue
    if entry.expire_at이 현재 시각보다 늦음:
        continue

    key를 실제로 삭제
```

이 검사를 통과한 티켓만 현재 키의 진짜 만료를 뜻한다.

---

## 6. 왜 안전할까?

오래된 티켓은 삭제 결정을 내릴 권한이 없다. 현재 `CacheEntry`의 상태가 진짜 기준이다.

| 힙 티켓 상태 | 현재 엔트리 상태 | 처리 |
| --- | --- | --- |
| 키가 이미 삭제됨 | 해시맵에 엔트리 없음 | 무시 |
| 버전이 다름 | TTL이 다시 설정되었거나 `SET`됨 | 무시 |
| 버전이 같고 만료 시각 지남 | 현재 TTL이 실제로 만료됨 | 키 삭제 |

즉, 힙 티켓은 "이 시각에 이 키를 확인해 달라"는 알림일 뿐이다. 실제 삭제 여부는 현재 엔트리 상태를 보고 결정한다.

---

## 7. 장점과 비용

### 장점

- 힙 중간의 특정 티켓을 매번 찾고 삭제할 필요가 없다.
- TTL 재설정, `SET`, `DEL`을 단순하게 처리할 수 있다.
- 최소 힙의 `peek`, `pop`, `push` 장점을 유지한다.

### 비용

- 오래된 티켓이 힙에 잠시 남는다.
- 같은 키에 TTL을 자주 설정하면 힙의 티켓 수가 일시적으로 늘 수 있다.

그러나 오래된 티켓도 언젠가 만료 시각 순서대로 힙의 맨 위에 올라오고, 그때 `pop`되어 제거된다. 그래서 이 구현에서는 단순함과 성능의 균형이 좋다.

---

## 8. 이 프로젝트의 구현과 연결하기

`mini_redis/store.py`의 TTL 관련 구현은 다음 규칙을 사용한다.

| 코드 요소 | 역할 |
| --- | --- |
| `CacheEntry.ttl_version` | 현재 TTL 버전 번호 |
| `CacheEntry.expire_at` | 최신 만료 시각 |
| `_expire()` | 버전을 증가시키고 새 티켓을 힙에 추가 |
| `_clear_ttl()` | `SET` 시 기존 TTL 무효화 |
| `_delete_key()` | `DEL`, eviction, 만료 시 TTL 상태 무효화 |
| `_purge_expired()` | 힙 티켓의 유효성을 검사하고 실제 만료 처리 |

TTL 티켓은 다음 형태다.

```text
(expire_at, key, ttl_version)
```

이 구조 덕분에 TTL을 다시 설정하거나 키를 삭제해도 힙을 복잡하게 수정하지 않고 안전하게 동작한다.
