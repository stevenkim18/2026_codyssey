# 7. 최소 힙 - 가장 빠른 만료를 찾는 방법

## 학습 목표

- TTL 관리에 최소 힙이 필요한 이유를 설명할 수 있다.
- 힙과 일반 정렬 목록의 차이를 설명할 수 있다.
- 완전 이진 트리와 배열 인덱스의 관계를 설명할 수 있다.
- `push`, `peek`, `pop`의 동작과 시간 복잡도를 설명할 수 있다.
- Mini Redis가 `(expire_at, key, version)` 티켓을 최소 힙에 저장하는 이유를 설명할 수 있다.

---

## 1. TTL이 많아지면 생기는 문제

TTL이 있는 키가 하나라면 만료 시각을 확인하기 쉽다.

```text
user:1 -> 10초 뒤 만료
```

하지만 TTL이 있는 키가 많아지면 어떨까?

```text
user:1 -> 30초 뒤 만료
user:2 ->  5초 뒤 만료
user:3 -> 12초 뒤 만료
user:4 -> 20초 뒤 만료
```

다음으로 만료될 키는 `user:2`다. 단순한 목록만 사용하면 모든 키의 만료 시각을 처음부터 끝까지 비교해야 한다.

```text
30, 5, 12, 20을 모두 확인
-> 가장 작은 5를 찾음
```

TTL 키가 n개라면 이 방식은 다음 만료 키를 찾을 때마다 O(n)이 걸린다.

최소 힙(Min Heap)은 **가장 작은 값, 즉 가장 이른 만료 시각을 맨 위에 두는 자료구조**다.

```text
가장 이른 만료 시각
        ↓
      [5초]
     /     \
 [12초]  [20초]
```

그래서 다음 만료 키를 O(1)에 확인할 수 있다.

---

## 2. 힙(Heap)이란?

여기서 힙은 메모리 영역을 뜻하는 "힙 메모리"와 다르다. 자료구조 힙은 **우선순위가 가장 높은 값을 빠르게 꺼내기 위한 완전 이진 트리 기반 자료구조**다.

TTL에서는 만료 시각이 빠를수록 우선순위가 높다.

```text
만료 시각이 작다 = 더 빨리 만료된다 = 먼저 처리해야 한다
```

힙은 모든 값을 완전히 정렬하지 않는다. 대신 부모와 자식 사이의 우선순위 규칙만 지킨다.

### 최소 힙의 규칙

최소 힙에서는 부모가 자식보다 작거나 같다.

```text
        [5]
       /   \
    [12]  [20]
    /  \
 [30]  [15]
```

위 구조에서는 항상 맨 위(root)의 `5`가 가장 작은 값이다.

하지만 `12`와 `20` 중 무엇이 더 작은지는 중요하지 않다. 두 값 모두 부모인 `5`보다 크기만 하면 된다.

> 최소 힙은 전체 정렬 구조가 아니라, 최솟값을 빠르게 꺼내기 위한 우선순위 구조다.

---

## 3. 완전 이진 트리와 배열

최소 힙은 **완전 이진 트리**로 생각할 수 있다.

완전 이진 트리는 위에서 아래로, 왼쪽에서 오른쪽 순서로 빈칸 없이 채워지는 트리다.

```text
        [5]             인덱스 0
       /   \
    [12]  [20]       인덱스 1, 2
    /  \
 [30]  [15]         인덱스 3, 4
```

이 모양은 포인터로 노드를 연결하지 않아도 배열에 순서대로 저장할 수 있다.

```text
인덱스:  0    1    2    3    4
값:     [5] [12] [20] [30] [15]
```

인덱스를 알면 부모와 자식 위치를 계산할 수 있다.

| 현재 노드 인덱스 | 계산식 |
| --- | --- |
| 부모 | `(index - 1) // 2` |
| 왼쪽 자식 | `index * 2 + 1` |
| 오른쪽 자식 | `index * 2 + 2` |

예를 들어 인덱스 1의 `12`는 부모가 인덱스 0의 `5`, 자식이 인덱스 3의 `30`과 인덱스 4의 `15`다.

Mini Redis의 `MinHeap`도 Python의 `list`를 인덱스 기반 저장소로 사용해 이 구조를 표현한다.

## 4. 핵심 연산

### 4.1 `peek`: 가장 이른 만료 확인

`peek`은 값을 제거하지 않고 가장 작은 값을 확인한다.

```text
힙: [5, 12, 20, 30, 15]
peek() -> 5
```

최솟값은 항상 인덱스 0에 있으므로 O(1)이다.

TTL 관리에서는 "지금 만료된 키가 있는가?"를 먼저 확인할 때 사용한다.

### 4.2 `push`: 새 만료 기록 추가

새 값을 배열의 마지막에 넣으면 힙 규칙이 깨질 수 있다.

```text
기존 힙: [5, 12, 20]
새 값: 3

마지막에 추가: [5, 12, 20, 3]
```

`3`은 부모인 `12`보다 작으므로 위로 올라가야 한다. 이 과정을 **heapify up** 또는 bubble up이라고 한다.

```text
[5, 12, 20, 3]
         3과 12 교환
[5, 3, 20, 12]
    3과 5 교환
[3, 5, 20, 12]
```

새 값은 트리 높이만큼만 위로 이동하므로 O(log n)이다.

### 4.3 `pop`: 가장 이른 만료 제거

`pop`은 맨 위의 최솟값을 제거한다.

```text
기존 힙: [5, 12, 20, 30]
pop() -> 5
```

마지막 값을 맨 위로 옮긴 뒤, 더 작은 자식과 자리를 바꾸며 아래로 내려 보낸다. 이 과정을 **heapify down** 또는 bubble down이라고 한다.

```text
5 제거 후 마지막 30을 맨 위로 이동
[30, 12, 20]
30과 더 작은 자식 12 교환
[12, 30, 20]
```

이 역시 트리 높이만큼 이동하므로 O(log n)이다.

## 5. TTL 티켓은 무엇을 저장할까?

Mini Redis는 최소 힙에 다음 형태의 값을 넣는다.

```text
(expire_at, key, version)
```

| 항목 | 의미 |
| --- | --- |
| `expire_at` | 키가 만료되는 시각 |
| `key` | 만료를 확인할 키 |
| `version` | 이 TTL 기록이 최신인지 확인하는 번호 |

예를 들어 다음 명령을 처리한다고 하자.

```text
EXPIRE user:1 10
```

현재 시각이 100이라면 힙에는 다음 티켓이 들어간다.

```text
(110, "user:1", 1)
```

튜플은 첫 번째 값부터 비교되므로, 만료 시각이 가장 작은 티켓이 힙의 맨 위에 위치한다. 만료 시각이 같을 때는 키와 버전이 추가 비교 기준이 된다.

```text
(105, "user:2", 1)  <- 먼저 처리
(110, "user:1", 1)
(112, "user:3", 1)
```

## 6. TTL 정리 흐름

명령을 실행하기 전 Mini Redis는 힙의 맨 위를 확인한다.

```text
peek()으로 가장 이른 expire_at 확인
  -> 아직 미래라면 정리 종료
  -> 현재 시각보다 이르면 pop()으로 꺼냄
  -> 해당 키가 실제로도 만료됐는지 확인
  -> 만료됐다면 저장소에서 삭제
```

핵심은 모든 TTL 키를 매번 순회하지 않고, **가장 빨리 만료될 가능성이 있는 키부터 확인한다**는 점이다.

---

## 7. 시간 복잡도

| 연산 | 시간 복잡도 | TTL에서의 역할 |
| --- | --- | --- |
| `peek` | O(1) | 가장 이른 만료 시각 확인 |
| `push` | O(log n) | 새 TTL 등록 |
| `pop` | O(log n) | 만료 후보 제거 |
| 전체 TTL 순회 | O(n) | 최소 힙을 쓰면 매번 수행할 필요 없음 |

TTL을 등록할 때는 O(log n)이 들지만, 매 명령마다 다음 만료 후보를 확인하는 일은 O(1)이다.

## 8. 이 프로젝트의 구현과 연결하기

`mini_redis/min_heap.py`의 `MinHeap`은 다음 메서드를 제공한다.

| 메서드 | 역할 |
| --- | --- |
| `push(item)` | 새 TTL 티켓 추가 후 heapify up |
| `peek()` | 가장 이른 TTL 티켓 확인 |
| `pop()` | 가장 이른 TTL 티켓 제거 후 heapify down |
| `size()` | 현재 티켓 수 확인 |

`mini_redis/store.py`의 `_expire`는 TTL을 설정할 때 티켓을 `push`한다. `_purge_expired`는 `peek`과 `pop`으로 만료 키를 차례대로 정리한다.

```text
EXPIRE key seconds
  -> expire_at 계산
  -> (expire_at, key, version) push

명령 시작
  -> peek으로 가장 이른 티켓 확인
  -> 만료됐다면 pop 후 삭제 처리
```

6. TTL 티켓에 `expire_at` 외에 `key`가 필요한 이유는 무엇인가?

### 한 문장으로 정리

> 최소 힙은 가장 작은 만료 시각을 맨 위에 유지하는 자료구조이며, Mini Redis는 이를 사용해 모든 TTL을 매번 순회하지 않고 다음 만료 키를 빠르게 찾는다.

다음 문서에서는 TTL을 다시 설정하거나 키를 삭제했을 때, 힙에 남은 오래된 기록을 안전하게 처리하는 **lazy deletion**을 살펴본다.
