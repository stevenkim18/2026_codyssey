# 2. 해시맵 - 키를 빠르게 찾는 방법

## 학습 목표

- Map, Hash, Hash Function이 각각 무엇인지 설명할 수 있다.
- 해시맵이 왜 필요한지 설명할 수 있다.
- 해시 함수, 버킷, 충돌, 체이닝의 관계를 설명할 수 있다.
- 로드 팩터와 리해싱이 해시맵 성능을 유지하는 방법을 설명할 수 있다.
- Mini Redis의 `SET`, `GET`, `DEL`이 해시맵과 어떻게 연결되는지 설명할 수 있다.

## 1. Map: 키와 값을 연결하e는 관계

여기서 Map은 지도나 JavaScript의 `map()` 함수가 아니다. 자료구조에서 Map은 **하나의 키를 하나의 값에 연결하는 관계**를 뜻한다.

```text
학생 이름  -> 전화번호
Alice      -> 010-1111-2222
Bob        -> 010-3333-4444
```

| 이름 | 역할 |
| --- | --- |
| Key(키) | 값을 찾기 위한 이름표 또는 식별자 |
| Value(값) | 키에 연결해 저장하는 실제 데이터 |

따라서 다음은 `user:1`이라는 키를 `Alice`라는 값에 연결하는, 즉 매핑하는 일이다.

```text
user:1 -> Alice
```

Redis의 `SET`, `GET`도 결국 이 연결을 저장하고 찾는 명령이다.

```text
SET user:1 "Alice"  # user:1 -> Alice 연결을 저장한다.
GET user:1          # user:1에 연결된 값을 찾는다.
```

Map은 "키로 값을 찾는다"는 개념을 말한다. 이제 남은 문제는 **키를 어떻게 빠르게 찾을 것인가?**다.

---

## 2. Hash와 Hash Function: 키로 위치를 계산하는 규칙

컴퓨터는 문자열 `user:1`을 그대로 비교하는 것보다, 그 문자열에서 계산한 숫자로 위치를 정하면 더 빠르게 데이터를 찾을 수 있다.

```text
"user:1" -> 123456
```

이때 `123456`처럼 키에서 계산한 숫자를 **해시값(Hash value)**이라고 한다.

그리고 키를 받아 해시값을 만드는 규칙을 **해시 함수(Hash Function)**라고 한다.

```text
hash("user:1") -> 123456
hash("user:2") -> 456789
```

해시 함수에는 두 가지 중요한 성질이 있다.

1. 같은 키를 입력하면 항상 같은 해시값이 나와야 한다.
2. 서로 다른 키는 가능한 한 여러 위치에 고르게 퍼져야 한다.

여기서 해시는 비밀번호를 암호화하는 보안 해시와 목적이 다르다. 해시맵의 해시는 원문을 숨기는 것이 아니라, **저장 위치를 빠르게 정하는 것**이 목적이다.

해시값은 매우 큰 숫자가 될 수 있다. 그래서 실제 버킷을 고를 때는 버킷 수로 나눈 나머지를 사용한다.

```text
hash("user:1") = 123456
버킷 수 = 8
123456 % 8 = 0

=> user:1은 0번 버킷에서 찾는다.
```

## 3. 왜 해시맵이 필요할까?

Mini Redis에는 다음과 같은 데이터가 저장된다.

```text
user:1  -> Alice
user:2  -> Bob
user:3  -> Charlie
```

만약 데이터를 단순한 목록에 저장하면 `GET user:3`을 할 때 앞에서부터 하나씩 비교해야 한다.

```text
[user:1, Alice] -> [user:2, Bob] -> [user:3, Charlie]
                                     ↑
                              세 번째에서 찾음
```

데이터가 3개면 괜찮지만, 수천 개나 수만 개가 되면 매번 처음부터 찾는 방식은 느려진다.

해시맵은 키를 이용해 **찾아갈 위치를 먼저 계산**한다. 그래서 전체 데이터를 순서대로 탐색하지 않고도 원하는 키가 있는 버킷으로 바로 갈 수 있다.

> 해시맵은 "키를 입력하면, 그 키가 있을 법한 칸을 빠르게 찾아가는 자료구조"다.

---

## 4. 해시맵의 기본 구성

해시맵은 크게 세 가지 요소로 이해하면 된다.

| 구성 요소 | 역할 | 비유 |
| --- | --- | --- |
| Key | 찾고 싶은 데이터의 이름 | 사물함을 찾기 위한 학생 이름 |
| 해시 함수 | 키를 숫자로 바꾸는 규칙 | 이름으로 사물함 번호를 계산하는 규칙 |
| 버킷(Bucket) | 실제 데이터를 보관하는 칸 | 사물함 구역 |

예를 들어 버킷이 8개인 해시맵을 생각해 보자.

```text
key: "user:1"
   ↓ 해시 함수
hash: 123456
   ↓ hash % 8
bucket index: 0
```

`%`는 나머지 연산자다. 해시값이 아무리 큰 숫자여도 버킷 수로 나눈 나머지를 사용하면 항상 `0`부터 `7` 사이의 인덱스를 얻을 수 있다.

```text
버킷 0: [user:1, Alice]
버킷 1: 비어 있음
버킷 2: [user:2, Bob]
...
버킷 7: 비어 있음
```

### Mini Redis의 해시 함수

해시 함수는 문자열 키를 정수로 바꾸는 함수다. 좋은 해시 함수는 서로 다른 키를 여러 버킷에 비교적 고르게 분산한다.

이 프로젝트의 해시 함수는 키를 UTF-8 바이트로 바꾼 뒤, 각 바이트를 차례대로 누적해 해시값을 만든다.

```text
"user:1"
  ↓ UTF-8 바이트 순회
  ↓ 누적 계산
정수 해시값
  ↓ 버킷 수로 나눈 나머지
버킷 인덱스
```

중요한 점은 같은 키는 항상 같은 해시값, 같은 버킷 인덱스를 만들어야 한다는 것이다. 그래야 저장할 때와 조회할 때 같은 위치를 찾아갈 수 있다.

## 5. 해시 충돌(Collision)이란?

서로 다른 키가 같은 버킷 인덱스를 얻는 상황을 **해시 충돌**이라고 한다.

```text
hash("user:1") % 8 = 3
hash("user:9") % 8 = 3
```

버킷 수는 제한되어 있지만 키는 계속 늘어날 수 있으므로, 충돌은 오류가 아니라 자연스럽게 발생하는 상황이다. 중요한 것은 충돌이 났을 때 데이터를 잃지 않고 처리하는 방법이다.

이 Mini Redis는 **체이닝(Chaining)** 방식으로 충돌을 해결한다.

```text
버킷 3
  ↓
[user:1, Alice] <-> [user:9, Diana]
```

하나의 버킷 안에 여러 키-값 엔트리를 연결 리스트로 이어서 저장한다. 조회할 때는 먼저 버킷을 계산한 다음, 그 버킷 안에서만 키를 비교한다.

```text
GET user:9
  1. hash("user:9")으로 버킷 3을 계산한다.
  2. 버킷 3의 연결 리스트를 순회한다.
  3. user:9와 같은 키를 찾으면 값을 반환한다.
```

이 방식 덕분에 충돌이 나도 `user:1`과 `user:9`가 모두 안전하게 저장된다.

---

## 6. 체이닝에 이중 연결 리스트를 쓰는 이유

이 프로젝트는 버킷의 충돌 목록으로 직접 구현한 `DoublyLinkedList`를 재사용한다.

```text
bucket 3
head <-> [user:1, Alice] <-> [user:9, Diana] <-> tail
```

이중 연결 리스트는 노드가 `prev`, `next`, `data`를 가진다.

- `prev`: 이전 노드
- `next`: 다음 노드
- `data`: 실제 키-값 엔트리

키를 찾는 과정은 버킷 안에서 순회해야 하지만, 이미 찾은 노드를 삭제할 때는 앞뒤 노드를 바로 연결할 수 있으므로 삭제 자체는 O(1)에 처리할 수 있다.

> 해시맵은 어느 버킷을 볼지 빠르게 정하고, 연결 리스트는 충돌한 여러 데이터를 보관한다.

---

## 7. 주요 연산의 흐름

### 7.1 `put(key, value)` — 저장 또는 덮어쓰기

```text
1. key의 해시값을 계산한다.
2. 해시값으로 버킷 인덱스를 계산한다.
3. 해당 버킷의 연결 리스트에서 같은 key를 찾는다.
4. 있으면 value를 교체한다.
5. 없으면 새 엔트리를 버킷 연결 리스트에 추가한다.
```

예시:

```text
SET user:1 "Alice"
  -> put("user:1", CacheEntry(...))
```

### 7.2 `get(key)` — 조회

```text
1. key의 버킷 인덱스를 계산한다.
2. 해당 버킷만 순회한다.
3. 같은 key를 찾으면 value를 반환한다.
4. 없으면 없는 키로 처리한다.
```

예시:

```text
GET user:1
  -> get("user:1")
  -> CacheEntry를 찾음
  -> "Alice" 반환
```

### 7.3 `remove(key)` — 삭제

```text
1. key의 버킷을 계산한다.
2. 버킷 안에서 같은 key의 노드를 찾는다.
3. 연결 리스트에서 해당 노드를 제거한다.
4. 해시맵의 전체 크기를 하나 줄인다.
```

Mini Redis에서는 해시맵에서 삭제한 뒤, LRU 연결 리스트와 TTL 정보, `used_memory`도 함께 정리한다.

## 8. 로드 팩터와 리해싱

버킷이 너무 적고 데이터가 많으면 충돌이 자주 발생한다. 그러면 한 버킷 안의 연결 리스트가 길어지고, 해시맵의 빠른 조회 장점이 줄어든다.

이를 판단하는 기준이 **로드 팩터(Load Factor)**다.

```text
로드 팩터 = 저장된 엔트리 수 / 버킷 수
```

예를 들어 버킷이 8개이고 엔트리가 6개라면 로드 팩터는 `6 / 8 = 0.75`다.

이 프로젝트에서는 로드 팩터가 **0.75를 초과**하면 버킷 수를 두 배로 늘린다.

```text
엔트리 7개 / 버킷 8개 = 0.875
  -> 0.75 초과
  -> 버킷 8개를 16개로 확장
```

버킷 수가 바뀌면 `hash % bucket_count`의 결과도 달라질 수 있다. 따라서 기존 엔트리를 단순히 복사하면 안 되고, 새 버킷 수를 기준으로 각 키의 인덱스를 다시 계산해야 한다. 이 과정을 **리해싱(Rehashing)**이라고 한다.

```text
기존: hash("user:1") % 8  = 3
확장: hash("user:1") % 16 = 11
```

### 왜 두 배로 확장할까?

작게 조금씩 확장하면 확장 작업이 너무 자주 일어난다. 두 배로 늘리면 리해싱은 가끔만 발생하고, 보통의 `put`은 빠르게 처리된다.

---

## 9. 시간 복잡도

| 연산 | 평균 시간 복잡도 | 가장 나쁜 경우 | 이유 |
| --- | --- | --- | --- |
| `get` | O(1) | O(n) | 충돌이 한 버킷에 몰리면 그 목록을 길게 순회할 수 있음 |
| `put` | O(1) | O(n) | 같은 이유, 또는 리해싱이 일어나는 경우 |
| `remove` | O(1) | O(n) | 해당 버킷 안의 충돌 목록을 탐색해야 함 |
| 리해싱 | - | O(n) | 모든 엔트리를 새 버킷으로 옮겨야 함 |

일반적으로 해시 함수가 키를 고르게 분산하고, 로드 팩터를 관리하면 `get`, `put`, `remove`는 평균적으로 O(1)에 가깝게 동작한다.

## 10. 이 프로젝트의 구현과 연결하기

`mini_redis/hash_map.py`의 `ChainedHashMap`은 다음 메서드를 제공한다.

| 메서드 | 역할 |
| --- | --- |
| `put(key, value)` | 키-값 저장 또는 값 교체 |
| `get(key)` | 키의 값 조회 |
| `remove(key)` | 키와 값 삭제 |
| `contains(key)` | 키 존재 여부 확인 |
| `keys()` | 저장된 전체 키 목록 반환 |
| `size()` | 저장된 엔트리 수 반환 |

구현에서 기억할 부분은 다음과 같다.

```text
해시 함수: _hash_key(key)
버킷 선택: _bucket_index(key)
충돌 처리: DoublyLinkedList 버킷
확장 조건: size * 4 > bucket_count * 3
확장 방식: 버킷 수를 두 배로 늘린 뒤 모든 키를 리해싱
```

Python의 `dict`를 사용하면 훨씬 짧게 만들 수 있다. 하지만 이 과제의 목표는 `dict`가 내부에서 해 주는 핵심 원리인 해시, 충돌 해결, 버킷 확장 과정을 직접 이해하는 것이다.

### 한 문장으로 정리

> 해시맵은 키를 해시 함수로 버킷 위치에 연결해 평균 O(1)로 값을 찾고, 충돌은 연결 리스트 체이닝으로 처리하며, 로드 팩터가 높아지면 리해싱으로 성능을 유지하는 자료구조다.

다음 문서에서는 충돌 처리와 LRU 구현에 모두 사용되는 **이중 연결 리스트**를 살펴본다.
