# 9. Mini Redis 전체 동작 흐름과 시간 복잡도

## 학습 목표

- 사용자 입력이 Mini Redis 내부에서 처리되는 전체 흐름을 설명할 수 있다.
- 해시맵, 이중 연결 리스트, 최소 힙이 각각 맡는 역할을 설명할 수 있다.
- `SET`, `GET`, `DEL`, TTL, 메모리 관리 명령의 핵심 흐름을 설명할 수 있다.
- 주요 명령의 시간 복잡도를 설명할 수 있다.
- 평가에서 설명해야 할 핵심 설계 결정을 정리할 수 있다.

---

## 1. Mini Redis의 전체 구조

Mini Redis는 사용자의 명령을 받아 파싱하고, 저장소 엔진이 자료구조를 조합해 처리한 뒤 Redis 스타일 결과를 출력하는 CLI 프로그램이다.

```text
사용자
  ↓ 명령 입력
CLI REPL
  ↓ shlex로 명령어와 인자 분리
MiniRedis.execute()
  ↓ 만료 키 정리 + 명령 분기
해시맵 / 이중 연결 리스트 / 최소 힙
  ↓ 결과 문자열 반환
CLI REPL
  ↓ 출력
사용자
```

예를 들어 사용자가 다음을 입력한다.

```text
SET user:1 "Alice Kim"
```

CLI는 따옴표를 고려해 다음처럼 파싱한다.

```text
명령어: SET
인자:   ["user:1", "Alice Kim"]
```

그다음 `MiniRedis.execute("SET", ...)`가 저장소 엔진의 `_set`을 호출하고, 최종 결과인 `OK`를 CLI가 출력한다.

---

## 2. 각 자료구조의 역할

Mini Redis는 하나의 자료구조만으로 모든 문제를 해결하지 않는다. 각 자료구조가 잘하는 일을 나누어 맡는다.

| 자료구조 또는 상태 | 역할 | 대표 작업 |
| --- | --- | --- |
| 체이닝 해시맵 | 키로 엔트리를 빠르게 찾음 | `GET`, `SET`, `DEL`, `EXISTS` |
| 이중 연결 리스트 | 최근 사용 순서를 관리 | LRU 갱신, 가장 오래된 키 제거 |
| 최소 힙 | 가장 빠른 만료 후보를 찾음 | TTL 만료 정리 |
| `used_memory` | 현재 저장된 키·값 바이트 합계 | 메모리 제한 확인 |
| `maxmemory` | 허용할 최대 메모리 | eviction 시작 기준 |
| `evicted_keys` | 자동 축출 횟수 | `INFO memory` 출력 |

저장하는 실제 값은 `CacheEntry`다.

```text
CacheEntry
- key: 키 문자열
- value: 값 문자열
- memory_size: 키와 값의 UTF-8 바이트 합계
- lru_node: LRU 연결 리스트 노드
- expire_at: 만료 시각 또는 None
- ttl_version: TTL 기록 버전
```

이 엔트리는 해시맵, LRU, TTL을 연결하는 중심 역할을 한다.

---

## 3. 모든 명령의 공통 시작: 만료 키 정리

명령을 실행하기 전에 `MiniRedis.execute()`는 `_purge_expired()`를 호출한다.

```text
명령 시작
  -> 최소 힙의 가장 이른 TTL 티켓 확인
  -> 이미 만료된 티켓이면 꺼냄
  -> 최신 TTL 기록인지 검증
  -> 실제로 만료된 키라면 삭제
  -> 다음 명령 처리
```

이 순서가 중요한 이유는 만료된 키를 모든 명령에서 "없는 키"처럼 일관되게 처리하기 위해서다.

```text
만료된 user:1

GET user:1    -> (nil)
EXISTS user:1 -> (integer) 0
TTL user:1    -> (integer) -2
```

만료 처리로 키를 삭제할 때는 해시맵, LRU 연결 리스트, TTL 상태, `used_memory`를 함께 정리한다.

---

## 4. `SET key value`의 전체 흐름

`SET`은 가장 많은 일을 하는 명령이다.

```text
SET user:1 "Alice"
```

### 4.1 단일 엔트리 크기 확인

먼저 키와 값의 UTF-8 바이트 길이를 계산한다.

```text
entry_size = len(utf8(key)) + len(utf8(value))
```

`maxmemory`가 0보다 크고, 새 엔트리 하나의 크기 자체가 제한보다 크다면 저장하지 않고 OOM 오류를 반환한다.

```text
(error) OOM command not allowed when used_memory > 'maxmemory'
```

이 검사에서는 기존 키도 변경하지 않는다.

### 4.2 새 키 또는 기존 키 처리

| 경우 | 처리 |
| --- | --- |
| 키가 없음 | `CacheEntry` 생성, 해시맵 저장, LRU 맨 앞 추가, 메모리 증가 |
| 키가 있음 | 이전 메모리 크기 차감, 값 교체, 새 크기 가산, TTL 초기화, LRU 맨 앞으로 이동 |

새 키와 기존 키 모두 성공한 `SET`이므로 가장 최근 사용 위치가 된다.

### 4.3 메모리 초과 시 eviction

저장 뒤 `used_memory > maxmemory`라면 LRU 연결 리스트의 맨 뒤 키부터 제거한다.

```text
while used_memory > maxmemory:
    연결 리스트 마지막 노드 선택
    해시맵, LRU, TTL, used_memory에서 함께 삭제
    evicted_keys 증가
```

최종 결과는 `OK`다.

## 5. `GET key`의 전체 흐름

```text
GET user:1
```

1. 해시맵에서 `user:1` 엔트리를 찾는다.
2. 키가 없거나 만료됐다면 `(nil)`을 반환한다.
3. 키가 있으면 해당 엔트리의 `lru_node`를 연결 리스트 맨 앞으로 옮긴다.
4. 값을 큰따옴표로 감싸 반환한다.

```text
GET user:1
"Alice"
```

핵심 규칙은 **성공한 `GET`만 LRU 순서를 갱신한다**는 것이다.

```text
GET missing-key
(nil)

-> 없는 키를 최근 사용한 것으로 만들지 않음
```

## 6. 삭제와 조회 명령

### 6.1 `DEL key`

`DEL`은 키가 존재하면 `(integer) 1`, 없으면 `(integer) 0`을 반환한다.

키를 삭제할 때는 `_delete_key()`라는 공통 흐름을 사용한다.

```text
해시맵에서 엔트리 제거
-> LRU 연결 리스트에서 노드 제거
-> TTL 상태 무효화
-> used_memory 차감
```

한 곳에서 삭제 로직을 모아야 데이터는 없어졌는데 LRU 목록에는 남아 있는 불일치를 막을 수 있다.

### 6.2 `EXISTS key`

키가 살아 있으면 1, 없거나 만료됐으면 0을 반환한다.

```text
EXISTS user:1
(integer) 1
```

`EXISTS`는 단순한 존재 확인이므로 LRU 순서를 갱신하지 않는다.

### 6.3 `DBSIZE`와 `KEYS`

| 명령 | 역할 |
| --- | --- |
| `DBSIZE` | 현재 살아 있는 키 개수 반환 |
| `KEYS` | 현재 살아 있는 모든 키 출력 |

두 명령도 만료된 키를 포함하지 않아야 한다.

---

## 7. TTL 명령의 전체 흐름

### 7.1 `EXPIRE key seconds`

```text
EXPIRE user:1 10
```

1. 키가 있는지 확인한다. 없으면 `(integer) 0`을 반환한다.
2. `seconds <= 0`이면 키를 즉시 삭제하고 `(integer) 1`을 반환한다.
3. 그렇지 않으면 `expire_at = 현재 시각 + seconds`를 계산한다.
4. `ttl_version`을 증가시킨다.
5. `(expire_at, key, ttl_version)`을 최소 힙에 넣는다.
6. `(integer) 1`을 반환한다.

### 7.2 `TTL key`

| 상태 | 결과 |
| --- | --- |
| 키가 없음 또는 만료됨 | `(integer) -2` |
| TTL 미설정 키 | `(integer) -1` |
| TTL 설정 키 | `(integer) N` |

TTL을 다시 설정하거나 키를 삭제해도 오래된 힙 티켓은 lazy deletion으로 안전하게 무시한다.

## 8. 메모리 관리 명령의 전체 흐름

### 8.1 `CONFIG SET maxmemory bytes`

```text
CONFIG SET maxmemory 30
```

- 0 이상의 정수만 허용한다.
- `0`은 무제한이다.
- 더 작은 제한으로 변경해 현재 사용량이 초과하면, 현재 구현은 즉시 LRU eviction을 실행한다.

### 8.2 `INFO memory`

```text
INFO memory
```

다음 값을 출력한다.

```text
used_memory:<현재 바이트 수>
maxmemory:<설정 바이트 수>
evicted_keys:<자동 축출 횟수>
```

## 9. CLI와 오류 처리

CLI는 `mini-redis>` 프롬프트에서 명령을 반복해서 읽는다.

```text
mini-redis> SET user:1 "Alice Kim"
OK
mini-redis> GET user:1
"Alice Kim"
mini-redis> quit
```

### 9.1 값 파싱

CLI는 `shlex`를 사용해 큰따옴표로 감싼 공백 포함 값을 하나의 인자로 처리한다.

```text
SET user:1 "Alice Kim"
```

명령어는 대소문자를 구분하지 않는다.

```text
set user:1 Alice
GET user:1
```

### 9.2 대표 오류 형식

| 상황 | 예시 출력 |
| --- | --- |
| 알 수 없는 명령 | `(error) ERR unknown command 'HELLO'` |
| 인자 수 오류 | `(error) ERR wrong number of arguments for 'GET' command` |
| 정수 파싱 실패 | `(error) ERR value is not an integer or out of range` |
| 메모리 초과 | `(error) OOM command not allowed when used_memory > 'maxmemory'` |

`exit` 또는 `quit`으로 REPL을 종료한다.

## 10. 시간 복잡도 한눈에 보기

아래 표에서 n은 저장된 키 수, t는 TTL 힙 티켓 수, k는 이번 명령에서 제거한 LRU 키 수다.

| 작업 | 일반적인 시간 복잡도 | 비고 |
| --- | --- | --- |
| `GET` | 평균 O(1) | 해시맵 조회 + LRU 노드 이동 |
| `SET` | 평균 O(1) + O(k) | 해시맵 확장 시 O(n), eviction 수만큼 추가 작업 |
| `DEL` | 평균 O(1) | 해시맵 삭제 + LRU 노드 삭제 |
| `EXISTS` | 평균 O(1) | 해시맵 조회 |
| `EXPIRE` | O(log t) | 최소 힙에 TTL 티켓 추가 |
| `TTL` | 일반적으로 O(1) | 엔트리의 만료 시각 확인 |
| `KEYS` | O(n) | 모든 키를 출력해야 함 |
| `DBSIZE` | O(n) 가능 | 현재 구현은 만료 키 보정을 위해 키를 확인함 |
| `CONFIG SET maxmemory` | O(k) 가능 | 제한을 낮추면 LRU eviction 발생 가능 |
| `INFO memory` | O(n) 가능 | 현재 구현은 만료 키 보정을 수행함 |

모든 명령의 시작에는 만료 티켓 정리도 있다. 한 번에 e개의 만료 티켓을 처리한다면 추가로 O(e log t)가 들 수 있다. 하지만 만료 티켓은 한 번만 힙에서 꺼내므로, 일반적인 명령 흐름에서는 비용이 분산된다.

## 11. 전체 상태 변화 예시

다음 명령을 차례로 실행해 보자.

```text
CONFIG SET maxmemory 20
SET user:1 "Alice"
SET user:2 "Bob"
GET user:1
EXPIRE user:1 3
INFO memory
```

### 상태 변화

```text
1. maxmemory = 20

2. SET user:1 "Alice"
   - 해시맵에 user:1 저장
   - LRU: [user:1]
   - used_memory: 11

3. SET user:2 "Bob"
   - LRU: [user:2] <-> [user:1]
   - used_memory: 20

4. GET user:1
   - LRU: [user:1] <-> [user:2]

5. EXPIRE user:1 3
   - user:1의 expire_at 설정
   - TTL 힙에 티켓 추가

6. INFO memory
   - used_memory:20
   - maxmemory:20
   - evicted_keys:0
```

3초가 지난 뒤 다음 명령이 들어오면 `user:1`은 만료 처리되어 해시맵, LRU, TTL 상태, `used_memory`에서 함께 삭제된다.

## 12. 평가에서 설명할 핵심 문장

아래 질문에 답할 수 있으면 이 과제의 핵심을 잘 이해한 것이다.

1. **왜 해시맵을 직접 구현했는가?**
   - 키를 빠르게 찾는 해시 함수, 버킷, 충돌 처리, 리해싱 원리를 이해하기 위해서다.

2. **왜 LRU에 해시맵과 이중 연결 리스트를 함께 쓰는가?**
   - 해시맵으로 키와 노드를 평균 O(1)에 찾고, 이중 연결 리스트로 노드를 O(1)에 이동·삭제하기 위해서다.

3. **왜 TTL에 최소 힙을 쓰는가?**
   - 만료 시각이 가장 빠른 키를 `peek`으로 O(1)에 확인하고, 등록·제거를 O(log n)에 처리하기 위해서다.

4. **왜 lazy deletion이 필요한가?**
   - 힙 중간의 오래된 TTL 티켓을 매번 찾아 지우지 않고도, 버전 검사로 안전하게 무시하기 위해서다.

5. **메모리 초과 시 무슨 일이 일어나는가?**
   - 키와 값의 UTF-8 바이트 수로 `used_memory`를 갱신하고, 제한을 넘으면 LRU 키부터 제거하며 `evicted_keys`를 증가시킨다.

---

## 13. 최종 정리

> Mini Redis는 해시맵으로 키를 찾고, 이중 연결 리스트로 LRU 순서를 관리하며, 최소 힙으로 TTL 만료를 관리한다. 명령마다 만료 키를 먼저 정리하고, 저장 뒤 메모리 제한을 넘으면 가장 오래 사용하지 않은 키를 제거해 일관된 상태를 유지한다.
