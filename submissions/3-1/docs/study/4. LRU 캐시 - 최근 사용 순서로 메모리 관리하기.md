# 4. LRU 캐시 - 최근 사용 순서로 메모리 관리하기

## 학습 목표

- 캐시와 LRU의 관계를 설명할 수 있다.
- MRU와 LRU가 각각 무엇인지 설명할 수 있다.
- 해시맵과 이중 연결 리스트를 함께 사용하는 이유를 설명할 수 있다.
- `GET`, `SET`, 메모리 초과 상황에서 LRU 순서가 어떻게 바뀌는지 설명할 수 있다.
- LRU와 TTL의 차이를 설명할 수 있다.

---

## 1. 캐시와 메모리 제한

**캐시(Cache)**는 나중에 빠르게 다시 사용하려고 데이터를 잠시 보관하는 공간이다.

예를 들어 인기 상품 목록을 데이터베이스에서 계산하는 데 시간이 걸린다면, 계산 결과를 Redis에 저장해 두고 다음 요청에서 바로 돌려줄 수 있다.

```text
첫 요청:  데이터베이스 조회 -> 결과를 캐시에 저장
다음 요청: 캐시 조회 -> 저장된 결과를 바로 반환
```

하지만 캐시는 보통 메모리에 저장한다. 메모리는 빠르지만 무한하지 않다.

```text
메모리 공간: [한정됨]
캐시 데이터: 계속 늘어날 수 있음
```

공간이 부족할 때 어떤 데이터를 지울지 정하는 규칙을 **캐시 교체 정책(Cache Eviction Policy)**이라고 한다. LRU는 가장 널리 쓰이는 교체 정책 중 하나다.

---

## 2. LRU란?

LRU는 **Least Recently Used**의 줄임말이다.

> 가장 오래 사용하지 않은 데이터를 먼저 제거하는 정책

LRU에서 중요한 것은 "언제 저장했는가"가 아니라 **마지막으로 언제 사용했는가**다.

| 용어 | 뜻 |
| --- | --- |
| MRU (Most Recently Used) | 가장 최근에 사용한 데이터 |
| LRU (Least Recently Used) | 가장 오래 사용하지 않은 데이터 |

연결 리스트의 앞을 MRU, 뒤를 LRU로 정하면 순서를 쉽게 표현할 수 있다.

```text
가장 최근 사용                              가장 오래된 사용
head <-> [A] <-> [C] <-> [B] <-> tail
           MRU                  LRU
```

메모리가 부족하면 `tail` 바로 앞의 `B`를 먼저 제거한다.

> LRU는 "오래된 데이터"가 아니라 "오래 사용하지 않은 데이터"를 지운다.

---

## 3. LRU 동작을 순서대로 살펴보기

메모리에 키를 세 개만 저장할 수 있다고 가정하자.

### 3.1 새 키 저장

```text
SET A "apple"
SET B "banana"
SET C "cherry"
```

새로 저장한 키는 방금 사용한 키이므로 맨 앞으로 이동한다.

```text
최근 사용                     오래된 사용
head <-> [C] <-> [B] <-> [A] <-> tail
```

### 3.2 기존 키 조회

이제 `A`를 조회한다.

```text
GET A
```

`A`는 방금 사용했으므로 맨 앞으로 이동한다.

```text
조회 전: head <-> [C] <-> [B] <-> [A] <-> tail
조회 후: head <-> [A] <-> [C] <-> [B] <-> tail
```

이제 `B`가 가장 오래 사용하지 않은 키다.

### 3.3 새 키 저장 후 축출

새 키 `D`를 저장한다.

```text
SET D "durian"
```

먼저 `D`는 맨 앞으로 들어간다.

```text
head <-> [D] <-> [A] <-> [C] <-> [B] <-> tail
```

하지만 세 개만 저장할 수 있으므로, 가장 뒤의 `B`를 제거한다.

```text
head <-> [D] <-> [A] <-> [C] <-> tail
```

이것이 LRU의 전체 흐름이다.

---

## 4. 해시맵과 이중 연결 리스트를 함께 쓰는 이유

LRU는 두 가지 일을 빠르게 해야 한다.

1. `user:1` 같은 키를 빠르게 찾는다.
2. 찾은 키를 최근 사용 위치인 맨 앞으로 옮긴다.

자료구조 하나만 사용하면 둘 다 잘 처리하기 어렵다.

| 자료구조 | 잘하는 일 | LRU에서 맡는 역할 |
| --- | --- | --- |
| 해시맵 | 키로 값 찾기 | 키에서 캐시 엔트리를 찾음 |
| 이중 연결 리스트 | 이미 아는 노드의 이동·삭제 | 최근 사용 순서를 관리함 |

해시맵만 있으면 키를 빨리 찾을 수 있지만, 어떤 키가 가장 오래 사용되지 않았는지는 알기 어렵다.

이중 연결 리스트만 있으면 사용 순서는 관리할 수 있지만, `user:1000`을 찾으려면 앞에서부터 순회해야 한다.

두 구조를 조합하면 다음과 같이 동작한다.

```text
해시맵
user:1 -> CacheEntry -> lru_node
user:2 -> CacheEntry -> lru_node

이중 연결 리스트
head <-> [user:1] <-> [user:3] <-> [user:2] <-> tail
```

`CacheEntry`는 자신이 LRU 연결 리스트의 어느 노드에 있는지 `lru_node`로 기억한다. 그래서 해시맵으로 엔트리를 찾은 뒤, 연결 리스트를 다시 탐색하지 않고 바로 해당 노드를 옮길 수 있다.

```text
GET user:1
  -> 해시맵에서 user:1 엔트리 조회
  -> 엔트리의 lru_node 확인
  -> move_to_front(lru_node)
```

## 5. 명령어에 따른 LRU 순서 변화

### 5.1 새 키 `SET`

새 키를 저장하면 그 키는 방금 사용한 데이터다.

```text
SET user:4 "Diana"
  -> 새 노드를 연결 리스트 맨 앞에 추가
```

### 5.2 기존 키 `SET`

이미 있는 키를 새 값으로 덮어써도 그 키를 사용한 것이므로 맨 앞으로 옮긴다.

```text
SET user:1 "New Alice"
  -> user:1 노드를 맨 앞으로 이동
```

### 5.3 성공한 `GET`

값을 실제로 찾은 경우에만 맨 앞으로 옮긴다.

```text
GET user:1
  -> 키가 있으면 맨 앞으로 이동

GET missing-key
  -> (nil), LRU 순서는 바꾸지 않음
```

만료된 키는 먼저 삭제되고 없는 키처럼 처리되므로, 역시 LRU 순서를 갱신하지 않는다.

### 5.4 `DEL`

키를 삭제하면 해시맵에서만 지우면 안 된다. LRU 연결 리스트에서도 해당 노드를 제거해야 한다.

```text
해시맵: user:1 엔트리 삭제
LRU:    user:1 노드 삭제
```

이 프로젝트에서는 TTL 정보와 `used_memory`도 같은 삭제 흐름에서 함께 정리한다.

---

## 6. 메모리 초과와 eviction

Mini Redis에서는 `maxmemory`가 0보다 크고, 저장 뒤의 `used_memory`가 그 제한을 넘으면 LRU 축출을 수행한다.

```text
while used_memory > maxmemory:
    가장 뒤의 LRU 키를 찾는다.
    해시맵, LRU, TTL 정보에서 함께 삭제한다.
    evicted_keys를 1 증가한다.
```

이 과정을 **eviction(축출)**이라고 한다.

```text
head <-> [최근 키] <-> [오래된 키] <-> tail
                              ↑
                         eviction 대상
```

하나의 키와 값 자체가 `maxmemory`보다 큰 경우에는 다른 키를 모두 지워도 저장할 수 없다. 이 경우 Mini Redis는 기존 데이터를 바꾸지 않고 OOM 오류를 반환한다.

`CONFIG SET maxmemory`로 이미 사용 중인 메모리보다 더 작은 제한을 설정한 경우에도, 현재 구현은 LRU부터 즉시 제거해 제한을 맞춘다.

---

## 7. 시간 복잡도

| 작업 | 시간 복잡도 | 이유 |
| --- | --- | --- |
| 키로 캐시 엔트리 찾기 | 평균 O(1) | 해시맵 사용 |
| 최근 사용 키를 맨 앞으로 이동 | O(1) | `lru_node`를 이미 알고 있음 |
| 가장 오래된 키 찾기 | O(1) | `tail` 바로 앞 노드 |
| 가장 오래된 키 제거 | 평균 O(1) | 해시맵 삭제 + 연결 리스트 삭제 |

해시맵의 평균 O(1)과 이중 연결 리스트의 O(1)을 조합하기 때문에, LRU 갱신과 축출을 빠르게 처리할 수 있다.

---

## 8. LRU와 TTL은 다르다

LRU와 TTL은 둘 다 데이터를 제거하지만 기준과 시점이 다르다.

| 구분 | LRU | TTL |
| --- | --- | --- |
| 제거 기준 | 가장 오래 사용하지 않은 데이터 | 만료 시간이 지난 데이터 |
| 제거 시점 | 메모리가 부족할 때 | 정해진 시간이 지났을 때 |
| 예시 | 오래 안 본 게시글 캐시 제거 | 인증 코드 5분 뒤 삭제 |

```text
LRU: "오래 사용하지 않았으니 지우자"
TTL: "정해 둔 시간이 지났으니 지우자"
```

Mini Redis는 만료된 키를 먼저 없는 키처럼 처리한다. 그 뒤에도 메모리가 부족하면 LRU 정책으로 추가 키를 제거한다.

## 9. 이 프로젝트의 구현과 연결하기

`mini_redis/store.py`에서 LRU 관련 핵심 흐름은 다음과 같다.

| 코드 요소 | 역할 |
| --- | --- |
| `CacheEntry.lru_node` | 엔트리가 연결 리스트의 어느 노드에 있는지 기억 |
| `_touch(entry)` | 엔트리의 노드를 맨 앞으로 이동 |
| `_evict_until_within_limit()` | 제한 이하가 될 때까지 마지막 LRU 키 제거 |
| `_delete_key(key)` | 해시맵·LRU·TTL·메모리 정보를 함께 삭제 |

`SET`은 새 엔트리를 맨 앞에 추가하거나 기존 엔트리를 `_touch`한다. 성공한 `GET`도 `_touch`를 호출한다.

```text
SET / GET 성공
  -> lru_node를 맨 앞으로 이동

메모리 초과
  -> 연결 리스트 마지막 노드 선택
  -> 해당 키를 모든 관련 구조에서 삭제
```

### 한 문장으로 정리

> LRU 캐시는 가장 오래 사용하지 않은 데이터를 먼저 제거하는 정책이며, Mini Redis는 해시맵으로 키를 찾고 이중 연결 리스트로 사용 순서를 관리해 조회·순서 갱신·축출을 빠르게 처리한다.
