# 5. 메모리 제한과 eviction - maxmemory로 캐시 크기 관리하기

## 학습 목표

- 메모리 제한이 왜 필요한지 설명할 수 있다.
- `maxmemory`, `used_memory`, `evicted_keys`의 의미를 설명할 수 있다.
- 문자열 길이와 UTF-8 바이트 길이의 차이를 설명할 수 있다.
- `SET` 뒤 메모리 초과가 발생했을 때의 LRU eviction 흐름을 설명할 수 있다.
- 단일 키가 메모리 제한보다 큰 경우 OOM 오류가 필요한 이유를 설명할 수 있다.

---

## 1. 왜 메모리 제한이 필요할까?

Mini Redis는 데이터를 메모리(RAM)에 저장한다. 메모리는 빠르지만 사용할 수 있는 양이 한정되어 있다.

```text
메모리 공간: 한정됨
저장 요청: 계속 들어올 수 있음
```

아무 제한 없이 데이터를 계속 저장하면 프로그램이 사용할 메모리가 늘어나고, 결국 시스템 전체가 느려지거나 프로그램이 종료될 수 있다.

그래서 캐시에는 보통 다음 두 규칙이 필요하다.

1. 얼마만큼의 메모리까지 사용할지 정한다.
2. 제한을 넘으면 어떤 데이터를 제거할지 정한다.

이 프로젝트에서는 첫 번째 규칙을 `maxmemory`, 두 번째 규칙을 LRU eviction으로 구현한다.

```text
maxmemory: 사용할 수 있는 최대 메모리
LRU:       공간이 부족할 때 먼저 제거할 키를 고르는 정책
eviction:  선택된 키를 실제로 제거하는 작업
```

---

## 2. `maxmemory`와 `used_memory`

### 2.1 `maxmemory`

`maxmemory`는 Mini Redis가 사용할 수 있는 최대 메모리 크기다. 단위는 바이트(byte)다.

```text
CONFIG SET maxmemory 30
```

위 명령은 최대 30바이트까지만 데이터를 저장하겠다는 뜻이다.

```text
CONFIG SET maxmemory 0
```

`0`은 무제한을 뜻한다. 즉, Mini Redis가 LRU eviction을 메모리 제한 때문에 자동 실행하지 않는다.

### 2.2 `used_memory`

`used_memory`는 현재 저장된 키와 값이 차지하는 메모리의 합이다.

이 과제에서는 자료구조 자체의 크기(노드, 포인터, 버킷 등)는 계산하지 않는다. 오직 키와 값의 UTF-8 바이트 길이만 더한다.

```text
used_memory = Σ(len(utf8(key)) + len(utf8(value)))
```

예를 들어 다음 데이터를 저장한다고 하자.

```text
SET user:1 "Alice"
```

| 항목 | 바이트 수 |
| --- | ---: |
| `user:1` | 6바이트 |
| `Alice` | 5바이트 |
| 합계 | 11바이트 |

따라서 이 명령 뒤 `used_memory`는 11이 된다.

---

## 3. 왜 문자 수가 아니라 UTF-8 바이트 수를 셀까?

컴퓨터 메모리는 문자가 아니라 바이트 단위로 사용된다. 영어 알파벳과 한글은 같은 한 글자여도 UTF-8에서 차지하는 바이트 수가 다를 수 있다.

| 문자열 | 글자 수 | UTF-8 바이트 수 |
| --- | ---: | ---: |
| `A` | 1 | 1 |
| `Alice` | 5 | 5 |
| `가` | 1 | 3 |
| `안녕` | 2 | 6 |

따라서 아래 두 값은 눈으로 보기에는 비슷한 길이여도 메모리 사용량이 다르다.

```text
SET greeting "Hello"
SET greeting "안녕"
```

Mini Redis는 Python의 `encode("utf-8")` 결과 길이로 메모리를 계산한다.

> 메모리 제한은 화면에 보이는 글자 수가 아니라, 실제로 저장되는 바이트 수를 기준으로 판단한다.

---

## 4. `SET`할 때 메모리는 어떻게 갱신될까?

### 4.1 새 키를 저장하는 경우

```text
SET user:1 "Alice"
```

1. `user:1`과 `Alice`의 바이트 수를 계산한다.
2. 새 `CacheEntry`를 만든다.
3. 해시맵과 LRU 연결 리스트에 추가한다.
4. 계산한 크기만큼 `used_memory`를 증가시킨다.

```text
used_memory: 0
저장 크기:    11
----------------
used_memory: 11
```

### 4.2 기존 키를 덮어쓰는 경우

```text
SET user:1 "Alice"
SET user:1 "Alice Kim"
```

기존 값을 새 값으로 바꿀 때는 기존 크기를 먼저 빼고, 새 크기를 더해야 한다.

```text
used_memory = used_memory - 이전 엔트리 크기 + 새 엔트리 크기
```

이 과정을 하지 않으면 같은 키를 덮어쓸 때마다 메모리가 실제보다 크게 계산되는 오류가 생긴다.

덮어쓰기는 해당 키를 방금 사용한 것이므로 LRU 연결 리스트에서도 맨 앞으로 이동한다. 기존 TTL은 초기화된다.

## 5. 메모리 초과와 LRU eviction

다음은 과제 예시와 같은 상황이다.

```text
CONFIG SET maxmemory 30
SET user:1 "Alice"
SET user:2 "Bob"
SET user:3 "Charlie"
```

각 엔트리의 크기는 다음과 같다.

| 키와 값 | 계산 | 크기 |
| --- | --- | ---: |
| `user:1` / `Alice` | 6 + 5 | 11 |
| `user:2` / `Bob` | 6 + 3 | 9 |
| `user:3` / `Charlie` | 6 + 7 | 13 |

세 번째 저장 직후에는 총 33바이트다.

```text
11 + 9 + 13 = 33
33 > maxmemory 30
```

메모리 제한을 넘었으므로 LRU 연결 리스트의 맨 뒤, 즉 가장 오래 사용하지 않은 `user:1`을 제거한다.

```text
제거 전: head <-> [user:3] <-> [user:2] <-> [user:1] <-> tail
제거 후: head <-> [user:3] <-> [user:2] <-> tail
```

`user:1`의 11바이트를 빼면 다음과 같다.

```text
used_memory = 33 - 11 = 22
```

이제 22바이트이므로 제한인 30바이트 이하가 된다.

### eviction의 전체 흐름

```text
SET 실행
  -> 새 키·값 크기 계산
  -> 데이터 저장과 used_memory 갱신
  -> used_memory > maxmemory 인지 확인
  -> 초과했다면 LRU 키를 제거
  -> 제한 이하가 될 때까지 반복
```

자동으로 제거한 키 하나마다 `evicted_keys`를 하나 증가시킨다.

## 6. 키 하나가 너무 큰 경우: OOM

어떤 키와 값 하나의 크기 자체가 `maxmemory`보다 클 수 있다.

```text
maxmemory = 10
SET very-long-key "very-long-value"
```

이 엔트리의 크기가 10바이트보다 크다면, 다른 키를 모두 제거해도 이 엔트리를 저장할 수 없다.

이때는 저장하기 전에 오류를 반환해야 한다.

```text
(error) OOM command not allowed when used_memory > 'maxmemory'
```

중요한 규칙은 다음과 같다.

- 새 키를 저장하지 않는다.
- 기존 키를 덮어쓰려던 상황이라면 기존 값도 유지한다.
- 다른 키를 불필요하게 삭제하지 않는다.

즉, OOM은 "일단 지우고 보자"가 아니라 "이 항목은 애초에 들어갈 수 없다"는 판단이다.

## 7. 메모리 상태 확인: `INFO memory`

메모리 관련 상태는 다음 명령으로 확인한다.

```text
INFO memory
```

출력에는 최소한 아래 세 값이 포함된다.

```text
used_memory:22
maxmemory:30
evicted_keys:1
```

| 항목 | 의미 |
| --- | --- |
| `used_memory` | 현재 살아 있는 키와 값이 차지하는 바이트 합계 |
| `maxmemory` | 설정한 최대 메모리 바이트 수 |
| `evicted_keys` | LRU 정책으로 자동 제거된 키의 누적 수 |

`DEL`로 사용자가 직접 삭제한 키나 TTL 만료로 삭제된 키는 `evicted_keys`에 포함하지 않는다. 이 값은 메모리 부족 때문에 자동 축출한 횟수만 센다.

---

## 8. `CONFIG SET maxmemory`를 더 작게 바꾸면?

이미 50바이트를 사용하고 있는데 `maxmemory`를 30으로 낮출 수 있다.

```text
현재 used_memory: 50
CONFIG SET maxmemory 30
```

현재 Mini Redis 구현은 설정값을 바꾼 직후에도 LRU eviction을 실행한다. 따라서 가장 오래 사용하지 않은 키부터 제거해 30바이트 이하로 맞춘다.

```text
used_memory 50
  -> LRU 제거
  -> LRU 제거
  -> used_memory 28
```

이 방식은 설정 직후에도 메모리 제한을 지킨다는 장점이 있다.

---

## 9. 이 프로젝트의 구현과 연결하기

`mini_redis/store.py`에서 메모리 관리를 담당하는 핵심 요소는 다음과 같다.

| 코드 요소 | 역할 |
| --- | --- |
| `_entry_memory_size(key, value)` | 키와 값의 UTF-8 바이트 수 계산 |
| `used_memory` | 현재 메모리 사용량 |
| `maxmemory` | 메모리 제한값 |
| `_evict_until_within_limit()` | 제한 이하가 될 때까지 LRU 키 축출 |
| `evicted_keys` | 자동 축출 횟수 누적 |
| `_delete_key(key, evicted=True)` | 자료구조와 메모리 상태를 함께 정리 |

삭제는 해시맵, LRU 연결 리스트, TTL 상태, `used_memory`를 모두 함께 갱신해야 한다. 한 곳만 삭제하면 나중에 없는 키가 LRU 목록에 남거나 메모리 사용량이 틀어질 수 있다.

### 한 문장으로 정리

> `maxmemory`는 캐시가 사용할 수 있는 최대 바이트 수이고, Mini Redis는 키와 값의 UTF-8 바이트 길이로 `used_memory`를 계산한 뒤 제한을 넘으면 LRU 키를 축출해 메모리 사용량을 관리한다.
