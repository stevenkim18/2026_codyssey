# 3-1 평가 항목 4 답변 가이드

이 문서는 `evaluations/evaluation3-1.md`의 **항목 4**에 답할 때 사용할 설명을 정리한 것이다. 이 항목은 현재 동작을 재현하는 문제가 아니라, 현재 구현을 바탕으로 자료구조 선택·확장성·메모리 측정 기준을 논리적으로 설명하는 문제다.

## 먼저 한 번에 답하기

> LRU를 LFU로 바꾸려면 전역 사용 순서 리스트 대신 빈도별 이중 연결 리스트를 두고, 각 엔트리에 빈도와 해당 빈도 리스트의 노드 참조를 저장해야 합니다. 해시맵은 여전히 키 조회에 사용하고, 가장 낮은 빈도 버킷에서 가장 오래된 노드를 제거하면 동률도 결정할 수 있습니다. 데이터가 10만 건이 되면 현재 구현은 전체 키를 순회하는 `KEYS`·`DBSIZE`·`INFO memory`, 한 번에 모든 엔트리를 옮기는 리해싱, 빈 버킷마다 생성하는 연결 리스트와 센티널, TTL 만료가 몰릴 때의 힙 정리에서 병목이 생길 수 있습니다. `used_memory`에 구조 오버헤드까지 넣으면 같은 `maxmemory`에서 더 적은 키가 저장되고 리해싱·TTL 티켓·빈 버킷도 메모리 정책에 영향을 줍니다. 따라서 공정한 평가는 무엇을 몇 바이트로 셀지, 공유 객체·미사용 용량·리해싱 중 임시 메모리를 어떻게 처리할지를 먼저 같은 규칙으로 정해야 합니다.

## 1. LRU 대신 LFU를 구현한다면 어떻게 바꾸어야 하는가?

### LRU와 LFU의 차이

| 정책 | 제거 기준 | 현재 구현에서의 후보 위치 |
| --- | --- | --- |
| LRU (Least Recently Used) | 가장 오래 사용하지 않은 키 | 하나의 `_lru` 리스트의 `tail.prev` |
| LFU (Least Frequently Used) | 사용 횟수가 가장 적은 키 | 가장 낮은 빈도 버킷의 후보 노드 |

LRU는 최근 사용 순서 하나만 있으면 된다. LFU는 각 키가 몇 번 사용됐는지와 **가장 작은 사용 횟수**를 함께 관리해야 한다. 단순히 `CacheEntry`에 카운터 하나만 추가하면 빈도는 알 수 있지만, “가장 낮은 빈도의 키를 즉시 찾는” 문제는 해결하지 못한다.

### 권장 자료구조

현재의 키 해시맵은 유지하고, 전역 `_lru` 리스트를 빈도별 버킷 구조로 바꾼다.

```text
키 해시맵
"a" -> CacheEntry(frequency=3, frequency_bucket=F3, frequency_node=노드 A)
"b" -> CacheEntry(frequency=1, frequency_bucket=F1, frequency_node=노드 B)
"c" -> CacheEntry(frequency=1, frequency_bucket=F1, frequency_node=노드 C)

빈도 버킷 (낮은 빈도 -> 높은 빈도)
F1 <-> F3

F1의 이중 연결 리스트: head <-> C(MRU 동률) <-> B(LRU 동률) <-> tail
F3의 이중 연결 리스트: head <-> A <-> tail
```

필요한 상태는 다음과 같다.

| 상태 | 역할 |
| --- | --- |
| `key -> CacheEntry` 해시맵 | 키로 엔트리를 평균 O(1)에 찾는다. 현재의 `_data` 역할을 유지한다. |
| `CacheEntry.frequency` | 현재 사용 빈도를 저장한다. |
| `CacheEntry.frequency_node` | 해당 빈도 리스트 안의 노드를 바로 제거·이동한다. |
| `CacheEntry.frequency_bucket` | 엔트리가 속한 빈도 버킷을 바로 찾는다. |
| `frequency -> DoublyLinkedList` | 같은 빈도를 가진 엔트리를 저장한다. |
| 최소 빈도 버킷 포인터 | eviction할 최저 빈도 버킷을 바로 찾는다. |

동일한 빈도의 키가 여럿일 때도 제거 기준이 필요하다. 각 빈도 버킷 안에 이중 연결 리스트를 두고, 앞에는 그 빈도 안에서 가장 최근 접근한 키, 뒤에는 가장 오래 접근한 키를 두면 **LFU + LRU 동률 해소**가 된다. 이 방식은 결과가 결정적이고 설명하기 쉽다.

현재의 `ChainedHashMap`은 문자열 키를 전제로 하므로, `frequency -> 버킷` 관리에는 정수 키를 지원하도록 해시맵을 일반화하거나 별도의 정수 키 해시맵을 구현해야 한다. 빈도 값을 문자열로 바꾸어 재사용할 수도 있지만, 자료구조의 의미가 흐려지므로 정수 키를 지원하는 별도 구조가 더 낫다.

### 명령별 LFU 갱신 흐름

현재 LRU에서 최근 사용으로 취급하는 성공한 `GET`과 기존 키의 `SET`을 LFU에서도 접근으로 취급한다고 정하면, 흐름은 다음과 같다.

| 상황 | LFU 처리 |
| --- | --- |
| 새 키 `SET` | `frequency = 1`로 만들고 F1의 맨 앞에 넣는다. 최소 빈도는 1이 된다. |
| 성공한 `GET` | 기존 Ff에서 노드를 O(1)에 제거하고, `frequency`를 `f + 1`로 올린 뒤 F(f+1)의 맨 앞에 넣는다. |
| 기존 키 `SET` | 현재 구현처럼 사용으로 본다면 성공한 `GET`과 같이 빈도를 올린다. |
| 키 삭제·TTL 만료 | 해당 빈도 버킷에서 노드를 제거하고, 비어 있는 빈도 버킷도 제거한다. |
| eviction | 최소 빈도 버킷의 맨 뒤 노드를 제거한다. 같은 빈도에서는 가장 오래 사용하지 않은 키가 선택된다. |

```text
GET B, B의 빈도 1 -> 2

이전: F1 = [C, B], F2 = []
1. F1에서 B를 분리
2. B.frequency = 2
3. F2의 맨 앞에 B 삽입

결과: F1 = [C], F2 = [B]
```

### 최소 빈도는 어떻게 빠르게 유지하는가?

가장 단순한 LFU 구현은 `min_frequency` 정수와 `frequency -> 리스트` 맵을 둔다. 일반적인 “새 키 하나를 넣기 위해 한 키 하나를 내보내는” LFU 캐시에서는 이 방식만으로도 흔히 평균 O(1)로 동작한다.

하지만 이 Mini Redis는 값의 크기가 다르고, `CONFIG SET maxmemory`로 제한을 크게 낮출 수도 있어서 eviction이 한 번에 여러 키를 반복 제거할 수 있다. 이때 최소 빈도 리스트가 비면 다음 비어 있지 않은 빈도를 찾아야 한다. 단순히 `min_frequency += 1`을 반복하면 빈도 값 사이에 큰 공백이 있을 때 O(1) 보장이 깨질 수 있다.

이 구현에서는 다음 중 하나가 필요하다.

| 선택 | 장점 | 비용 |
| --- | --- | --- |
| 빈도가 낮은 순서로 연결한 **비어 있지 않은 빈도 버킷 리스트**를 추가 | `min_bucket`과 다음 버킷을 O(1)에 찾는다. 빈도 증가 `f -> f+1`은 인접한 위치에 만들 수 있다. | 빈도 버킷 객체와 연결을 추가로 관리해야 한다. |
| 최소 빈도용 힙을 사용 | 다음 최솟값을 쉽게 찾는다. | 빈도 변경·힙 갱신이 O(log n)이어서 순수 O(1) LFU는 아니다. |

변수 크기 eviction도 자주 일어나는 현재 구조에는 첫 번째 방식이 더 잘 맞는다. 빈도 버킷이 비면 버킷 목록에서 제거하고, 최소 버킷을 삭제했다면 다음 버킷을 새 최소로 삼는다.

### LFU에서 추가로 정할 정책

LFU는 과거에 많이 사용된 키가 이후에는 사용되지 않아도 높은 빈도를 오래 유지할 수 있다. 장시간 실행되는 캐시에서는 이 현상을 줄이기 위해 다음 중 하나를 정책으로 정할 수 있다.

- 빈도 상한을 둔다.
- 일정 시점마다 빈도를 감쇠(aging)한다.
- 접근 시각과 빈도를 함께 고려하는 근사 LFU 정책을 사용한다.

모든 엔트리의 빈도를 한 번에 반으로 줄이는 방식은 O(n)이므로, 대규모 환경에서는 에포크 기반 감쇠나 근사 정책을 검토해야 한다. 이 과제의 작은 구현이라면 우선 “동률은 빈도 버킷 내부 LRU로 해결한다”는 정책을 명확히 하는 것이 중요하다.

## 2. 데이터가 10만 건으로 늘어나면 어디가 병목이 되는가?

### 먼저, 현재 구조에서 실제로 커지는 비용

현재 해시맵은 로드 팩터가 0.75를 **초과**하면 용량을 두 배로 늘린다. 100,000개의 서로 다른 키를 저장할 경우, 용량 131,072개에서는 98,304개까지가 정확히 0.75다. 98,305번째 새 키에서 262,144개로 확장되므로 100,000건 시점에는 버킷이 262,144개다.

현재 `_new_buckets`는 모든 버킷에 `DoublyLinkedList`를 만들고, 각 리스트는 `head`, `tail` 센티널 노드를 각각 하나씩 만든다.

```text
버킷 262,144개
  -> DoublyLinkedList 262,144개
  -> 빈 버킷을 포함한 센티널 Node 524,288개
  -> 실제 해시 엔트리 노드 100,000개
  -> LRU 노드 100,000개
```

즉, 충돌이 없는 빈 버킷에도 객체가 여러 개 생긴다. Python의 현재 `Node`, `DoublyLinkedList`, `CacheEntry`는 `__slots__`를 쓰지 않는 객체이므로 객체 헤더와 인스턴스 딕셔너리 비용까지 더해진다. 이것은 알고리즘의 O(1) 표기와 별개로 실제 메모리와 할당 비용에서 큰 부담이 된다.

### 병목과 개선 방향

| 병목 | 현재 구현에서 발생하는 이유 | 개선 방향 |
| --- | --- | --- |
| 리해싱 지연 | `_resize`가 모든 기존 버킷과 엔트리를 순회해 한 번에 재배치하므로 O(n)이다. | 예상 크기로 초기 용량을 크게 잡거나, 각 명령마다 일부 버킷만 옮기는 incremental rehashing을 사용한다. |
| 빈 버킷 오버헤드 | 모든 버킷에 이중 연결 리스트와 센티널 두 개를 미리 만든다. | 빈 버킷은 `None`으로 두고 충돌이 처음 생길 때만 체인을 만들거나, 더 압축적인 버킷 표현을 사용한다. |
| `KEYS` | 모든 키를 읽어 결과 배열·출력 문자열을 만들어야 하므로 본질적으로 O(n)이다. | 커서 기반 `SCAN`을 제공해 결과를 나누어 반환하고, 전체 목록 생성과 큰 응답을 피한다. |
| `DBSIZE`, `INFO memory` | `_remove_entries_that_expired_between_commands()`가 `_data.keys()`로 전체 키를 만들고 각각 만료 여부를 확인한다. 보통 O(1)이어야 할 정보 조회도 O(n)이 된다. | 명령 시작의 힙 기반 만료 정리를 신뢰하고 살아 있는 키 수·메모리 카운터를 유지한다. 응답 직전 전체 보정은 필요할 때만 제한적으로 수행한다. |
| TTL 만료 폭주 | 같은 시점에 많은 TTL이 만료되면 다음 명령이 힙에서 많은 티켓을 `pop`하며 O(e log t) 작업을 한다. lazy deletion 티켓도 힙에 남을 수 있다. | 명령당 정리 개수를 제한하고 백그라운드/주기 정리, 힙 재구축, 시간 버킷·타이밍 휠을 검토한다. |
| 충돌 체인 | 해시 분포가 나쁘거나 의도적인 충돌 키가 들어오면 한 버킷 순회가 길어져 최악 O(n)이다. | 시드가 있는 더 강한 해시를 쓰거나, 긴 체인을 트리로 전환하는 기준을 둔다. |
| Python 객체 수 | 키마다 해시 버킷 노드, LRU 노드, `CacheEntry`가 있고 TTL이 있으면 힙 튜플도 추가된다. | `__slots__` 또는 슬롯 dataclass, 더 압축적인 노드·배열 표현, 객체 풀은 측정 뒤 선택한다. |
| 대량 eviction | 값이 큰 `SET`이나 `maxmemory` 축소는 여러 LRU 키를 제거하므로 O(k)다. | 필요한 삭제 자체는 피할 수 없다. 요청 지연을 줄이려면 eviction 작업을 예산 단위로 나누는 정책을 별도로 정의한다. |

### 우선순위를 두고 개선한다면

1. `DBSIZE`와 `INFO memory`의 전체 순회를 없애고, `KEYS` 대신 `SCAN` 같은 점진적 조회를 제공한다. 이 단계는 일상적인 명령의 지연을 먼저 줄인다.
2. 해시맵의 빈 버킷 객체를 지연 생성하고, 예상 데이터 수를 알 수 있다면 초기 용량을 설정할 수 있게 한다. 메모리와 리해싱 횟수를 함께 줄인다.
3. 리해싱을 점진화해 10만 건 재배치가 한 요청의 긴 지연으로 보이지 않게 한다.
4. TTL 만료 폭주와 lazy deletion 티켓 비율을 측정한 뒤, 정리 예산·힙 재구축·타이밍 휠 중 필요한 방법을 선택한다.
5. 외부 입력을 신뢰하지 않는 서비스라면 충돌 공격을 막을 해시 정책을 강화한다.

LRU의 개별 노드 이동과 `tail.prev` 후보 선택은 이미 O(1)이므로, 10만 건에서 첫 번째 병목은 보통 LRU 자체가 아니라 전체 순회·일괄 리해싱·객체/출력량이다.

## 3. `used_memory`에 자료구조 오버헤드까지 포함하면 무엇이 달라지는가?

### 현재 모델과 확장 모델의 차이

현재 `_entry_memory_size`는 키와 값의 UTF-8 바이트 수만 더한다.

```text
현재 used_memory
  = Σ (UTF-8 key bytes + UTF-8 value bytes)
```

구조 오버헤드까지 포함하는 모델은 적어도 아래 항목의 범위를 정의해야 한다.

| 범주 | 포함할 수 있는 항목 |
| --- | --- |
| 엔트리별 객체 | `CacheEntry`, 해시 버킷의 `HashMapEntry`와 노드, LRU 노드, 객체 헤더와 참조 슬롯 |
| 해시맵 테이블 | 버킷 배열의 용량, 각 `DoublyLinkedList`, `head`·`tail` 센티널, 비어 있는 버킷의 예약 공간 |
| TTL 구조 | 힙 배열의 예약 공간, `(expire_at, key, version)` 티켓, lazy deletion으로 아직 남은 오래된 티켓 |
| 문자열 객체 | UTF-8 내용 외의 문자열 객체 헤더·할당 여유 공간 |
| 런타임 비용 | 정렬(alignment), 가비지 컬렉션 메타데이터, 할당기 여유 공간 |

키 문자열은 `CacheEntry`와 `HashMapEntry` 양쪽에서 참조하지만, 같은 문자열 객체 자체는 한 번만 세야 한다. 대신 두 객체 안의 참조 슬롯 비용은 각 객체 비용에 포함해야 한다. 이처럼 공유 객체를 중복 계산하지 않는 규칙이 필요하다.

```text
확장 used_memory
  = payload_memory
  + per_entry_overhead
  + table_and_capacity_overhead
  + ttl_heap_overhead
```

### 동작에서 달라지는 점

| 상황 | 현재 키·값 바이트 모델 | 구조 오버헤드 포함 모델 |
| --- | --- | --- |
| 새 키 추가 | 키와 값 크기만큼 증가한다. | 엔트리·노드·참조와 필요 시 새 버킷/힙 할당까지 증가한다. |
| 기존 값 갱신 | 값 크기 차이만 반영한다. | 보통 값 차이만 바뀌지만, TTL 티켓 추가 등 구조 변화가 있으면 그 비용도 반영한다. |
| 해시맵 확장 | `used_memory`가 바뀌지 않는다. | 더 큰 버킷 배열과 새 센티널을 할당하므로 크게 증가한다. 리해싱 중에는 이전·새 테이블이 잠시 함께 존재하는지도 정해야 한다. |
| TTL 재설정 | 키·값 크기가 같으면 바뀌지 않는다. | 새 힙 티켓이 추가되고, 오래된 티켓이 나중에 빠질 때까지 비용이 남을 수 있다. |
| 삭제·eviction | 키·값 바이트만 감소한다. | 엔트리별 객체는 줄지만, 현재 구현처럼 축소하지 않는 버킷 배열의 비용은 즉시 줄지 않는다. |

따라서 같은 `maxmemory` 값에서도 저장 가능한 키 수는 줄고, eviction은 더 빨리 시작하며 `evicted_keys`도 더 많이 증가할 수 있다. 특히 새 키 하나가 작더라도 해시맵 확장을 유발하면 구조 메모리 증가가 커질 수 있다.

### 구현할 때 필요한 메모리 회계 방식

명령마다 모든 객체를 `sys.getsizeof()`로 다시 합산하면 O(n)이 되어 메모리 제한 기능이 새로운 병목이 된다. 대신 구조가 변하는 시점에 차이를 누적하는 방식이 필요하다.

```text
payload_memory:        키·값 바이트 합
structure_memory:      엔트리·노드·버킷·힙의 회계상 크기
used_memory:           payload_memory + structure_memory
```

예를 들면 다음 이벤트마다 카운터를 갱신한다.

- 새 엔트리 생성 / 삭제: `CacheEntry`, 해시 노드, LRU 노드의 비용을 더하거나 뺀다.
- 해시맵 확장: 새 테이블의 비용을 더하고, 이전 테이블을 해제한 뒤의 정상 상태와 확장 중 최대치를 명확히 기록한다.
- TTL 설정: 새 힙 티켓과 배열 확장 비용을 더한다.
- TTL 티켓 `pop`: 티켓이 실제로 제거될 때 비용을 뺀다.
- 빈도 버킷 같은 새 정책 구조를 도입하면 그 버킷과 노드도 같은 규칙으로 더한다.

실제 물리 메모리(RSS)는 Python 할당기가 객체를 해제해도 운영체제에 즉시 돌려주지 않을 수 있다. 따라서 “현재 살아 있는 객체의 회계상 크기”를 측정할지, “프로세스가 확보한 실제 메모리”를 측정할지 먼저 정해야 한다. 둘을 혼용하면 eviction 규칙이 예측하기 어려워진다.

또한 빈 저장소의 버킷 배열 같은 **기본 구조 비용**이 `maxmemory`보다 큰 경우, 키를 모두 evict해도 제한 아래로 내려가지 않을 수 있다. 기본 비용을 quota에 포함할지, 초기화 비용으로 제외할지, 제한 설정 자체를 거부할지 정책을 명시해야 한다.

## 4. 공정한 비교와 채점을 위해 어떤 보정이 필요한가?

### 먼저 하나의 측정 규격을 정한다

가장 재현성 있는 방법은 Python 구현의 실제 바이트 수에 바로 의존하기보다, 채점용 **고정 회계 모델**을 먼저 만드는 것이다.

```text
예시 규격
- UTF-8 문자열 본문: 실제 바이트 수
- CacheEntry: 정해진 C_entry 바이트
- 일반 Node: 정해진 C_node 바이트
- HashMapEntry: 정해진 C_hash_entry 바이트
- 참조 슬롯: 정해진 C_ref 바이트
- 버킷 테이블: capacity * C_bucket_slot
- 센티널 / TTL 티켓: 각각 정해진 비용
```

정확한 상수는 평가 전에 제공하거나 모두가 같은 표를 사용해야 한다. 이 방식은 Python 버전, 32/64비트 환경, 메모리 할당기 차이 때문에 점수가 달라지는 일을 막는다.

실제 런타임 측정을 사용할 수도 있지만, 그 경우에는 Python 버전·운영체제·아키텍처·측정 도구를 모두 고정해야 한다. `sys.getsizeof()`는 얕은 크기만 보여 주므로, 공유 객체를 identity 기준으로 한 번만 세는 재귀 회계가 필요하다. `tracemalloc` 같은 도구는 회계 모델을 검증하는 보조 수단으로 쓰되, 그 결과를 서로 다른 실행 환경의 절대 점수로 바로 비교하면 안 된다.

### 반드시 같은 기준으로 맞출 항목

| 비교 항목 | 공정한 기준 |
| --- | --- |
| 포함 범위 | 키·값, 노드, 버킷 배열, 센티널, TTL 힙, 빈 용량, lazy deletion 티켓을 포함하는지 모두 동일하게 정한다. |
| 공유 객체 | 같은 키 문자열처럼 여러 곳에서 참조되는 객체는 한 번만 세는지, 참조 슬롯은 어떻게 세는지 명시한다. |
| 시간 기준 | 명령 완료 뒤의 안정 상태만 볼지, 리해싱 중 이전·새 테이블이 공존하는 피크도 제한에 넣을지 정한다. |
| 삭제 뒤 용량 | 현재처럼 버킷이 축소되지 않을 때 예약 용량을 계속 포함할지 정한다. |
| TTL 상태 | 만료 직후, 명령 시작 정리 뒤, 오래된 힙 티켓이 남은 상태를 같은 시점에서 비교한다. |
| 실행 환경 | 실제 측정이라면 Python 버전, 64비트 여부, 운영체제, 할당기를 고정한다. |
| 작업 부하 | 키·값 길이와 문자 집합, 삽입 순서, 접근 분포, TTL 재설정 횟수, `maxmemory`를 동일하게 준다. |

### 어떤 값을 맞춰 비교할 것인가?

payload만 세던 기존 구현과 구조 오버헤드를 세는 새 구현에 똑같이 `maxmemory = 1 MiB`를 주면, 두 구현은 처음부터 저장 가능한 데이터량이 다르다. 이 비교 자체는 “실제 메모리 효율”을 볼 때는 의미가 있지만, 기능을 동일 조건으로 채점하는 비교는 아니다.

목적에 따라 두 가지 방식을 구분해야 한다.

| 비교 목적 | 권장 보정 |
| --- | --- |
| 기능·정책의 동일성 비교 | 동일한 payload 데이터 집합이 들어가도록 논리 데이터 예산을 맞추고, 구조 오버헤드는 별도 지표로 보고한다. |
| 실제 메모리 효율 비교 | 같은 전체 메모리 예산과 같은 회계 모델을 적용하고, 저장 가능한 키 수·eviction 수·hit rate를 비교한다. |

`INFO memory`에는 합계만 보여 주기보다 아래처럼 구성 요소를 함께 보여 주면 평가자가 차이를 이해하기 쉽다.

```text
payload_memory:<키·값 바이트>
structure_memory:<자료구조 오버헤드>
used_memory:<두 값의 합>
maxmemory:<같은 회계 기준의 제한>
evicted_keys:<자동 축출 횟수>
```

### 평가자에게 말할 결론

> 구조 오버헤드를 포함하면 `used_memory`는 값의 크기만이 아니라 버킷 수, 노드 수, TTL 티켓 수에도 영향을 받습니다. 그래서 단순히 같은 숫자의 `maxmemory`를 주는 것만으로는 공정하지 않습니다. 먼저 동일한 회계 규격과 실행 환경을 정하고, 목적에 따라 같은 payload를 비교하거나 같은 전체 예산에서 저장량·eviction을 비교해야 합니다.

## 평가에서 확인할 핵심 표현

| 질문 | 핵심 답변 |
| --- | --- |
| LFU에 무엇이 더 필요한가? | 키 해시맵 외에 빈도별 이중 연결 리스트, 엔트리의 빈도·노드 참조, 최소 빈도 버킷 관리가 필요하다. |
| LFU에서 동률은 어떻게 처리하는가? | 같은 빈도 버킷 안에서는 LRU 순서를 유지해 가장 오래 사용하지 않은 키를 제거한다. |
| 10만 건에서 LRU가 병목인가? | 개별 LRU 이동은 O(1)이다. 실제 병목은 전체 순회, 일괄 리해싱, 빈 버킷 객체, 대량 TTL 정리와 큰 `KEYS` 응답이다. |
| 구조 오버헤드를 넣으면 왜 eviction이 빨라지는가? | 같은 제한 안에 키·값 외의 노드·버킷·힙도 들어가므로 저장 가능한 payload가 줄기 때문이다. |
| 공정한 채점의 핵심은 무엇인가? | 무엇을 어떤 시점에 얼마나 세는지 같은 회계 모델과 같은 실행·작업 부하 조건을 모든 구현에 적용하는 것이다. |

### 한 문장으로 정리

> LFU는 빈도별 버킷과 최소 빈도 관리로 LRU의 전역 순서를 대체할 수 있고, 대규모화에서는 전체 순회·일괄 리해싱·객체 오버헤드를 줄여야 하며, 구조 메모리를 포함한 평가는 명시된 동일 회계 규격 없이는 공정하게 비교할 수 없다.
