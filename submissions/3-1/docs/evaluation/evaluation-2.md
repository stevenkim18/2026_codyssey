# 3-1 평가 항목 2 답변 가이드

이 문서는 `evaluations/evaluation3-1.md`의 **항목 2**에 답할 때 사용할 설명을 정리한 것이다. 설명은 현재 구현인 `mini_redis/linked_list.py`와 `mini_redis/hash_map.py`를 기준으로 한다.

## 먼저 한 번에 답하기

> 이중 연결 리스트의 노드는 `prev`, `next`, `data`를 가집니다. `head`와 `tail` 센티널을 두고, 이미 알고 있는 노드의 앞뒤 연결만 바꾸도록 했기 때문에 맨 앞·뒤 삽입, 맨 앞·뒤 삭제, 특정 노드 삭제와 맨 앞으로 이동은 모두 O(1)입니다. 해시맵은 문자열 키를 UTF-8 바이트로 순회하는 DJB2 계열 함수로 64비트 해시값을 만든 뒤, 버킷 수로 나눈 나머지를 인덱스로 사용합니다. 서로 다른 키가 같은 인덱스에 오면 그 버킷의 이중 연결 리스트에 `HashMapEntry`를 이어 저장하는 체이닝으로 처리합니다. 새 키를 추가한 뒤 로드 팩터가 0.75를 초과하면 빈 버킷을 두 배로 만들고, 모든 엔트리의 새 인덱스를 다시 계산해 재배치합니다.

## 1. 이중 연결 리스트는 어떻게 O(1) 연산을 보장하는가?

### 노드와 리스트의 구조

`Node`는 다음 세 필드를 가진다.

| 필드 | 저장하는 내용 | 역할 |
| --- | --- | --- |
| `prev` | 이전 노드의 참조 | 현재 노드 앞의 연결을 바로 변경할 수 있게 한다. |
| `next` | 다음 노드의 참조 | 현재 노드 뒤의 연결을 바로 변경할 수 있게 한다. |
| `data` | 실제 데이터 | LRU에서는 `CacheEntry`, 해시 버킷에서는 `HashMapEntry`를 저장한다. |

리스트는 실제 데이터 앞뒤에 `head`, `tail` 센티널 노드를 둔다.

```text
head <-> [data] <-> [data] <-> tail
```

비어 있는 경우도 `head <-> tail`이라는 같은 형태를 유지한다. 따라서 첫 노드 삽입이나 마지막 노드 삭제처럼 빈 리스트를 따로 처리해야 하는 상황이 줄어든다. 센티널은 실제 데이터가 아니므로 `remove_node`와 `move_to_front`에서 제거 대상이 되지 않도록 검증한다.

### O(1)이 되는 핵심: 탐색하지 않고 이웃만 다시 연결한다

연결 리스트의 O(1) 연산에는 전제가 있다. **삭제하거나 이동할 `Node` 객체를 이미 알고 있어야 한다.** 값만 알고 노드를 찾는 과정은 순회가 필요하므로 O(n)이다.

예를 들어 `B` 노드를 제거할 때 `B.prev`와 `B.next`를 이미 알 수 있다.

```text
제거 전: head <-> A <-> B <-> C <-> tail
제거 후: head <-> A <--------> C <-> tail

A.next = C
C.prev = A
B.prev = None  # 완전히 제거할 때 연결을 끊는다.
B.next = None
```

이 작업은 노드 수와 관계없이 참조 몇 개만 바꾸므로 O(1)이다. 구현의 `_detach`가 이 재연결을 담당한다.

### 핵심 메서드와 시간 복잡도

| 메서드 | 동작 | O(1)인 이유 |
| --- | --- | --- |
| `insert_front(data)` | `head` 바로 뒤에 새 노드를 연결한다. | `head`와 기존 첫 노드만 수정한다. |
| `insert_back(data)` | `tail.prev`와 `tail` 사이에 새 노드를 연결한다. | 마지막 노드를 `tail.prev`로 바로 얻는다. |
| `remove_front()` | `head.next`인 첫 실제 노드를 제거한다. | 첫 노드를 바로 얻고, 그 노드의 연결만 끊는다. |
| `remove_back()` | `tail.prev`인 마지막 실제 노드를 제거한다. | 마지막 노드를 바로 얻고, 그 노드의 연결만 끊는다. |
| `remove_node(node)` | 이미 알고 있는 실제 노드를 제거한다. | `node.prev`, `node.next`로 양옆을 바로 잇는다. |
| `move_to_front(node)` | 노드를 현재 자리에서 분리한 뒤 `head` 바로 뒤에 넣는다. | 분리와 삽입이 모두 이웃 노드만 변경한다. |
| `first_node()` / `last_node()` | 첫 번째 / 마지막 실제 노드를 반환한다. | `head.next`, `tail.prev`를 바로 읽는다. |
| `size()` / `is_empty()` | 크기 또는 빈 상태를 확인한다. | `_size`를 별도로 유지한다. |

`iter_nodes()`는 예외다. 버킷의 엔트리나 전체 목록을 앞에서부터 순회하므로 O(n)이다. 따라서 “이중 연결 리스트의 모든 작업이 O(1)”이라고 말하면 안 되고, **노드를 이미 알고 있는 위치 변경·삭제 작업이 O(1)**이라고 설명해야 정확하다.

### `move_to_front`의 실제 흐름

`move_to_front(node)`은 이미 맨 앞인 노드면 바로 끝낸다. 그렇지 않으면 `_detach(node, clear_links=False)`로 현재 위치에서 분리하고, `_insert_after(head, node)`로 맨 앞에 다시 연결한다. 이동은 노드를 삭제한 뒤 새로 만들지 않으며 `_size`도 바꾸지 않는다.

```text
이동 전: head <-> A <-> B <-> C <-> tail
B 분리:  head <-> A <--------> C <-> tail
B 삽입:  head <-> B <-> A <-> C <-> tail
```

## 2. 직접 설계한 해시 함수는 어떻게 인덱스를 만드는가?

해시맵은 문자열 `key`를 입력으로 받는다. `_hash_key(key)`는 Python 내장 `hash()`가 아니라 직접 구현한 **결정적 DJB2 계열 해시 함수**다.

```python
hash_value = 5381
for byte in key.encode("utf-8"):
    hash_value = ((hash_value << 5) + hash_value) ^ byte
    hash_value &= 0xFFFFFFFFFFFFFFFF

index = hash_value % len(self._buckets)
```

각 단계를 말로 풀면 다음과 같다.

1. 문자열 키를 `key.encode("utf-8")`으로 바꾼다. 따라서 영문뿐 아니라 한글 같은 유니코드 키도 UTF-8 바이트열로 일관되게 처리한다.
2. 초기값 `5381`에서 시작한다.
3. 각 바이트마다 `((hash_value << 5) + hash_value) ^ byte`를 계산한다. `((h << 5) + h)`는 `h * 33`과 같으므로, 이전 해시값에 33을 곱한 뒤 현재 바이트와 XOR하는 누적 방식이다.
4. `& 0xFFFFFFFFFFFFFFFF`로 결과를 64비트 범위에 남긴다. 같은 키가 항상 같은 결과를 내도록 계산 범위를 고정한다.
5. 마지막 해시값을 현재 버킷 수로 나눈 나머지로 바꾼다. 이 결과가 `0` 이상 `버킷 수 - 1` 이하의 실제 버킷 인덱스다.

```text
문자열 key
  -> UTF-8 바이트열
  -> DJB2 계열 누적 계산
  -> 64비트 해시값
  -> hash_value % 버킷 수
  -> 버킷 인덱스
```

예를 들어 초기 버킷 수가 8일 때 `user:1`과 `user:9`는 모두 7번 버킷을 가리킨다. 이는 오류가 아니라 충돌이며, 아래의 체이닝으로 두 엔트리를 함께 보관한다. 버킷을 16개로 확장한 뒤에는 같은 해시값을 새 버킷 수로 다시 나누므로 `user:1`은 15번, `user:9`는 7번 버킷으로 나뉜다.

> 해시값 자체는 키가 같으면 변하지 않지만, 최종 인덱스는 `해시값 % 버킷 수`이므로 버킷 수가 바뀌면 달라질 수 있습니다.

## 3. 충돌은 체이닝으로 어떻게 해결하는가?

### 버킷 내부 구조

바깥쪽의 `_buckets`는 버킷에 인덱스로 접근하기 위한 Python `list`다. 각 버킷의 실제 충돌 목록은 직접 구현한 `DoublyLinkedList`다. 이 연결 리스트의 각 `Node.data`에는 `HashMapEntry(key, value)`가 들어간다.

```text
_buckets[7]
  head <-> [HashMapEntry("user:1", value1)]
       <-> [HashMapEntry("user:9", value2)] <-> tail
```

따라서 충돌한 키가 있어도 한 키가 다른 키를 덮어쓰지 않는다. 같은 버킷 안에서 실제 키 문자열까지 비교해 구분한다.

### 저장·조회·삭제 흐름

| 연산 | 처리 순서 |
| --- | --- |
| `put(key, value)` | 해당 키의 버킷을 계산하고 `_find_node`로 같은 키가 있는지 순회한다. 있으면 `entry.value`만 갱신하고, 없으면 그 버킷의 맨 뒤에 새 `HashMapEntry`를 추가한다. |
| `get(key)` / `contains(key)` | 해당 버킷만 순회하며 `entry.key == key`인 노드를 찾는다. |
| `remove(key)` | 해당 버킷에서 같은 키의 노드를 찾은 뒤 `bucket.remove_node(node)`로 연결을 O(1)에 끊고 `_size`를 하나 줄인다. |

체이닝에서는 해시 함수가 먼저 볼 버킷을 제한하기 때문에 보통 전체 엔트리를 탐색하지 않는다. 로드 팩터를 관리하고 해시가 고르게 분산된다는 가정 아래 버킷 길이가 짧아져 `get`, `put`, `remove`는 평균 O(1)이다.

다만 더 정확히는 다음과 같다.

- 해시 계산 자체는 키의 바이트 수에 비례한다.
- 충돌한 버킷 안의 탐색은 그 버킷 길이에 비례한다.
- 모든 키가 한 버킷에 몰리면 탐색은 최악 O(n)이다.
- 노드를 찾은 뒤 연결 리스트에서 제거하는 단계만 O(1)이다.

## 4. 로드 팩터가 0.75를 초과하면 어떻게 두 배 확장하는가?

로드 팩터는 다음 식으로 계산한다.

```text
로드 팩터 = 엔트리 수 / 버킷 수
```

구현은 새 키를 저장해 `_size`를 증가시킨 뒤 아래 조건으로 검사한다.

```python
if self._size * 4 > len(self._buckets) * 3:
    self._resize(len(self._buckets) * 2)
```

이는 `_size / 버킷 수 > 3 / 4`, 즉 로드 팩터가 **0.75를 초과**한다는 뜻이다. 같을 때는 확장하지 않는다. 예를 들어 처음 버킷이 8개라면 엔트리 6개일 때는 `6 / 8 = 0.75`이므로 유지하고, 일곱 번째 새 키가 들어오면 `7 / 8 = 0.875`이므로 16개로 확장한다. 기존 키의 값을 덮어쓰는 `put`은 `_size`를 증가시키지 않으므로 확장 조건도 검사하지 않는다.

### 확장과 리해싱 절차

```text
1. 기존 버킷 목록을 old_buckets에 보관한다.
2. 기존 버킷 수의 두 배만큼, 비어 있는 DoublyLinkedList 버킷을 새로 만든다.
3. old_buckets의 모든 버킷과 모든 노드를 순회한다.
4. 각 HashMapEntry의 key로 새 버킷 수 기준 인덱스를 다시 계산한다.
5. 계산한 새 버킷의 뒤에 entry를 추가한다.
6. _size는 그대로 유지한다. 엔트리를 추가하거나 삭제한 것이 아니라 위치만 다시 배치했기 때문이다.
```

```text
확장 전 (버킷 8개)
hash(key) % 8  -> 기존 위치

확장 후 (버킷 16개)
hash(key) % 16 -> 새 위치
```

버킷 수가 달라지면 나머지 연산 결과도 달라질 수 있으므로, 기존 버킷 배열을 단순히 복사하면 조회 위치가 맞지 않게 된다. 모든 엔트리에 대해 새 인덱스를 계산하는 이유가 리해싱이다.

`_resize` 한 번은 모든 엔트리를 순회하므로 O(n)이다. 하지만 버킷을 매번 조금씩이 아니라 두 배로 늘리기 때문에 확장은 자주 일어나지 않으며, 일반적인 `put`의 시간 복잡도는 상각 O(1)로 볼 수 있다.
