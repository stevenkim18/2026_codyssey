# 1-1 평가 문항 점검 및 답변 가이드

이 문서는 [평가 문항](../../../evaluations/evaluation1-1.md)을 기준으로 1-1 제출물을 점검하고, 평가 때 설명할 수 있도록 답변을 정리한 자료다. 설명의 근거는 [수행 내역서](../README.md), [관제 스크립트](../monitor.sh), [검증 캡처](../evidence/verification-result.png)다.

> 이 문서는 저장소에 제출된 코드와 증빙을 검토한 결과다. 현재 개발 환경에서 Ubuntu VM 자체를 재실행한 검증은 할 수 없으므로, VM에서만 확인 가능한 항목은 **구현 근거**와 **평가 직전 재시연 명령**을 함께 적었다.

## 1. 전체 판단

### 결론

제출물은 평가 문항의 핵심 요구사항을 모두 구현하고 있으며, SSH·방화벽·계정 그룹·스크립트 권한·cron·로그 누적은 캡처로도 확인된다. `monitor.sh`는 Bash 문법 검사(`bash -n`)도 통과했다.

다만 평가 직전 아래 두 가지는 실제 VM에서 한 번 더 보여 주는 편이 좋다.

1. 앱의 Boot Sequence 5단계 `[OK]`와 `Agent READY`
2. 10MB 회전이 실제로 발생한 뒤의 파일 개수와 크기

둘 다 README와 코드에는 근거가 있지만, 현재 검증 캡처에는 직접적인 강한 증거가 부족하다. 이는 구현 실패라는 뜻이 아니라, 동료 평가에서 질문이 나올 가능성을 미리 줄이기 위한 증빙 보강이다.

### 판정 표기

| 표기 | 뜻 |
| --- | --- |
| **충족** | 요구사항 구현과 제출 증거를 모두 확인했다. |
| **충족 · 재시연 권장** | 구현은 확인했지만, 실제 실행 화면을 한 번 더 준비하면 좋다. |
| **보완 권장** | 현재도 평가 조건은 대체로 만족하지만, 더 엄격한 해석이나 운영 환경을 위해 개선하면 좋은 부분이다. |

### 한눈에 보는 결과

## 2. 평가 직전 시연 순서

아래 명령은 **Ubuntu VM에서** 실행한다. 설정을 바꾸는 명령이 아니라 결과를 확인하는 명령만 골랐다. 평가자는 명령 자체보다 “왜 이 결과가 요구사항을 증명하는가”를 들을 가능성이 크다.

```bash
# 1. SSH와 방화벽
sudo sshd -T | grep -E '^(port|permitrootlogin)'
sudo ss -tulnp | grep sshd
sudo ufw status numbered

# 2. 계정·그룹·권한
id agent-admin
id agent-dev
id agent-test
sudo stat -c '%U %G %a %n' \
  /home/agent-admin/agent-app/bin/monitor.sh \
  /var/log/agent-app/monitor.log
sudo getfacl -p \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app

# 3. 앱을 agent-admin으로 실행한 터미널에서 Boot Sequence 확인
sudo -iu agent-admin
source ~/.profile
cd "$AGENT_HOME"
./agent-app-linux-arm64

# 4. 다른 터미널에서 관제와 cron 확인
sudo -u agent-admin /home/agent-admin/agent-app/bin/monitor.sh
echo "monitor.sh 종료 코드: $?"
sudo crontab -u agent-admin -l
sudo tail -n 5 /var/log/agent-app/monitor.log
```

앱 실행 명령은 마지막 `Agent READY`가 나온 뒤에도 계속 실행된다. 이 상태를 유지한 채 다른 터미널에서 `monitor.sh`를 실행해야 프로세스와 15034 포트 검사가 모두 성공한다. 앱 종료는 앱 실행 터미널에서 `Ctrl+C`를 누른다.

## 3. 항목 1 — 요구사항 충족 여부

### 3-1. SSH 포트가 20022이고 Root 원격 접속이 차단되었는가?

**판정: 충족**

**확인 근거**

- README에는 `/etc/ssh/sshd_config.d/00-codyssey.conf`에 `Port 20022`, `PermitRootLogin no`를 설정했다고 기록되어 있다.
- 검증 캡처의 `sudo sshd -T` 결과가 `port 20022`, `permitrootlogin no`를 보인다.
- 이어지는 `ss -tulnp | grep sshd` 결과에서 SSH 서버가 `0.0.0.0:20022`와 `[::]:20022`에서 `LISTEN` 중이다.

**초보자 설명**

SSH 포트는 서버 관리자가 원격 터미널에 들어오는 출입문 번호다. 설정 파일만 바꿔도 오타나 다른 설정 파일 때문에 실제 적용값이 다를 수 있다. 그래서 `sshd -T`로 **실제로 적용된 설정**을 보고, `ss`로 **새 포트에서 실제로 연결을 기다리는지**까지 확인했다.

Root는 운영체제를 전부 바꿀 수 있는 최고 권한 계정이다. Root 원격 로그인을 막으면 공격자가 Root 비밀번호를 추측하거나 탈취해 바로 시스템 전체를 장악하는 경로를 줄일 수 있다. 운영자는 일반 계정으로 로그인한 뒤, 필요한 작업에만 `sudo`를 사용한다.

**평가 때 이렇게 답하면 된다**

> SSH 포트를 20022로 변경하고 `PermitRootLogin no`로 Root의 원격 로그인을 막았습니다. `sshd -T`는 실제 적용된 SSH 설정을, `ss -tulnp`는 20022 포트의 실제 LISTEN 상태를 확인합니다. 포트 변경은 무차별 스캔 노출을 줄이는 보조 수단이고, Root 차단과 일반 계정 + sudo 운영이 더 중요한 방어입니다.

### 3-2. 방화벽이 활성화되어 있고 20022/tcp, 15034/tcp만 허용되는가?

**판정: 충족**

**확인 근거**

- README의 UFW 설정은 `default deny incoming` 뒤에 `20022/tcp`, `15034/tcp`만 허용한다.
- 검증 캡처에서 `Status: active`를 확인했다.
- 캡처의 규칙은 IPv4용 두 줄과 IPv6용 두 줄이다. IPv6 줄은 별도 포트를 연 것이 아니라 같은 두 포트에 IPv6 정책도 적용한 것이다.

**초보자 설명**

방화벽은 서버 앞의 경비원이다. 기본 정책을 “외부에서 들어오는 연결은 거부”로 두면, 실수로 프로그램이 다른 포트를 열어도 외부에서 접속하기 어렵다. 이 과제에서는 관리용 SSH 20022와 앱 15034만 예외로 열었다.

**평가 때 이렇게 답하면 된다**

> UFW를 활성화하고 인바운드는 기본 거부로 설정했습니다. 외부에서 필요한 통로인 SSH 20022/tcp와 앱 15034/tcp만 허용했습니다. `ufw status numbered`에서 active 상태와 허용 규칙 전체를 함께 확인했기 때문에, 단순히 UFW가 켜진 것뿐 아니라 필요한 포트만 열렸다는 점까지 확인할 수 있습니다.

### 3-3. agent-admin/dev/test 계정과 agent-common/core 그룹이 요구사항대로 구성되었는가?

**판정: 충족 · 재시연 권장**

**확인 근거**

- 캡처의 `id` 결과에서 `agent-admin`과 `agent-dev`는 `agent-common`, `agent-core`에 속한다.
- `agent-test`는 `agent-common`에는 속하지만 `agent-core`에는 속하지 않는다.
- README는 `upload_files`를 `agent-common`, `api_keys`와 `/var/log/agent-app`을 `agent-core`로 분리했다고 설명한다.
- 캡처에는 `monitor.sh`가 `agent-dev:agent-core`, 권한 `750`이고 로그 파일이 `agent-admin:agent-core`, 권한 `660`임이 나온다.

**초보자 설명**

사용자 계정은 “누가 작업하는가”, 그룹은 “어떤 역할이 같은 자원에 접근하는가”를 나타낸다.

| 역할 | `agent-common` | `agent-core` | 접근 의도 |
| --- | --- | --- | --- |
| `agent-admin` | O | O | 운영 및 cron 실행 |
| `agent-dev` | O | O | 스크립트 작성과 운영 지원 |
| `agent-test` | O | X | 업로드 테스트만 참여 |

`agent-test`에게 API 키나 운영 로그를 보여 주지 않는 것이 핵심이다. `upload_files`는 세 역할의 협업 공간이라 `agent-common`으로, 키와 로그는 민감한 자원이라 `agent-core`로 나누었다.

**평가 직전 보강할 증거**

현재 캡처의 `getfacl` 명령은 일반 `user`로 실행되어 `upload_files`, `api_keys`의 ACL을 읽지 못한다. 이는 일반 사용자가 상위 디렉터리를 통과하지 못한다는 점에서는 정상 동작이지만, ACL 자체를 직접 보이는 증거는 아니다. 아래처럼 `sudo`로 한 번 더 찍어 두면 완전하다.

```bash
sudo getfacl -p \
  /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app

sudo -u agent-test test -w /home/agent-admin/agent-app/upload_files \
  && echo '[OK] agent-test can write upload_files'
sudo -u agent-test test -r /home/agent-admin/agent-app/api_keys/t_secret.key \
  && echo '[FAIL] key must not be readable' \
  || echo '[OK] agent-test cannot read the key'
```

**평가 때 이렇게 답하면 된다**

> 공용 업로드 파일은 admin, dev, test가 모두 협업해야 하므로 `agent-common` 그룹을 사용했습니다. 반면 API 키와 운영 로그는 기밀성·무결성이 더 중요하므로 admin과 dev만 포함한 `agent-core`로 제한했습니다. `agent-test`는 업로드는 다룰 수 있지만 키와 로그에는 접근하지 못합니다.

### 3-4. 앱이 Boot Sequence 5단계 [OK]를 통과하고 Agent READY를 출력하는가?

**판정: 충족 · 재시연 권장**

**확인 근거**

- README에 일반 계정 `agent-admin`으로 실행해 1~5단계 모두 `[OK]`와 `Agent READY`를 확인한 결과가 기록되어 있다.
- 환경 변수, ARM64 실행 파일 선택, 키 파일 호환 처리, 로그 디렉터리 권한을 README가 함께 설명한다.

**주의할 점**

현재 검증 캡처에는 Boot Sequence 전문이 보이지 않는다. 동료 평가에서 가장 빠르게 확인할 수 있는 핵심 화면이므로, 평가 직전에 앱을 다시 실행하여 다섯 줄과 `Agent READY`를 보여 주는 것이 좋다.

또한 과제 명세에는 `AGENT_KEY_PATH`가 `t_secret.key` 파일을 가리키는 형태로 적혀 있지만, README는 제공 실행 파일이 실제로는 `api_keys` 디렉터리와 그 안의 `secret.key`를 검사했다고 기록한다. 그래서 요구된 `t_secret.key`를 보존하고 `secret.key` 하드 링크를 두었다. 이 차이를 질문받으면 “명세 파일은 유지했고, 실제 제공 앱의 검사 방식에 맞춰 같은 inode를 가리키게 했다”고 설명하면 된다.

**초보자 설명**

Boot Sequence는 앱이 “일단 실행됐다”보다 더 많은 것을 검사한다. 실행 계정, 환경 변수, 키 파일, 포트 사용 가능 여부, 로그 디렉터리 쓰기 권한을 순서대로 검사한다. 다섯 단계가 모두 성공해야 앱이 실제 서비스 준비를 마친 것으로 볼 수 있다.

**평가 때 이렇게 답하면 된다**

> 앱은 Root가 아닌 `agent-admin`으로 실행했습니다. Boot Sequence의 다섯 단계는 계정, 환경 변수, 키 파일, 포트, 로그 쓰기 권한을 차례대로 검사합니다. 모두 `[OK]`이고 마지막에 `Agent READY`가 나왔으므로, 설정값만 만든 것이 아니라 앱이 그 설정을 실제로 사용할 수 있음을 확인했습니다.

### 3-5. monitor.sh가 프로세스·포트 상태를 점검하고, 비정상이면 exit 1로 종료하는가?

**판정: 충족**

**확인 근거**

- `monitor.sh` 27~31행은 `pgrep -f`로 `agent-app-linux-arm64` 프로세스를 찾고, 없으면 `[FAIL]`을 출력한 뒤 `exit 1`을 실행한다.
- 34~39행은 `ss -ltnH`에서 TCP 15034의 LISTEN 상태를 찾고, 없으면 `exit 1`을 실행한다.
- 과제는 제공 앱 파일명을 대상으로 검사하는 것을 허용하므로 `agent_app.py` 대신 실제 실행 파일명을 쓰는 선택은 적절하다.
- `bash -n submissions/1-1/monitor.sh` 문법 검사는 통과했다.

**초보자 설명**

프로세스와 포트는 비슷해 보여도 다른 사실을 확인한다.

- 프로세스 확인: 앱 프로그램이 운영체제에서 실행 중인가?
- 포트 확인: 앱이 네트워크 연결을 받을 준비가 되었는가?

프로세스는 살아 있어도 초기화 실패로 포트를 못 열 수 있다. 반대로 15034 포트만 열려 있어도 다른 프로그램이 그 포트를 사용했을 수 있다. 따라서 둘 다 확인해야 한다. 둘 중 하나라도 틀리면 “정상 앱 상태”라고 볼 수 없으므로 종료 코드 `1`로 실패를 알린다.

**평가 때 이렇게 답하면 된다**

> `pgrep -f`로 실제 실행 명령줄에서 제공 앱 프로세스를 찾고, `ss -ltnH`로 15034 TCP 포트가 LISTEN인지 확인했습니다. 둘은 서로 다른 장애를 잡기 때문에 함께 검사합니다. 둘 중 하나라도 실패하면 cron이나 호출자가 비정상을 알 수 있도록 `exit 1`로 끝냅니다.

### 3-6. /var/log/agent-app/monitor.log가 지정 포맷으로 누적 기록되는가?

**판정: 충족**

**확인 근거**

- `monitor.sh` 95행은 `[날짜] PID:... CPU:... MEM:... DISK_USED:...` 형식의 `LOG_LINE`을 만든다.
- 96행은 `printf '%s\n' ... >> "${LOG_FILE}"`로 파일 끝에 한 줄을 추가한다.
- 캡처에는 같은 형식의 여러 로그 줄이 시간 순서로 기록돼 있다.

**초보자 설명**

로그는 사람이 읽는 메모이면서 나중에 프로그램이 분석할 데이터이기도 하다. 그래서 매번 같은 순서와 같은 이름으로 기록해야 한다. 예를 들어 `CPU:` 뒤 숫자, `MEM:` 뒤 숫자를 `awk`나 다른 도구로 안정적으로 꺼낼 수 있다. 날짜를 `YYYY-MM-DD HH:MM:SS` 형식으로 두면 문자열 정렬만 해도 시간순이 유지된다.

**평가 때 이렇게 답하면 된다**

> 로그 한 줄은 시각, 앱 PID, CPU, 메모리, 루트 디스크 사용률을 같은 순서로 기록합니다. 이 형식을 고정하면 사람이 장애 시점을 읽기 쉽고, 나중에 `grep`이나 `awk`로 항목별 통계를 낼 때도 파싱 규칙이 흔들리지 않습니다. `>>`를 사용해 기존 기록을 지우지 않고 끝에 누적했습니다.

### 3-7. cron 매분 실행으로 monitor.log가 자동 증가하는가?

**판정: 충족**

**확인 근거**

- 캡처의 `agent-admin` crontab에는 다음 행이 있다.

```cron
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >/dev/null 2>&1
```

- 캡처의 `monitor.log`에는 `12:59:02`, `13:00:02`, `13:01:02`, `13:02:02`처럼 분 단위로 새 행이 늘어난 결과가 있다.

**초보자 설명**

crontab의 다섯 `*`은 분, 시, 일, 월, 요일을 뜻한다. 가장 앞의 `*`이 매분을 의미하고, 나머지도 제한하지 않았으므로 매분 실행된다. `/dev/null` 리다이렉션은 cron 메일에 콘솔 출력이 쌓이는 것을 막고, 중요한 관제 결과는 스크립트가 직접 `monitor.log`에 남긴다.

**평가 때 이렇게 답하면 된다**

> `agent-admin`의 crontab에 매분 실행 규칙을 등록했습니다. 수동 실행 로그 하나와 그 뒤 1분 간격으로 추가된 로그들을 비교해, 사람이 명령을 다시 입력하지 않아도 cron이 실행했다는 것을 확인했습니다. cron 실행 계정은 로그 디렉터리와 스크립트 실행 권한이 있는 `agent-admin`입니다.

### 3-8. monitor.log 용량 관리가 10MB/10개로 설정되어 있는가?

**판정: 충족 · 재시연 권장**

**확인 근거**

- `monitor.sh` 13~14행에서 최대 파일 크기를 `10 * 1024 * 1024` 바이트(10MiB), 최대 파일 수를 10개로 정한다.
- 83~93행에서 현재 로그가 한계 이상이면 `.9`를 지우고, `.1`~`.8`을 한 칸씩 뒤로 옮긴 뒤 현재 로그를 `.1`로 회전한다.
- 회전 뒤 새 `monitor.log`를 만들고 권한을 다시 `660`으로 맞춘다.

**동작 원리**

```text
회전 전: monitor.log, monitor.log.1, ..., monitor.log.9
          │
          ├─ monitor.log.9 삭제
          ├─ .8 → .9, .7 → .8, ... , .1 → .2
          ├─ monitor.log → monitor.log.1
          └─ 빈 monitor.log 생성

회전 후: 현재 1개 + 과거 9개 = 최대 10개
```

**보완 권장**

현재 구현은 새 로그 줄을 쓰기 **전** 파일 크기가 10MiB 이상인지 검사한다. 따라서 파일이 한계보다 아주 조금 작은 상태에서 한 줄을 추가하면 다음 실행까지 한 줄만큼 10MiB를 넘을 수 있다. 과제의 일반적인 “10MB 기준 회전”에는 부합하지만, “절대로 한 바이트도 넘지 않게” 해석하는 평가자에게는 다음처럼 보완할 수 있다.

1. `LOG_LINE`을 먼저 만든다.
2. 현재 파일 크기와 새 줄의 바이트 수 합계가 10MiB를 초과하는지 검사한다.
3. 초과한다면 먼저 회전하고, 그 뒤 새 줄을 기록한다.

지금은 코드 변경 요청이 아니므로 이 문서에는 개선 방향만 남긴다. 평가 전에는 운영 로그를 인위적으로 지우지 말고, 별도 테스트 사본에서 회전을 재현하거나 이미 회전된 파일 목록을 보여 주는 방식이 안전하다.

**평가 때 이렇게 답하면 된다**

> 로그가 10MiB에 도달하면 현재 로그를 `.1`로 옮기고, 기존 파일은 번호를 하나씩 뒤로 밉니다. 가장 오래된 `.9`는 삭제하므로 현재 로그를 포함해 최대 10개만 유지됩니다. 최근 장애 기록은 남기면서도 로그가 무한히 커져 디스크를 가득 채우는 문제를 막는 정책입니다.

## 4. 항목 2 — 구현 선택을 설명하는 답변

### 4-1. 프로세스 식별과 포트 확인 명령은 무엇이며, 왜 선택했는가?

**답변 예시**

> 프로세스 식별에는 `pgrep -f agent-app-linux-arm64`를 사용했습니다. `pgrep`는 PID를 바로 반환하므로 `ps | grep`보다 파이프와 문자열 처리 코드가 적고, `grep` 자기 자신이 검색 결과에 섞일 위험도 줄어듭니다. `-f`는 프로세스 이름만이 아니라 전체 실행 명령줄에서 실제 제공 앱 파일명을 찾게 합니다.
>
> 포트 확인에는 `ss -ltnH`를 사용했습니다. `ss`는 현재 리눅스에서 널리 사용하는 소켓 조회 도구이고, `netstat`보다 일반적으로 더 현대적인 인터페이스입니다. `-l`은 LISTEN 소켓만, `-t`는 TCP만, `-n`은 포트 번호를 숫자로, `-H`는 헤더 없이 출력한다는 뜻입니다. 그 결과를 `awk`로 검사해 15034 포트가 정확히 열려 있는지 확인했습니다.

**추가 질문에 대비할 설명**

- `pgrep`는 앱 프로세스의 존재를 확인한다.
- `ss`는 네트워크 서비스 준비 상태를 확인한다.
- `pgrep -f`의 `-f`는 프로세스 이름만이 아니라 전체 명령줄을 비교한다. 제공 바이너리 이름을 명시하므로, 실행 파일이 전체 경로로 실행되더라도 찾을 수 있다. 반환된 PID가 여러 개일 수 있으므로 현재 구현은 `head -n 1`로 하나를 골라 로그에 기록한다. 프로세스가 없을 때는 빈 값으로 만든 뒤 명시적으로 `[FAIL]`과 `exit 1`을 처리한다.
- `ss` 출력의 네 번째 열은 로컬 주소다. `awk`의 `:${APP_PORT}$` 조건은 이 열이 정확히 `:15034`으로 끝나는지를 검사하므로, 예를 들어 `:115034` 같은 다른 포트를 잘못 통과시키지 않는다. IPv4의 `0.0.0.0:15034`와 IPv6의 `[::]:15034` 모두 이 조건에 맞는다.
- 현재 코드는 “15034에 어떤 프로세스라도 LISTEN 중인가”를 확인한다. 더 엄격하게 “`pgrep`로 찾은 PID가 15034을 열었는가”까지 확인하려면 권한이 허용되는 범위에서 `ss -ltnp`의 PID 정보도 비교할 수 있다. 이는 현재 과제 요구를 넘는 강화안이다.

**두 검사를 함께 하는 이유**

```text
프로세스 있음 + 포트 없음  → 앱이 초기화 실패했거나 포트를 열기 전 상태일 수 있음
프로세스 없음 + 포트 있음  → 다른 프로그램이 해당 포트를 사용 중일 수 있음
프로세스 있음 + 포트 있음 → 관제 대상 앱이 서비스 준비 상태일 가능성이 높음
```

따라서 둘 중 하나라도 실패하면 자원 수치를 기록하지 않고 `exit 1`로 끝낸다. 자원 수치만 남기면 실제 앱이 서비스 가능한 상태인 것처럼 오해할 수 있기 때문이다. 실제 운영 환경에서 systemd로 관리하는 서비스라면 `systemctl is-active`와 서비스의 health endpoint를 추가로 확인하는 방식도 고려할 수 있다.

### 4-2. CPU/MEM/DISK를 어떻게 추출·파싱했고, 로그 포맷은 왜 고정했는가?

**답변 예시**

> CPU는 `/proc/stat`을 1초 간격으로 두 번 읽었습니다. `/proc/stat`에는 CPU가 사용자 작업, 시스템 작업, 대기 등에 쓴 누적 시간이 들어 있습니다. 두 시점의 전체 시간 차이와 idle 시간 차이를 구한 뒤, `(전체 차이 - idle 차이) / 전체 차이 × 100`으로 실제 1초 동안의 CPU 사용률을 계산했습니다. `awk`로 소수점 첫째 자리까지 출력했습니다.
>
> 메모리는 `free -b`의 `Mem:` 행에서 사용 바이트(`$3`)를 전체 바이트(`$2`)로 나누어 백분율로 만들었습니다. 디스크는 `df -P /`의 루트 파티션 행에서 사용률 열(`$5`)을 읽고 `%` 문자를 제거했습니다. `-P`는 출력 열 구조를 POSIX 형식으로 고정해 파싱이 흔들리지 않도록 한 옵션입니다.
>
> 로그는 `[시간] PID:... CPU:... MEM:... DISK_USED:...` 형식으로 고정했습니다. 사람이 읽기 쉽고, 항목 이름과 순서가 변하지 않아 나중에 `grep`, `awk`, 리포트 스크립트로 숫자를 안정적으로 추출할 수 있기 때문입니다.

**코드 위치**

| 값 | 코드 | 핵심 계산 |
| --- | --- | --- |
| CPU | `monitor.sh` 47~58행 | `/proc/stat` 두 번의 차이 |
| 메모리 | `monitor.sh` 60행 | `used / total × 100` |
| 디스크 | `monitor.sh` 61행 | 루트 파티션의 Used% |
| 로그 | `monitor.sh` 95~96행 | `printf`와 `>>` 누적 |

### 4-3. 소유자와 실행자 권한 정책을 어떻게 만족했는가?

**답변 예시**

> `monitor.sh`의 소유자는 `agent-dev`, 그룹은 `agent-core`, 권한은 `750`입니다. 따라서 작성자인 `agent-dev`는 읽기·쓰기·실행이 가능하고, 같은 core 그룹의 `agent-admin`은 읽기·실행만 가능합니다. cron 실행자 `agent-admin`은 스크립트를 실행할 수 있지만 스크립트 내용을 임의로 수정할 수 없습니다. `agent-test`는 core 그룹이 아니므로 실행할 수 없습니다.
>
> 로그 디렉터리와 로그 파일은 `agent-core`로 제한했습니다. cron은 `agent-admin` 계정에서 실행되고 이 계정은 core 그룹에 속하므로 로그를 생성하고 누적할 수 있습니다. 새 파일의 기본 권한은 `umask 007`으로 other 사용자에게 열리지 않게 하고, 로그 파일은 `chmod 660`으로 owner와 group만 읽고 쓸 수 있게 유지했습니다. UFW 상태 조회에만 필요한 최소 sudo 권한도 `agent-admin`에 한정했습니다.

**권한을 숫자로 읽는 법**

| 권한 | 소유자 | 그룹 | 그 밖의 사용자 | 이 과제의 의미 |
| --- | --- | --- | --- | --- |
| `750` | `rwx` | `r-x` | `---` | dev는 수정 가능, admin은 실행 가능, 그 외는 접근 불가 |
| `660` | `rw-` | `rw-` | `---` | admin/dev는 로그를 읽고 쓸 수 있고, 그 외는 불가 |
| `2770` | `rwx` | `rwx` | `---` | 공유 디렉터리 + 새 파일 그룹 상속(setgid) |

### 4-4. 10MB/10개 로그 관리를 어떻게 구현했는가?

**답변 예시**

> 별도 `logrotate` 설정 대신 `monitor.sh` 안에 크기 기반 회전 로직을 구현했습니다. `stat -c %s`로 현재 파일의 바이트 수를 확인하고, 10MiB 이상이면 가장 오래된 `.9`를 삭제합니다. 그 다음 `.8`부터 `.1`까지 뒤에서 앞으로 이동해 이름이 덮어써지지 않도록 하고, 현재 `monitor.log`를 `.1`로 옮깁니다. 마지막으로 빈 `monitor.log`를 새로 만들고 권한을 `660`으로 복구합니다. 그래서 현재 파일 1개와 과거 파일 9개, 최대 10개를 유지합니다.

**왜 뒤에서 앞으로 옮기는가?**

`.1`을 먼저 `.2`로 옮기면 기존 `.2`를 덮어쓸 수 있다. `.8 → .9`처럼 큰 번호부터 움직이면 아직 옮기지 않은 파일을 덮어쓰지 않는다. 이 작은 순서가 로그를 안전하게 보존하는 핵심이다.

**회전 전후의 파일 변화**

```text
회전 전: monitor.log, monitor.log.1, ..., monitor.log.8, monitor.log.9

1. monitor.log.9 삭제
2. .8 → .9, .7 → .8, ..., .1 → .2
3. monitor.log → monitor.log.1
4. 빈 monitor.log 생성 후 새 로그 한 줄 기록

회전 후: monitor.log, monitor.log.1, ..., monitor.log.8, monitor.log.9
         현재 1개 + 과거 9개 = 최대 10개
```

`rm -f`는 `.9`가 아직 없어도 오류 없이 진행하게 하고, 반복문의 `[[ -f ... ]]` 조건은 중간 번호의 파일이 없는 초기 상태에서도 안전하게 동작하게 한다. 회전 전 `touch`로 현재 로그 파일의 존재를 보장하고, 회전 뒤 `chmod 660`을 다시 적용해 새 파일도 admin/dev만 읽고 쓸 수 있게 한다.

**동시 실행과 경계값 처리**

로그 회전 전에 `flock`으로 잠금을 잡으므로 cron 실행과 수동 실행이 동시에 파일을 이동시키는 경쟁 상태를 막는다. 용량은 `>= 10MiB`인지 새 로그 줄을 쓰기 전에 검사한다. 따라서 파일이 한계보다 아주 조금 작은 상태에서 한 줄이 추가되면, 다음 실행 시 회전할 때까지 한 줄만큼 한계를 넘을 수 있다. 과제의 일반적인 용량 기준에는 부합하지만, 한 바이트도 넘지 않게 하려면 새 `LOG_LINE`의 바이트 수까지 더해 회전 여부를 판단하도록 개선할 수 있다.

## 5. 항목 3 — 보안과 운영 원리를 설명하는 답변

### 5-1. SSH 포트 변경과 Root 접속 차단이 왜 보안에 효과적인가?

**답변 예시**

> 위협 모델은 인터넷 또는 같은 네트워크에서 자동화된 봇이 SSH 기본 포트 22를 스캔하고, 흔한 계정이나 유출된 비밀번호로 로그인을 시도하는 상황입니다. 20022로 포트를 바꾸면 기본 포트만 노리는 잡음과 무차별 시도가 줄어들지만, 모든 포트를 스캔하는 공격자까지 막는 완전한 방어는 아닙니다.
>
> 더 중요한 조치는 Root 원격 로그인 차단입니다. Root는 이미 최고 권한이므로 Root 계정이 탈취되면 추가 방어선 없이 시스템 전체가 노출됩니다. 일반 계정으로 로그인하고 필요한 작업에만 `sudo`를 쓰면, 공격자는 일반 계정 탈취 후에도 추가 권한 상승 단계를 거쳐야 하고 운영자는 누가 어떤 명령을 실행했는지 더 명확히 추적할 수 있습니다.

**짧은 핵심 문장**

> 포트 변경은 노출을 줄이는 보조 수단이고, Root 원격 차단과 최소 권한 운영이 피해 범위를 줄이는 핵심 수단입니다.

### 5-2. api_keys와 로그 디렉터리를 agent-core로 제한한 이유는 무엇인가?

**답변 예시**

> 최소 권한 원칙은 각 역할에 필요한 권한만 주고, 필요 없는 권한은 주지 않는 원칙입니다. `agent-test`는 업로드 기능을 테스트해야 하므로 `upload_files`에는 접근해야 합니다. 하지만 API 키는 외부 서비스 권한으로 이어질 수 있는 비밀 정보이고, 운영 로그는 시스템 구조나 사용자 정보가 포함될 수 있으며 조작되면 장애 분석의 신뢰성이 깨질 수 있습니다. 그래서 키와 로그는 운영·개발 역할인 `agent-core`로만 제한했습니다.

**구분해서 기억할 점**

| 자원 | 주된 보호 목표 | 허용 역할 |
| --- | --- | --- |
| `upload_files` | 협업 가능성 | admin, dev, test |
| `api_keys` | 비밀성 | admin, dev |
| `/var/log/agent-app` | 비밀성 + 기록 무결성 | admin, dev |

### 5-3. 방화벽 비활성이나 임계치 초과는 왜 경고만 출력하고 종료하지 않는가?

**답변 예시**

> 앱 프로세스가 없거나 서비스 포트가 LISTEN하지 않는 것은 앱이 서비스를 제공하지 못하는 치명적 상태라서 `exit 1`로 실패시킵니다. 반면 CPU·메모리·디스크 사용률이 높거나 방화벽 상태를 읽지 못하는 것은 조사와 대응이 필요한 위험 신호지만, 그 순간 앱이 반드시 죽었다는 뜻은 아닙니다.
>
> 이런 경고까지 종료 처리하면 가장 필요한 순간에 리소스 수치와 경고 로그를 남기지 못할 수 있습니다. 그래서 경고를 출력하고 로그는 계속 기록합니다. 운영자는 추세를 보고 대응하고, 별도의 알림 시스템이 있다면 경고를 알림으로 연결할 수 있습니다.

### 5-4. >와 >>의 차이와 로그에 >>가 필요한 이유는 무엇인가?

**답변 예시**

> `>`는 파일을 새로 쓰는 리다이렉션입니다. 대상 파일이 이미 있으면 기존 내용을 먼저 비웁니다. `>>`는 파일 끝에 이어 쓰는 리다이렉션입니다. 모니터링 로그는 매분 이전 기록 위에 새 관측값을 쌓아야 하므로 `>>`를 사용했습니다. `>`를 쓰면 매 실행 때 마지막 한 줄만 남아 장애의 시간 흐름을 분석할 수 없습니다.

**예시**

```bash
echo '첫 번째 기록' > monitor.log    # 기존 로그를 비우고 새로 기록
echo '두 번째 기록' >> monitor.log  # 첫 번째 기록 뒤에 추가
```

참고로 cron 행의 `>/dev/null 2>&1`은 스크립트의 표준 출력과 오류 출력을 모두 버리는 설정이다. 실제 관제 데이터는 콘솔이 아닌 `monitor.log`에 남기므로 cron 메일이 불필요하게 쌓이는 것을 막는다.

## 6. 항목 4 — 상황 대응을 설명하는 답변

### 6-1. 모니터링 대상이 Nginx 같은 웹 서버로 바뀌면 무엇을 바꿔야 하는가?

**답변 예시**

> 먼저 프로세스 이름을 Nginx의 master process 또는 systemd 서비스 상태를 확인하는 방식으로 바꿉니다. 포트는 서비스 설정에 따라 80/tcp, 443/tcp 또는 내부 프록시 포트로 바꾸고, HTTPS라면 인증서 만료도 별도 점검 대상으로 추가할 수 있습니다.
>
> 로그는 단일 `monitor.log`뿐 아니라 Nginx의 access log와 error log를 함께 봐야 합니다. 웹 서버에서는 CPU·메모리·디스크 외에도 5xx 오류 수, 요청 수, 응답 시간, 활성 연결 수, 파일 디스크립터 사용량 같은 지표가 중요합니다. 임계값도 현재 앱의 20%/10%를 그대로 복사하지 않고, 평소 트래픽을 측정해 정상 범위와 경고 기준을 정해야 합니다.

| 점검 항목 | 현재 앱 | Nginx로 바꿀 때 예 |
| --- | --- | --- |
| 프로세스 | `agent-app-linux-arm64` | `nginx` master/worker 또는 `systemctl is-active nginx` |
| 포트 | 15034/tcp | 80/tcp, 443/tcp, 또는 실제 설정 포트 |
| 로그 | `monitor.log` | access/error log + 관제 로그 |
| 임계값 | CPU, MEM, 디스크 | 리소스 + 5xx 비율, 응답 시간, 연결 수 |

### 6-2. 프로세스는 살아 있는데 포트가 열리지 않을 때, 원인 후보와 확인 순서는 무엇인가?

**답변 예시**

> 우선 “포트가 로컬에서 LISTEN하지 않는 것”과 “외부에서 접속되지 않는 것”을 구분합니다. `ss`에 LISTEN이 없다면 방화벽보다 앱의 시작·바인딩 문제를 먼저 봐야 합니다. 방화벽은 외부 패킷을 막을 수는 있지만, 로컬 LISTEN 소켓을 없애지는 않기 때문입니다.

**확인 순서**

1. `ps` 또는 `pgrep`로 프로세스가 정말 기대한 실행 명령인지 확인한다.
2. `ss -ltnp`로 해당 포트에 LISTEN 소켓이 있는지, 있다면 어느 PID가 열었는지 확인한다.
3. 앱 또는 Nginx의 error log와 systemd journal을 보고 시작 실패·설정 오류를 확인한다.
4. 포트 충돌, 잘못된 포트 설정, `127.0.0.1`에만 바인딩한 경우, 권한 부족, 디스크 부족, 파일 디스크립터 고갈을 확인한다.
5. 로컬 LISTEN이 정상인데 외부 접속만 실패할 때 UFW, 보안 그룹, 라우팅, 클라이언트 연결을 확인한다.

**원인 후보**

- 앱이 초기화 중 오류를 만나 포트를 열기 전 멈춤
- 환경 변수의 포트가 다르거나 설정 파일이 잘못됨
- 다른 프로세스가 이미 같은 포트를 사용함
- 웹 서버가 루프백(`127.0.0.1`)에만 바인딩됨
- 1024 미만 포트 바인딩 권한, 디스크 공간, 파일 디스크립터 같은 운영 자원 부족

### 6-3. 로그 급증으로 디스크가 가득 찰 위험이 있으면 어떻게 대응하는가?

**답변 예시**

> 단기적으로는 `df -h`와 `du -sh /var/log/*`로 어느 로그가 얼마나 커졌는지 확인하고, 급증 원인인 반복 오류·디버그 로그·비정상 요청을 찾습니다. 서비스에 영향을 주지 않도록 먼저 로그를 보존하거나 복사한 뒤, 설정된 회전을 즉시 실행하거나 로그 레벨을 낮춥니다. 열려 있는 로그 파일을 무작정 `rm`하면 프로세스가 파일 핸들을 계속 잡고 있어 디스크가 바로 회수되지 않을 수 있으므로 주의해야 합니다.
>
> 중기적으로는 logrotate 또는 스크립트 회전 정책에 크기, 보존 개수, 압축, 보존 기간을 정하고, 디스크 사용률 경고를 더 이른 시점에 알림으로 연결합니다. 중앙 로그 저장소나 별도 볼륨을 쓰고, 반복적으로 로그를 폭증시키는 애플리케이션 오류를 수정하는 것도 필요합니다.

| 시점 | 우선 대응 |
| --- | --- |
| 단기 | 디스크·로그 용량 확인, 급증 원인 파악, 안전한 회전/압축, 필요 시 로그 레벨 완화 |
| 중기 | 보존 정책·알림·중앙 수집·저장 용량 계획, 애플리케이션 원인 수정 |

## 7. 평가 전에 확인할 마지막 체크리스트

- [ ] `sudo sshd -T`에서 `port 20022`, `permitrootlogin no`를 다시 확인했다.
- [ ] UFW가 active이고 20022/tcp, 15034/tcp 외 추가 인바운드 허용 규칙이 없는지 확인했다.
- [ ] 세 계정의 그룹 소속과 세 디렉터리의 ACL을 `sudo getfacl`로 다시 확인했다.
- [ ] `agent-admin`으로 실행한 앱 화면에서 5단계 `[OK]`와 `Agent READY`를 보여 줄 수 있다.
- [ ] 앱이 실행 중인 상태에서 `monitor.sh`를 실행해 프로세스·포트 `[OK]`, 로그 한 줄 추가를 보여 줄 수 있다.

## 8. 1분 요약 답변

> 이 과제에서는 서버를 안전하게 운영하기 위한 최소 환경을 만들었습니다. SSH는 20022 포트로 변경하고 Root 원격 로그인을 차단했으며, UFW에서는 SSH와 앱 포트 15034만 허용했습니다. 역할별로 계정과 그룹을 분리해 업로드 공간은 세 역할이 협업하고, API 키와 운영 로그는 admin·dev만 접근하도록 제한했습니다.
>
> 앱은 `agent-admin`으로 실행해 Boot Sequence 5단계를 통과했습니다. `monitor.sh`는 앱 프로세스와 15034 LISTEN 상태를 먼저 검사하고, 둘 중 하나가 비정상이면 `exit 1`로 종료합니다. 정상일 때는 CPU, 메모리, 루트 디스크 사용률과 PID를 고정된 형식의 로그로 남깁니다. cron이 이를 매분 실행하고, 로그는 10MiB 기준으로 회전해 현재 파일 포함 최대 10개를 유지하도록 구현했습니다.
