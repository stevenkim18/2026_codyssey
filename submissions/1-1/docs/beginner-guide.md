# 초심자를 위한 서버 관제 학습 가이드

이 문서는 1-1 과제를 처음 보는 사람을 위한 설명 자료다. 명령어를 외우는 것보다 **왜 이런 설정이 필요한지**, 그리고 각 설정이 어떻게 하나의 운영 흐름으로 이어지는지를 이해하는 데 초점을 둔다.

실제 구현과 검증 결과는 [수행 내역서](../README.md), 자동화 코드의 원문은 [monitor.sh](../monitor.sh), 최종 화면 증빙은 [검증 캡처](../evidence/verification-result.png)에서 확인할 수 있다.

> 이 문서는 완성된 환경을 이해하고 설명하기 위한 가이드다. 아래 명령어는 모두 **확인용**이며 서버 설정을 바꾸지 않는다. 처음부터 VM을 설치하는 튜토리얼은 아니다.

## 1. 이 과제가 해결하는 문제

서버에서 프로그램이 멈추거나 컴퓨터 자원이 부족해졌을 때, 기록이 없다면 나중에 원인을 추측해야 한다. 이 과제는 다음 세 가지를 함께 해결한다.

1. 서버에 들어오는 길을 안전하게 만든다.
2. 사람마다 필요한 권한만 주어 중요한 파일을 보호한다.
3. 앱이 살아 있는지와 자원 상태를 주기적으로 점검해 로그로 남긴다.

즉, 단순히 앱을 실행하는 과제가 아니라 **앱을 안전하게 계속 운영할 수 있는 최소 환경을 만드는 과제**다.

## 2. 전체 흐름 한눈에 보기

```text
[관리자 PC] -- SSH / TCP 20022 --> [UFW 방화벽] --> [sshd 서비스]

[앱 이용자] -- 앱 접속 / TCP 15034 --> [UFW 방화벽] --> [agent-app-linux-arm64]

[agent-admin의 cron: 매분]
              |
              v
         [monitor.sh] ------ 프로세스·포트 확인 ------> [앱]
              |
              +------------ UFW·CPU·MEM·DISK 확인 ----> [Ubuntu 시스템]
              |
              +------------ 한 줄씩 기록 -------------> [/var/log/agent-app/monitor.log]
```

위 흐름에서 앱은 `15034` 포트를 열고 기다린다. `monitor.sh`는 앱과 운영체제 상태를 확인한 뒤 로그를 남긴다. `cron`은 사람이 매번 명령을 실행하지 않아도 `monitor.sh`를 매분 실행하는 스케줄러다.

## 3. 먼저 알아둘 핵심 용어

| 용어 | 쉬운 설명 | 이 과제에서의 예 |
| --- | --- | --- |
| 서버 | 다른 컴퓨터나 사람에게 기능을 제공하는 컴퓨터 | UTM 안에서 실행한 Ubuntu Server VM |
| 서비스/데몬 | 사용자가 로그인하지 않아도 뒤에서 계속 동작하는 프로그램 | 원격 접속을 받는 `sshd` |
| 프로세스 | 지금 실행 중인 프로그램 한 개 | `agent-app-linux-arm64` 실행 인스턴스 |
| PID | 운영체제가 프로세스에 붙이는 고유 번호 | 로그의 `PID:3313` 같은 값 |
| 포트 | 한 컴퓨터 안에서 네트워크 프로그램을 구분하는 번호 | SSH는 `20022`, 앱은 `15034` |
| TCP | 연결을 확인하며 데이터를 전달하는 네트워크 방식 | 이 과제에서 허용한 두 포트의 프로토콜 |
| SSH | 네트워크를 통해 서버 터미널에 안전하게 접속하는 방법 | 맥에서 Ubuntu VM에 접속할 때 사용 |
| 방화벽 | 들어오고 나가는 네트워크 연결을 규칙으로 통제하는 장치 | UFW가 허용되지 않은 인바운드 연결을 막음 |
| 사용자·그룹 | 리눅스에서 사람 또는 역할을 구분하는 단위 | `agent-admin`, `agent-dev`, `agent-test`와 역할 그룹 |
| ACL | 기본 소유자·그룹 권한보다 세밀하게 추가하는 접근 규칙 | 홈 디렉터리 탐색 권한과 새 파일의 기본 권한 |
| 환경 변수 | 프로그램 실행 전에 전달하는 이름-값 설정 | `AGENT_PORT=15034` |
| cron | 정해진 시간마다 명령을 자동 실행하는 리눅스 스케줄러 | 매분 `monitor.sh` 실행 |
| 로그 회전 | 로그가 무한히 커지지 않도록 오래된 로그를 밀어내는 관리 방식 | 10MB 기준, 현재 파일 포함 최대 10개 유지 |

## 4. 안전하게 접속시키는 방법: SSH와 방화벽

### SSH: 관리용 출입문

SSH는 원격 서버의 터미널에 접속하는 관리용 통로다. 이 환경에서는 기본 SSH 포트 대신 `20022`를 사용하고, `root` 계정의 원격 로그인을 막았다.

```text
Port 20022
PermitRootLogin no
```

- `Port 20022`: 흔히 스캔되는 기본 포트 `22` 대신 별도 번호를 쓴다. 무작위 접속 시도를 줄이는 **보조 수단**이지만, 이것만으로 서버가 안전해지는 것은 아니다.
- `PermitRootLogin no`: 시스템 전체를 바꿀 수 있는 최고 관리자 계정인 `root`로 바로 접속하지 못하게 한다. 일반 계정으로 접속한 뒤 필요한 일만 `sudo`로 수행하면 작업 주체를 추적하고 실수를 줄이기 쉽다.

**확인용 명령어**

```bash
sudo sshd -T | grep -E '^(port|permitrootlogin)'
sudo ss -tulnp | grep sshd
```

첫 명령은 SSH가 실제로 적용한 설정을 보여 준다. 두 번째 명령은 `sshd`가 `0.0.0.0:20022`과 `[::]:20022`에서 연결을 기다리는지(LISTEN 상태인지) 확인한다. `0.0.0.0`은 모든 IPv4 네트워크 인터페이스에서 받는다는 뜻이고, `[::]`는 IPv6에 대한 같은 의미다.

### UFW: 필요한 문만 여는 경비원

UFW는 Ubuntu에서 사용하는 방화벽 관리 도구다. 이 과제의 정책은 다음 한 문장으로 요약된다.

> 외부에서 들어오는 연결은 기본적으로 막고, SSH용 TCP 20022와 앱용 TCP 15034만 허용한다.

이 방식을 **최소 권한 원칙**이라고 한다. 앱이 실수로 다른 포트를 열더라도 UFW 규칙이 없다면 외부에서 접속하기 어렵다. 반대로 꼭 필요한 관리와 서비스 기능은 계속 사용할 수 있다.

**확인용 명령어**

```bash
sudo ufw status numbered
```

정상 결과에서는 UFW 상태가 `active`이고, IPv4·IPv6 각각에 `20022/tcp`, `15034/tcp`만 `ALLOW IN`으로 표시된다. 캡처의 IPv6 규칙은 중복 오류가 아니라 UFW가 IPv6 연결도 같은 정책으로 보호한 결과다.

## 5. 사람마다 다른 권한을 주는 방법: 사용자, 그룹, ACL

### 역할을 먼저 나눈 이유

과제에는 세 계정과 두 역할 그룹이 있다.

| 계정 | 역할 | 소속 그룹 |
| --- | --- | --- |
| `agent-admin` | 운영·관리, cron 실행 | `agent-common`, `agent-core` |
| `agent-dev` | 개발·운영, `monitor.sh` 작성 | `agent-common`, `agent-core` |
| `agent-test` | QA·테스트 | `agent-common` |

`agent-common`은 세 사람이 함께 쓰는 업로드 공간을 위한 그룹이다. `agent-core`는 키와 운영 로그처럼 더 민감한 자원에 접근할 수 있는 개발·운영 그룹이다. 그래서 테스트 계정은 공유 업로드에는 참여하지만 API 키와 운영 로그에는 접근하지 못한다.

### `rwx`는 파일과 디렉터리에서 뜻이 다르다

리눅스 권한은 소유자(user), 그룹(group), 그 밖의 사용자(other)에 대해 `r`, `w`, `x`를 각각 정한다.

| 권한 | 일반 파일 | 디렉터리 |
| --- | --- | --- |
| `r` | 내용을 읽을 수 있음 | 안의 이름 목록을 볼 수 있음 |
| `w` | 내용을 수정할 수 있음 | 항목을 만들거나 지울 수 있음. 보통 `x`도 함께 필요 |
| `x` | 실행할 수 있음 | 그 디렉터리를 통과해 내부 파일에 접근할 수 있음 |

디렉터리의 `x`는 특히 중요하다. 파일 이름을 알고 있어도 상위 디렉터리를 통과할 권한이 없으면 접근할 수 없다. 검증 캡처에서 일반 `user`가 `$AGENT_HOME` 아래의 `bin`, `api_keys`, `upload_files`를 조회할 때 `Permission denied`가 나온 이유가 이것이다. `user`는 과제의 서비스 역할 그룹에 속하지 않으므로, 이 거절은 설정 실패가 아니라 의도한 보호 동작이다.

### 실제 디렉터리 정책

| 경로 | 그룹 | 접근 가능한 역할 | 이유 |
| --- | --- | --- | --- |
| `$AGENT_HOME/upload_files` | `agent-common` | admin, dev, test | 세 역할이 협업하는 업로드 공간 |
| `$AGENT_HOME/api_keys` | `agent-core` | admin, dev | 키는 QA 계정에 노출하지 않음 |
| `/var/log/agent-app` | `agent-core` | admin, dev | 운영 로그를 변경·열람할 수 있는 사람을 제한 |
| `$AGENT_HOME/bin/monitor.sh` | `agent-core` | admin, dev | 개발자가 작성하고 운영 계정이 실행 |

권한 앞자리의 `2`는 **setgid 비트**다. 예를 들어 `2770` 디렉터리 안에 새 파일을 만들면 그 파일은 만든 사람의 개인 그룹 대신 디렉터리 그룹을 상속한다. 공유 작업 중 파일의 그룹이 제각각이 되어 협업이 막히는 일을 줄인다.

ACL은 기본 소유자·그룹 규칙만으로 표현하기 어려운 예외를 보완한다. 이 환경에서는 `agent-common` 구성원이 `/home/agent-admin`을 통과해 앱 디렉터리까지 갈 수 있도록 하고, 공유 디렉터리에 기본 ACL을 적용해 새 파일에도 정한 협업 정책이 이어지게 했다.

**확인용 명령어**

```bash
id agent-admin
id agent-dev
id agent-test
sudo getfacl -p /home/agent-admin/agent-app/upload_files \
  /home/agent-admin/agent-app/api_keys \
  /var/log/agent-app
```

`getfacl`은 일반 `user`로 실행하면 상위 경로를 통과하지 못해 실패할 수 있다. ACL 자체를 검토할 때는 위처럼 `sudo`를 사용하거나, 권한이 있는 역할 계정으로 확인해야 한다.

## 6. 앱이 같은 방식으로 실행되게 만드는 방법: 환경 변수

프로그램을 실행할 때 경로와 포트를 코드 안에만 넣어 두면 계정이나 서버가 바뀔 때 수정하기 어렵다. 환경 변수는 실행 환경에서만 값을 주입하는 설정값이다. 이 과제에서는 `agent-admin`의 `~/.profile`에 다음 값을 두었다.

| 변수 | 실제 값 | 역할 |
| --- | --- | --- |
| `AGENT_HOME` | `/home/agent-admin/agent-app` | 앱의 기준 디렉터리 |
| `AGENT_PORT` | `15034` | 앱이 사용할 TCP 포트 |
| `AGENT_UPLOAD_DIR` | `$AGENT_HOME/upload_files` | 공유 업로드 경로 |
| `AGENT_KEY_PATH` | `$AGENT_HOME/api_keys` | 제공 실행 파일이 검사하는 키 디렉터리 |
| `AGENT_LOG_DIR` | `/var/log/agent-app` | 앱과 관제 로그 경로 |

`~/.profile`은 로그인할 때 읽히는 셸 설정 파일이다. 이미 로그인한 터미널에서 새 값을 바로 반영하려면 `source ~/.profile`을 실행한다.

**확인용 명령어**

```bash
sudo -iu agent-admin
source ~/.profile
env | grep '^AGENT_'
```

### ARM64 실행 파일을 선택한 이유

CPU는 서로 다른 명령어 형식을 사용한다. Apple Silicon 기반 UTM VM은 ARM64(`aarch64`) CPU이므로, 압축 파일에 함께 있던 x86 실행 파일 대신 `agent-app-linux-arm64`를 사용했다. 다른 CPU용 실행 파일을 고르면 프로그램이 시작하지 않을 수 있다.

```bash
file /home/agent-admin/agent-app/agent-app-linux-arm64
```

결과의 `ARM aarch64`는 현재 VM과 맞는 실행 파일이라는 뜻이다.

### 키 파일 요구사항의 실제 차이

과제 명세는 `api_keys/t_secret.key` 파일에 `agent_api_key_test` 한 줄을 두도록 요구한다. 이 값은 과제용 테스트 키이며 실제 서비스 비밀값을 문서에 넣는 방식과는 다르다.

제공된 실행 파일은 명세와 달리 `AGENT_KEY_PATH`를 **파일이 아닌 `api_keys` 디렉터리**로 받고, 그 안의 `secret.key`를 확인했다. 따라서 이 구현은 요구된 `t_secret.key`를 그대로 만들고, 같은 파일을 가리키는 `secret.key` 하드 링크를 추가했다. 하드 링크는 파일 내용을 복사하는 것이 아니라 한 파일에 두 이름을 붙이는 방법이므로 두 키가 서로 달라지는 문제가 없다.

이 사례의 핵심은 “문서의 기대값”과 “실행 파일이 실제로 검사하는 값”이 다를 수 있으므로, 오류 메시지와 실행 결과를 근거로 호환 방식을 확인해야 한다는 점이다.

### Boot Sequence가 확인하는 것

일반 계정 `agent-admin`으로 앱을 실행하면 Boot Sequence가 다음 다섯 가지를 검사한다.

| 단계 | 확인 대상 | 실패하면 알 수 있는 문제 |
| --- | --- | --- |
| 1 | 실행 계정 | root로 실행했거나 서비스 계정이 잘못됨 |
| 2 | 환경 변수 | 경로·포트 설정이 누락되었거나 값이 다름 |
| 3 | 키 파일 | 키 경로, 이름, 내용, 읽기 권한이 맞지 않음 |
| 4 | 포트 | 15034가 이미 다른 프로그램에 사용 중임 |
| 5 | 로그 디렉터리 | 앱이 로그를 쓸 권한이 없음 |

다섯 단계가 모두 `[OK]`이고 `Agent READY`가 나오면, 앱이 `0.0.0.0:15034`에서 서비스할 준비를 마친 것이다.

## 7. `monitor.sh`가 하는 일

자동화 코드는 [monitor.sh](../monitor.sh)에 있다. 이 스크립트는 단순히 숫자를 출력하는 프로그램이 아니라, 앱의 기본 생존 여부를 먼저 확인한 뒤 운영 정보를 로그로 보존한다.

### 실행 전에 안전장치를 거는 부분

- `set -u`: 값이 없는 변수를 실수로 사용하면 바로 오류로 처리한다.
- `set -o pipefail`: 파이프로 연결한 명령 중 앞부분이 실패해도 실패를 놓치지 않는다.
- `PATH=...`: cron처럼 제한된 환경에서도 `ss`, `df`, `free` 같은 명령을 일관되게 찾도록 한다.
- `umask 007`: 새 파일을 만들 때 other 사용자에게 권한이 생기지 않도록 기본 권한을 제한한다.
- `flock`: 이전 실행이 아직 끝나지 않았을 때 두 번째 실행이 동시에 로그를 건드리지 못하게 한다.

### 1단계: Health Check는 실패하면 종료한다

스크립트는 다음 두 조건 중 하나라도 만족하지 않으면 `exit 1`로 끝난다.

1. `pgrep -f agent-app-linux-arm64`로 앱 프로세스를 찾을 수 있어야 한다.
2. `ss -ltnH` 결과에서 TCP `15034` 포트가 LISTEN 상태여야 한다.

두 검사가 필요한 이유는 서로 확인하는 대상이 다르기 때문이다. 프로세스가 있어도 앱 초기화가 끝나지 않아 포트를 열지 못할 수 있고, 포트만 열려 있어도 다른 프로그램이 그 포트를 사용하고 있을 수 있다. Health Check 실패는 “이 상태의 자원 수치는 앱 운영 상태를 대표하지 못한다”는 뜻이므로 바로 종료한다.

### 2단계: 방화벽과 자원은 경고만 남긴다

UFW 상태, CPU, 메모리, 루트 디스크 사용률은 확인한다. 다만 UFW를 읽지 못했거나 자원 임계값을 넘었다고 해서 로그 기록 자체를 포기하지는 않는다. 이런 경우에는 `[WARNING]`을 출력하고 계속 진행한다.

| 항목 | 수집 방법 | 경고 기준 |
| --- | --- | --- |
| CPU | `/proc/stat`을 1초 간격으로 두 번 읽어 사용 시간 비율 계산 | `> 20%` |
| 메모리 | `free -b`에서 사용량 ÷ 전체량 계산 | `> 10%` |
| 디스크 | `df -P /`에서 루트(`/`) 파티션 사용률 확인 | `> 80%` |
| 방화벽 | `sudo -n /usr/sbin/ufw status` | 비활성 또는 조회 실패 시 경고 |

`sudo -n`의 `-n`은 암호 입력을 기다리지 않는다는 뜻이다. cron은 비대화형으로 실행되기 때문에 암호를 물어보면 멈춘다. 그래서 `agent-admin`에는 UFW 상태 조회 명령 하나에만 비밀번호 없는 sudo 권한을 주었다.

### 3단계: 로그를 남기고 오래된 로그를 정리한다

정상 Health Check 뒤에는 아래처럼 한 줄의 구조화 로그를 남긴다.

```text
[YYYY-MM-DD HH:MM:SS] PID:... CPU:..% MEM:..% DISK_USED:..%
```

시간과 PID가 함께 있으면 “언제, 어느 앱 실행 인스턴스가, 어느 정도 자원을 썼는지”를 나중에 비교할 수 있다. 스크립트는 `monitor.log` 권한을 `660`으로 유지해 admin/dev 역할만 읽고 쓸 수 있게 한다.

로그가 10MB 이상이면 현재 `monitor.log`를 `monitor.log.1`로 옮기고, 기존 `.1`~`.8`은 한 번호씩 뒤로 민다. `.9`는 제거한다. 따라서 현재 로그 하나와 과거 로그 아홉 개, 즉 최대 10개만 남는다. 이는 장애 분석에 필요한 최근 기록은 남기되 로그가 디스크를 계속 차지하지 않게 하는 보존 정책이다.

## 8. cron으로 사람이 아닌 컴퓨터가 매분 확인하게 만들기

`agent-admin`의 crontab에는 다음 한 줄이 등록되어 있다.

```cron
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >/dev/null 2>&1
```

앞의 별 다섯 개는 차례로 분, 시, 일, 월, 요일을 뜻한다. 모두 `*`이므로 매분 실행한다. 뒤의 `>/dev/null 2>&1`은 콘솔 출력과 오류 출력을 버린다는 뜻이다. 중요한 결과는 터미널이 아니라 스크립트가 직접 기록하는 `monitor.log`에 남으므로, cron에서 메일이 쌓이는 일을 막을 수 있다.

`agent-admin`이 cron 실행자인 이유는 앱의 실행 상태와 운영 로그에 접근할 수 있는 `agent-core` 구성원이기 때문이다. `agent-dev`는 스크립트 작성자이고, `agent-admin`은 운영 자동화 실행자라는 역할 분리도 여기서 드러난다.

**확인용 명령어**

```bash
sudo crontab -u agent-admin -l
sudo tail -n 5 /var/log/agent-app/monitor.log
```

검증은 다음 순서로 해석하면 된다.

1. `monitor.sh`를 수동으로 실행해 Health Check와 로그 기록을 확인한다.
2. crontab에 매분 실행 규칙이 있는지 확인한다.
3. 1~2분 뒤 로그의 시간을 다시 본다.
4. 새 시각의 로그 줄이 추가되었으면 사람이 실행하지 않아도 자동 실행된 것이다.

## 9. 검증 캡처를 읽는 방법

[검증 캡처](../evidence/verification-result.png)의 각 부분은 아래 요구사항을 보여 준다.

| 캡처의 명령·출력 | 무엇을 증명하는가 |
| --- | --- |
| `sshd -T`의 `port 20022`, `permitrootlogin no` | SSH 포트 변경과 Root 원격 로그인 차단 |
| `ss -tulnp`의 `0.0.0.0:20022` LISTEN | SSH 서비스가 새 포트에서 실제 대기 중 |
| `ufw status numbered`의 네 허용 행 | IPv4·IPv6의 20022/tcp·15034/tcp 허용 |
| `id agent-*` 결과 | 계정별 `agent-common`, `agent-core` 소속 |
| `Permission denied`와 `/var/log/agent-app` 권한 | 일반 `user`가 민감한 서비스 디렉터리를 탐색할 수 없음 |
| `monitor.sh`의 `agent-dev:agent-core 750` | 스크립트 소유자·그룹·실행 권한 정책 |
| `monitor.log`의 연속된 다른 시각 | 매분 cron이 자동으로 로그를 누적함 |

하나의 결과만 보는 대신, “설정값”, “실제로 리슨 중인 상태”, “권한 적용 결과”, “시간이 흐른 뒤의 로그 변화”를 함께 제시하는 것이 좋은 운영 검증이다.

## 10. 평가에서 설명할 수 있어야 하는 질문과 답

### Q1. SSH 포트만 22에서 20022로 바꾸면 안전한가?

아니다. 기본 포트 스캔 노출을 줄이는 보조 수단일 뿐이다. 핵심은 Root 원격 로그인을 차단하고, 방화벽으로 필요한 포트만 열며, 일반 계정과 최소 권한을 쓰는 여러 방어를 함께 적용하는 것이다.

### Q2. 왜 Root로 직접 접속하지 않는가?

Root는 시스템 전체 권한을 가진다. Root 계정이 탈취되면 피해 범위가 매우 크다. 일반 계정으로 로그인한 뒤 필요한 작업에만 `sudo`를 쓰면 권한 상승 시점과 작업 주체를 더 명확히 관리할 수 있다.

### Q3. 왜 `agent-common`과 `agent-core`을 나누었는가?

업로드 파일은 개발·운영·테스트가 함께 다뤄야 하지만, API 키와 운영 로그는 더 제한된 역할만 다뤄야 한다. 그룹을 역할 단위로 나누면 계정을 한 명씩 설정하지 않고도 같은 정책을 적용할 수 있다.

### Q4. `Permission denied`는 언제 문제이고, 언제 정상인가?

권한이 있어야 하는 `agent-admin` 또는 `agent-dev`가 거절되면 문제다. 하지만 서비스 역할 밖의 일반 `user`나 `agent-test`가 `api_keys`·운영 로그에 거절되는 것은 민감한 자원이 분리되었다는 정상 결과다. 먼저 “어떤 역할이 접근해야 하는가”를 기준으로 판단한다.

### Q5. 환경 변수는 왜 쓰는가?

앱 경로, 포트, 업로드·키·로그 위치를 실행 코드와 분리하기 위해서다. 같은 프로그램을 다른 계정이나 서버에서 실행할 때 값만 바꿔 재사용할 수 있고, Boot Sequence로 누락·오타·권한 문제를 빠르게 찾을 수 있다.

### Q6. 프로세스와 포트를 둘 다 확인하는 이유는 무엇인가?

프로세스 존재는 프로그램이 시작됐다는 신호이고, 포트 LISTEN은 외부 연결을 받을 준비가 됐다는 신호다. 둘 중 하나만 확인하면 “실행 중이지만 서비스 불가” 또는 “다른 프로그램이 포트를 사용”하는 상황을 놓칠 수 있다.

### Q7. CPU나 메모리가 임계값을 넘으면 왜 스크립트를 실패시키지 않는가?

자원 사용률이 높다는 것은 조사·경고가 필요한 상태이지 앱이 반드시 죽었다는 뜻은 아니다. 이 과제에서는 앱 프로세스와 포트 이상만 치명적 실패로 보고 `exit 1`을 사용한다. 자원·방화벽 문제는 로그를 계속 남겨 원인을 분석할 수 있도록 경고로 처리한다.

### Q8. 로그를 남기기만 하면 되지, 왜 회전도 필요한가?

로그가 무한히 커지면 디스크가 가득 차 앱과 운영체제 모두에 장애를 낼 수 있다. 회전 정책은 최근 기록을 보존하면서 파일 크기와 개수를 제한해 관측 가능성과 디스크 안전성을 함께 확보한다.

### Q9. cron을 쓸 때 왜 실행 계정과 권한을 신경 써야 하는가?

cron은 터미널에서 로그인한 사람이 아니라 등록된 계정의 제한된 환경에서 실행된다. 이 과제에서는 `agent-admin`이 앱 상태와 로그 디렉터리에 접근할 수 있고, UFW 상태 조회에 필요한 최소 sudo 권한도 있으므로 적합한 실행자다.

## 11. 설명 전 마지막 점검

다른 사람에게 과제를 설명하기 전, 아래 문장을 자신의 말로 말할 수 있으면 충분하다.

- “서버의 관리 통로는 20022로 옮기고 Root 직접 로그인은 막았습니다.”
- “UFW는 외부 연결을 기본 거부하고 SSH와 앱 포트만 열었습니다.”
- “공유 업로드와 민감한 키·로그를 서로 다른 그룹으로 나눴습니다.”
- “환경 변수와 Boot Sequence로 앱이 올바른 계정·경로·포트에서 실행되는지 확인했습니다.”
- “관제 스크립트는 앱 프로세스와 포트를 먼저 확인하고, 자원 상태를 로그로 남깁니다.”
- “cron이 매분 스크립트를 실행하고 로그 회전이 저장 공간을 보호합니다.”

이 여섯 문장은 과제의 학습 목표와 직접 연결된다. 세부 명령어를 모두 암기하는 것보다, 각 문장이 **어떤 문제를 막고 어떤 결과로 검증됐는지** 설명하는 것이 중요하다.
