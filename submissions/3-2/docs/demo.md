# Mini Git 시연 및 구현 설명

3-2 과제의 구현 결과를 시연하면서 동작과 구현 이유를 함께 확인하는 문서다. 1~7절의 명령을 순서대로 실행하면 하나의 예제로 필수 기능을 모두 확인할 수 있다. 각 절의 **확인할 내용**은 화면에서 볼 결과이고, **동작과 구현 이유**는 해당 기능을 설명할 때 참고할 내용이다.

## 1. 프로그램 실행과 구현 범위

저장소 루트에서 실행한다.

```bash
cd submissions/3-2
python3 main.py
```

### 확인할 내용

`mini-git>` 프롬프트가 나타나고 명령을 반복해서 입력할 수 있다. 명령어는 대소문자를 구분하지 않으며, 공백이 포함된 사용자명·메시지·검색어는 따옴표로 묶는다.

### 동작과 구현 이유

이 프로그램은 커밋의 메타데이터와 브랜치 관계를 메모리에 관리한다. 커밋 그래프, 탐색, 정렬, 역색인을 직접 구현하는 것이 과제의 핵심이다. 실제 파일 내용 추적, 영속 저장, 네트워크 통신은 포함하지 않았으며 종료하면 데이터가 사라진다. 보너스인 DIFF, MERGE, 정렬 성능 비교도 구현하지 않았다.

입력 → 명령 해석 → 실행 → 출력이 반복되는 방식을 REPL이라고 한다. `shlex.split()`으로 따옴표와 공백을 처리하고, 명령어를 대문자로 정규화한 뒤 저장소의 기능을 호출한다. 입력 오류가 발생해도 오류 메시지를 출력하고 다음 명령을 받는다.

코드는 커밋 모델, 저장소와 명령 처리, 탐색·정렬 알고리즘, CLI로 역할을 나눴다. 특히 알고리즘을 입출력과 분리하여 테스트에서 직접 호출할 수 있도록 했다. Python 3.10 이상에서 실행하며 외부 라이브러리는 사용하지 않는다.

## 2. 초기화와 커밋 생성

```text
init "Alice Kim"
COMMIT "Initial commit"
```

### 확인할 내용

```text
Initialized repository.
Current branch: main
Current user: Alice Kim
[main c000001] Initial commit
```

초기화하면 `main` 브랜치와 작성자가 설정된다. 첫 커밋은 `c000001`이며 부모가 없는 루트 커밋이다. 이 문서의 커밋 번호는 프로그램을 새로 실행하고 명령을 순서대로 입력한 경우를 기준으로 한다.

### 동작과 구현 이유

커밋은 다음 정보를 가진다.

| 필드 | 의미와 용도 |
| --- | --- |
| `hash` | 커밋을 찾거나 경로 탐색에 사용할 유일한 식별자 |
| `message` | 커밋 설명과 키워드 검색 대상 |
| `author` | 초기화 시 설정한 작성자이며 작성자 검색·정렬 기준 |
| `timestamp` | 커밋 생성 시각이며 날짜 정렬 기준 |
| `parents` | 이전 커밋과 연결하는 부모 hash 튜플 |
| `sequence` | 생성 순서이며 hash 생성과 정렬의 동률 처리에 사용 |

`hash`는 증가 카운터를 `c000001` 형식으로 표현한 값이다. 커밋 내용으로 계산한 암호학적 해시는 아니지만, 카운터를 계속 증가시키므로 실행 중 식별자가 중복되지 않는다. 생성 시각은 로컬 현재 시각을 사용하므로 실행할 때마다 달라진다.

커밋은 `hash → Commit` 딕셔너리에 저장한다. 딕셔너리는 키로 값을 찾는 해시맵으로, hash를 알고 있으면 전체 목록을 뒤지지 않고 평균 `O(1)`에 조회할 수 있다. `Commit`은 `frozen=True`인 데이터 클래스로 정의하여 생성 후 필드를 변경하지 않도록 했다.

새 커밋을 만들 때는 현재 HEAD를 부모로 기록하고, 커밋 저장소와 부모의 자식 목록을 갱신한다. 이어서 현재 브랜치가 새 커밋을 가리키게 하고 키워드·작성자 역색인에도 등록한다. 커밋이 하나 생성되면 로그, 탐색, 검색에서 함께 사용할 정보가 준비되는 것이다.

## 3. 브랜치 생성·전환과 커밋 그래프

```text
BRANCH feature
SWITCH feature
COMMIT "Add login feature"
COMMIT "Fix login bug"
SWITCH main
COMMIT "Add payment feature"
```

### 확인할 내용

feature에서 `c000002`, `c000003`이 생성되고, main에서 `c000004`가 생성된다. 만들어진 관계는 다음과 같다. 화살표는 부모에서 자식 방향으로 표시했다.

```text
c000001 ─┬─→ c000002 ─→ c000003  [feature]
         └─→ c000004             [main]
```

| 시점 | 현재 브랜치 | main이 가리키는 커밋 | feature가 가리키는 커밋 |
| --- | --- | --- | --- |
| feature 생성 직후 | main | c000001 | c000001 |
| feature에서 두 번 커밋한 뒤 | feature | c000001 | c000003 |
| main에서 커밋한 뒤 | main | c000004 | c000003 |

### 동작과 구현 이유

브랜치는 `브랜치 이름 → 마지막 커밋 hash` 딕셔너리로 관리한다. 브랜치를 만드는 것은 커밋 전체를 복사하는 작업이 아니라 현재 HEAD의 hash를 새 이름에 등록하는 작업이다. `BRANCH`는 현재 브랜치를 바꾸지 않으며, 실제 전환은 `SWITCH`가 담당한다.

현재 구현에는 별도의 HEAD 객체가 없다. 현재 브랜치 이름을 저장하고, 그 브랜치가 가리키는 hash를 조회하여 HEAD로 사용한다. feature에서 새 커밋을 만들어도 main의 참조는 그대로 남으므로, main으로 돌아왔을 때 `c000004`의 부모는 `c000003`이 아닌 `c000001`이 된다.

그래프는 노드와 연결 관계를 표현하는 자료구조다. 여기서는 커밋이 노드이고 부모 관계가 연결이므로, 한 줄짜리 목록보다 분기와 조상 관계를 표현하기에 적합하다. 각 커밋의 `parents`에는 부모 hash를 저장하고, 별도의 `children` 딕셔너리에는 부모별 자식 hash 목록을 저장한다. 이 자식 목록 덕분에 로그나 경로 탐색에서 자식을 찾기 위해 전체 커밋을 다시 검사할 필요가 없다.

DAG는 방향이 있고 순환이 없는 그래프다. 새 커밋은 이미 존재하는 커밋만 부모로 삼고 기존 부모 관계는 바꾸지 않으므로, 부모를 계속 따라가도 자기 자신으로 되돌아오지 않는다. 저장된 부모 참조는 자식에서 부모 방향이지만, 로그에서는 부모가 먼저 나오도록 반대 방향의 자식 목록을 함께 사용한다.

부모 목록을 튜플로 정의하여 여러 부모를 표현할 수 있게 했다. 다만 현재 CLI의 `COMMIT`은 부모가 0개 또는 1개인 커밋만 만들며, 여러 부모를 만드는 MERGE는 구현하지 않았다.

## 4. 로그·최단 경로·조상 탐색

### 4.1 LOG: 부모가 먼저 나오는 전체 로그

```text
LOG
```

**확인할 내용:** 현재 브랜치만이 아니라 전체 저장소의 커밋을 `c000001`, `c000002`, `c000003`, `c000004` 순서로 출력한다. 각 커밋의 hash, 작성자, 시각, 메시지를 확인할 수 있다.

**동작과 구현 이유:** 기본 로그의 기준은 최신순이 아니라 **부모가 자식보다 먼저 나오는 순서**다. 이를 위해 선행 관계를 지키며 노드를 나열하는 위상 정렬을 사용한다.

구현은 Kahn 방식이며 다음 순서로 진행한다.

1. 각 커밋의 부모 수를 진입 차수로 계산한다. 여기서 진입 차수는 부모 → 자식 방향을 기준으로 한다.
2. 부모 수가 0인 커밋을 출력 가능한 목록에 넣는다.
3. 목록에서 하나를 출력하고 그 자식의 남은 부모 수를 줄인다.
4. 남은 부모 수가 0이 된 자식을 목록에 넣고 반복한다.

예제에서 `c000001`을 출력하면 `c000002`, `c000004`가 모두 출력 가능해진다. 구현은 그중 생성 순서가 빠른 `c000002`를 고른다. 이어서 `c000003`이 준비되며, 이것도 `c000004`보다 먼저 생성되어 먼저 출력된다. 위상 정렬 결과는 여러 개일 수 있지만, 생성 순서로 선택하여 결과를 일정하게 유지했다.

### 4.2 PATH: 두 브랜치 사이의 최단 경로

```text
PATH c000003 c000004
```

**확인할 내용:**

```text
Path: c000003 -> c000002 -> c000001 -> c000004
```

커밋 4개를 지나지만 이동한 간선 수는 3개다. 과제에서 정의한 경로 길이는 간선 수다.

**동작과 구현 이유:** PATH에서는 부모 연결을 무방향으로 취급한다. 부모 방향으로만 이동하면 `c000001`까지 갈 수 있어도 다른 갈래의 자식인 `c000004`로 이동할 수 없기 때문이다. 부모 목록과 자식 목록을 모두 이웃으로 사용한다.

모든 간선의 비용이 1이므로 BFS가 적합하다. BFS는 가까운 노드부터 차례로 방문하여 처음 발견한 거리가 최단거리가 되도록 한다. 먼저 발견한 노드를 먼저 처리하기 위해 FIFO 큐인 `deque`를 사용한다. 반면 DFS는 한 갈래를 깊게 따라가므로 도착점을 처음 발견했다고 해서 최단 경로를 보장하지 않는다.

현재 구현은 도착점인 `c000004`에서 BFS를 시작하여 각 커밋에서 도착점까지 남은 거리를 구한다.

| 커밋 | 도착점까지 남은 거리 |
| --- | ---: |
| c000003 | 3 |
| c000002 | 2 |
| c000001 | 1 |
| c000004 | 0 |

이후 출발점부터 남은 거리가 정확히 1씩 줄어드는 이웃을 고르면 최단 경로가 만들어진다. 그런 이웃이 여러 개라면 hash가 가장 작은 것을 선택하여 최단 경로 중 사전순으로 가장 작은 경로를 만든다. 거리 딕셔너리는 방문 여부도 함께 관리하여 같은 커밋을 반복해서 큐에 넣지 않도록 한다.

출발점과 도착점이 같으면 커밋 하나만 출력하고, 서로 연결되지 않았으면 `No path`를 출력한다. 이 시연 그래프에는 경로가 하나뿐이며, 여러 최단 경로의 사전순 선택은 기존 테스트에서 여러 부모를 가진 그래프를 구성하여 검증한다.

### 4.3 ANCESTORS: 해당 커밋의 모든 조상

```text
ANCESTORS c000003
```

**확인할 내용:** `c000001`, `c000002`가 순서대로 나온다. 자기 자신인 `c000003`과 다른 갈래의 `c000004`는 나오지 않는다.

**동작과 구현 이유:** 조상은 부모 방향으로 따라가서 도달할 수 있는 모든 커밋이다. PATH와 달리 자식 방향은 탐색하지 않으며, 시작 커밋의 부모부터 탐색하므로 자기 자신도 제외된다.

리스트를 스택으로 사용해 부모 hash를 넣고 마지막에 넣은 것부터 꺼낸다. 이는 DFS 방식의 탐색이며, 모든 조상을 수집하는 목적이라 최단거리 계산이 필요하지 않다. 집합에 방문한 hash를 기록하여 여러 경로에서 같은 조상을 만나도 한 번만 처리한다.

탐색과 출력 순서는 별개다. 예제의 탐색에서는 가까운 부모인 `c000002`를 먼저 찾지만, 수집한 조상에 위상 정렬을 적용하여 화면에는 `c000001`, `c000002` 순서로 보여준다. 루트 커밋을 조회하면 `No ancestors.`가 나온다.

## 5. 키워드·작성자 검색과 역색인

```text
SEARCH "LOGIN"
SEARCH "login feature"
SEARCH "--author=alice kim"
```

### 확인할 내용

| 명령 | 검색 결과 | 확인하는 동작 |
| --- | --- | --- |
| `SEARCH "LOGIN"` | c000002, c000003 — 2개 | 대소문자 정규화 |
| `SEARCH "login feature"` | c000002 — 1개 | 여러 토큰을 모두 포함하는 커밋 검색 |
| `SEARCH "--author=alice kim"` | c000001~c000004 — 4개 | 공백이 있는 작성자 이름과 대소문자 정규화 |

### 동작과 구현 이유

역색인은 **검색어 → 해당 검색어를 포함하는 항목 목록**으로 연결하는 구조다. 커밋마다 메시지를 검사하는 대신, 커밋 생성 시 미리 만든 목록에서 후보를 가져오기 위해 사용했다. 키워드와 작성자용으로 각각 딕셔너리를 관리한다.

이 시연에서 키워드 역색인의 일부는 다음과 같다.

```text
login   → [c000002, c000003]
feature → [c000002]
payment → [c000004]
```

메시지는 공백으로 분리하고 소문자로 바꾼다. 예를 들어 `Add login feature`는 `add`, `login`, `feature`로 등록된다. 한 메시지에 같은 단어가 반복되어도 집합으로 중복을 확인하여 해당 hash는 한 번만 등록한다.

`SEARCH "login feature"`는 두 목록의 교집합을 구한다. 따라서 단어의 연속된 문장 일치가 아니라 **두 토큰을 모두 포함하는지**를 확인한다. 부분 문자열 검색도 아니므로 `log`로 `login`을 찾을 수 없고, 별도로 문장부호를 제거하지 않아 `login`과 `login,`는 다른 토큰이다. 작성자 검색은 소문자로 정규화한 이름 전체가 일치하는 목록을 조회한다.

역색인은 메시지 전체를 다시 검사하지 않고 후보를 얻는다는 장점이 있다. 다만 현재 키워드 검색은 결과를 생성 순서로 반환하기 위해 마지막에 전체 커밋 딕셔너리를 순회한다. 따라서 후보 조회가 빨라도 전체 검색 비용을 결과 수 `K`에만 비례하는 `O(K)`라고 설명해서는 안 된다. 작성자 검색은 해당 목록을 바로 사용하므로 평균 `O(K)`다.

## 6. 날짜·작성자 정렬과 병합 정렬

```text
LOG --sort-by=date
LOG --sort-by=author
```

### 확인할 내용

| 명령 | 주 정렬 기준 | 기준값이 같을 때 |
| --- | --- | --- |
| `LOG --sort-by=date` | timestamp 오름차순 | 생성 순서 |
| `LOG --sort-by=author` | 소문자로 비교한 작성자 이름 오름차순 | 생성 순서 |

이번 시연은 작성자가 모두 `Alice Kim`이므로 작성자 정렬 결과도 `c000001`~`c000004` 순서다. 현재 CLI에는 작성자 변경 명령이 없으며, `INIT`을 다시 입력해도 작성자를 바꾸거나 저장소를 초기화하지 않는다. 여러 작성자에 대한 정렬은 기존 테스트에서 별도의 커밋 데이터를 만들어 확인한다.

### 동작과 구현 이유

기본 `LOG`는 부모 관계를 지키는 위상 정렬이고, 정렬 옵션은 선택한 필드 값을 비교하는 정렬이다. 날짜·작성자 정렬에는 부모 우선이라는 별도의 조건을 적용하지 않는다.

정렬은 표준 API인 `sorted()`와 `list.sort()`를 사용하지 않고 병합 정렬을 직접 구현했다. 리스트를 절반으로 나누고, 각 부분을 재귀적으로 정렬한 뒤 두 리스트의 앞쪽 원소를 비교하면서 합친다. 비교 기준을 함수로 전달하므로 같은 알고리즘으로 날짜와 작성자를 모두 정렬할 수 있다.

병합 정렬은 약 `log V`번 나누고 각 단계에서 전체 원소 `V`개를 처리하므로 평균과 최악 시간복잡도가 모두 `O(V log V)`다. 입력 상태와 관계없이 이 비용을 유지하며, 병합용 리스트에 추가 공간 `O(V)`가 필요하다.

안정 정렬은 비교 키가 같은 원소들의 기존 상대 순서를 유지하는 정렬이다. 병합할 때 키가 같으면 왼쪽 원소를 먼저 선택하므로 안정성이 유지된다. 실제 로그에서는 비교 키에 `sequence`도 포함하여 날짜나 작성자가 같으면 생성 순서로 출력되도록 명시했다.

## 7. 오류 처리와 종료

```text
SWITCH missing
PATH c000003 c999999
LOG --sort-by=message
quit
```

### 확인할 내용

앞의 세 명령은 순서대로 다음 오류를 출력하며 프로그램은 계속 실행된다.

```text
Unknown branch: missing
Unknown commit: c999999
Invalid args
```

`quit`은 프로그램을 종료한다. `exit`으로도 종료할 수 있다.

### 동작과 구현 이유

브랜치와 커밋이 존재하는지 확인한 뒤 기능을 실행하여 잘못된 참조를 막는다. 지원하지 않는 정렬 옵션이나 인자 개수가 잘못된 명령에는 `Invalid args`를 반환한다. 초기화 전 기능을 호출하면 `Repository not initialized.`를 출력하고, 이미 초기화한 상태에서 `INIT`을 다시 호출하면 `Repository already initialized.`를 출력해 기존 데이터를 유지한다.

## 8. 자료구조와 복잡도 참고

### 자료구조: 개념과 선택 이유

| 자료구조 | 간단한 개념 | 사용한 이유 |
| --- | --- | --- |
| 그래프·DAG | 노드와 연결로 구성되며, DAG는 방향이 있고 순환이 없는 그래프다. | 커밋 분기와 부모 관계를 표현하고 탐색하기 위해 사용했다. |
| 딕셔너리 | 키로 값을 찾는 해시맵이다. | hash 조회, 브랜치별 HEAD 관리, 역색인 조회를 빠르게 하기 위해 사용했다. |
| 리스트·튜플 | 리스트는 변경 가능한 순서 자료형이며, 튜플은 변경할 수 없는 순서 자료형이다. | 늘어나는 자식·검색 목록은 리스트로, 생성 후 고정되는 부모 목록은 튜플로 저장했다. |
| 큐 | 먼저 넣은 항목을 먼저 꺼내는 FIFO 구조다. | BFS에서 가까운 커밋부터 처리하기 위해 `deque`를 사용했다. |
| 스택 | 마지막에 넣은 항목을 먼저 꺼내는 LIFO 구조다. | 부모를 따라 깊게 탐색하며 조상을 수집하기 위해 리스트를 사용했다. |
| 집합 | 중복 없이 원소를 관리하는 구조다. | 중복 방문·토큰 등록을 막고 여러 키워드의 교집합을 구하기 위해 사용했다. |
| 역색인 | 검색어에서 해당 항목 목록을 찾는 구조다. | 커밋 메시지 전체를 다시 검사하지 않고 검색 후보를 얻기 위해 사용했다. |

### 현재 구현의 시간복잡도

`V`는 전체 커밋 수, `E`는 부모 연결 수, `K`는 검색 결과 수다. `A`는 조상 수, `P`는 조회한 토큰별 hash 목록 길이의 합이다. 딕셔너리·집합 연산은 평균 `O(1)`로 보며 문자열 길이에 따른 처리 비용은 생략한다.

| 기능 | 시간복잡도 | 구현에서 확인할 점 |
| --- | --- | --- |
| hash 조회 | 평균 `O(1)` | 커밋 딕셔너리에서 직접 조회한다. |
| 기본 `LOG` | 최악 `O(V² + E)` | 준비 목록에서 가장 빠른 생성 순서를 매번 선형 탐색하고, 리스트 중간 원소를 제거한다. |
| `PATH` | `O(V + E)` | BFS 거리 계산과 경로 복원 비용이다. |
| 조상 수집 | `O(V + E)` | 스택으로 탐색하고 집합으로 중복 처리를 막는다. |
| 조상 출력용 위상 정렬 | 최악 `O(A² + E)` | 조상만 선택하지만 자식 목록에서 조상에 포함되지 않은 연결도 확인한다. |
| 병합 정렬 | 평균·최악 `O(V log V)` | 안정 정렬이며 추가 공간은 `O(V)`다. |
| 단일 키워드 검색 | 평균 `O(V + K)` | 역색인 후보 조회 후 전체 커밋을 순회한다. |
| 여러 키워드 검색 | 평균 `O(V + P)` | 토큰별 목록의 교집합을 구한 뒤 전체 커밋을 순회한다. |
| 작성자 검색 | 평균 `O(K)` | 해당 작성자의 hash 목록으로 결과를 만든다. |

일반적인 Kahn 알고리즘은 `O(V + E)`지만, 현재 구현은 생성 순서 선택을 위해 준비 목록을 매번 검사하므로 최악 `O(V² + E)`다. 조상 탐색도 수집 자체와 출력용 위상 정렬을 나누어 설명해야 한다.

### 시연 뒤 설명할 수 있어야 하는 핵심

- 브랜치는 커밋의 복사본이 아니라 특정 커밋을 가리키는 참조이며, 새 커밋은 현재 브랜치만 갱신한다.
- 커밋 그래프가 DAG인 이유와 기본 로그가 부모를 먼저 출력하는 방법을 설명할 수 있다.
- PATH는 무방향 BFS로 최단거리를 찾고, ANCESTORS는 부모 방향의 스택 탐색으로 모든 조상을 찾는다.
- 역색인의 후보 조회와 현재 구현의 전체 결과 정리 비용을 구분할 수 있다.
- 병합 정렬을 선택한 이유, 평균·최악 시간복잡도, 안정 정렬의 의미를 설명할 수 있다.
