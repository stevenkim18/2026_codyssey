# 03. 검색과 정렬: 역색인과 병합 정렬

## 이번 문서에서 배울 것

앞에서는 커밋 그래프와 그래프 탐색 알고리즘을 공부했다. 이번에는 원하는 커밋을 빠르게 찾는 방법과 커밋 목록을 원하는 기준으로 정렬하는 방법을 살펴본다.

- 전체 커밋 순회와 역색인의 차이
- 키워드·작성자 역색인의 저장 구조
- 여러 키워드의 posting list를 교집합하는 방법
- 병합 정렬의 분할과 병합 과정
- 안정 정렬의 의미
- 날짜·작성자 정렬 기준과 시간복잡도

## 1. 사용할 명령어

첫 번째 문서에서 만든 커밋을 그대로 사용한다.

```text
c000001: Initial commit
c000002: Add login feature
c000003: Add payment feature
```

검색 명령은 다음과 같다.

```text
SEARCH login
SEARCH "add login"
SEARCH "--author=Alice Kim"
```

정렬 명령은 다음과 같다.

```text
LOG --sort-by=date
LOG --sort-by=author
```

## 2. 전체 순회 검색의 문제

가장 단순한 검색 방법은 모든 커밋을 하나씩 확인하는 것이다.

```python
for commit in commits:
    if keyword in commit.message:
        # 검색 결과에 추가
```

커밋이 `V`개라면 검색할 때마다 최대 `V`개의 메시지를 확인해야 한다. 커밋 수가 늘어날수록 같은 검사를 반복하게 된다.

Mini Git은 커밋을 생성할 때 검색용 정보를 미리 정리한 **역색인**을 함께 만든다.

## 3. 역색인이란 무엇인가

일반적인 커밋 저장소는 commit hash를 이용해 커밋을 찾는다.

```text
commit hash → Commit
```

역색인은 이 관계를 검색어 중심으로 뒤집은 구조다.

```text
검색어 → 검색어가 들어 있는 커밋 hash 목록
```

책의 맨 뒤에 있는 찾아보기를 생각하면 쉽다. 책 전체를 처음부터 읽지 않고도 단어와 관련된 페이지 번호를 바로 확인할 수 있다. 역색인도 검색어에 연결된 커밋 hash 목록을 바로 가져온다.

검색어에 연결된 결과 목록을 **posting list**라고 한다.

## 4. 키워드 역색인

### 4.1 메시지를 토큰으로 나누기

커밋 메시지는 공백을 기준으로 나누고 각 단어를 소문자로 바꾼다.

```text
"Add login feature"
→ ["Add", "login", "feature"]
→ ["add", "login", "feature"]
```

이렇게 검색의 단위로 나눈 단어를 토큰이라고 한다. 소문자로 정규화하므로 `login`, `LOGIN`, `Login`은 같은 토큰으로 처리한다.

현재 구현은 공백만 기준으로 나누며 문장부호를 제거하지 않는다.

```text
"Fix login"
→ ["fix", "login"]

"Fix login,"
→ ["fix", "login,"]
```

따라서 `login`과 `login,`은 서로 다른 토큰이다. 부분 문자열 검색도 아니므로 `log`로 `login`을 찾을 수 없다.

### 4.2 인덱스의 모습

예제의 세 커밋을 인덱싱하면 일부 항목은 다음과 같다.

```text
initial → [c000001]
commit  → [c000001]
add     → [c000002, c000003]
login   → [c000002]
payment → [c000003]
feature → [c000002, c000003]
```

코드에서는 딕셔너리로 저장한다.

```python
keyword_index = {
    "add": ["c000002", "c000003"],
    "login": ["c000002"],
    "payment": ["c000003"],
    "feature": ["c000002", "c000003"],
}
```

한 메시지에 같은 단어가 여러 번 들어 있어도 해당 커밋 hash는 posting list에 한 번만 추가한다. 커밋을 인덱싱할 때 `seen` 집합으로 이미 처리한 토큰인지 확인한다.

### 4.3 단일 키워드 검색

```text
mini-git> SEARCH login
Found 1 commit(s):

- c000002: Add login feature
```

`login`의 posting list인 `[c000002]`에서 검색 후보를 얻는다. 모든 커밋 메시지를 다시 분리하고 비교할 필요가 없다.

### 4.4 여러 키워드 검색

```text
mini-git> SEARCH "add login"
Found 1 commit(s):

- c000002: Add login feature
```

여러 키워드가 주어지면 각 posting list의 교집합을 구한다.

```text
add   → {c000002, c000003}
login → {c000002}

교집합 → {c000002}
```

따라서 `SEARCH "add login"`은 두 단어 중 하나만 들어 있는 커밋이 아니라 두 단어를 모두 포함하는 커밋을 반환한다. 단어의 순서나 연속 여부는 확인하지 않는다.

## 5. 작성자 역색인

작성자도 소문자로 정규화하여 별도의 역색인에 저장한다.

```python
author_index = {
    "alice kim": ["c000001", "c000002", "c000003"],
}
```

```text
mini-git> SEARCH "--author=Alice Kim"
Found 3 commit(s):

- c000001: Initial commit
- c000002: Add login feature
- c000003: Add payment feature
```

작성자 이름 전체를 소문자로 바꿔 조회하므로 대소문자를 구분하지 않는다. 부분 이름이 아닌 전체 작성자 이름이 일치해야 한다.

현재 CLI에서는 `INIT`할 때 작성자를 한 번 설정하고 실행 중에 바꾸지 않는다. 따라서 일반적인 한 세션의 커밋은 모두 같은 작성자를 가진다. 여러 작성자가 있을 때의 정렬 동작은 테스트에서 별도의 `Commit` 데이터를 만들어 확인한다.

## 6. 인덱스는 언제 갱신하는가

역색인은 검색할 때 만드는 것이 아니라 새 커밋을 생성할 때 함께 갱신한다.

```text
COMMIT 실행
→ 새 Commit 생성
→ commits에 저장
→ 브랜치와 그래프 연결 갱신
→ author_index 갱신
→ keyword_index 갱신
```

메시지의 토큰 수를 `T`라고 하면, 한 커밋의 인덱스를 갱신하는 작업은 평균 `O(T)`에 동작한다. 검색 전에 필요한 정보를 미리 만들어 두어 이후 검색에서 메시지 분석을 반복하지 않는 방식이다.

역색인은 검색 속도를 얻는 대신 posting list를 저장할 추가 메모리와 커밋 생성 시의 인덱싱 비용을 사용한다.

## 7. 검색 시간복잡도

작성자 검색은 작성자 딕셔너리에서 posting list를 바로 가져온다. 결과 커밋이 `K`개라면 목록 복사, 커밋 조회, 출력에 평균 `O(K)`가 걸린다.

키워드 검색은 다음 두 단계를 수행한다.

1. 각 키워드의 posting list를 집합으로 바꾸고 교집합한다.
2. 검색 결과를 생성 순서로 반환하기 위해 전체 `commits` 딕셔너리를 한 번 순회한다.

전체 커밋 수를 `V`, 각 posting list 길이의 합을 `P`라고 하면 현재 키워드 검색 구현의 시간복잡도는 `O(P + V)`다.

역색인을 사용해 검색 후보를 빠르게 줄이지만, 현재 구현은 결과 순서를 정리하는 마지막 단계에서 전체 커밋을 확인한다. 따라서 현재 키워드 검색을 결과 수에만 비례하는 `O(K)`라고 설명해서는 안 된다.

## 8. 정렬 옵션과 기본 LOG의 차이

기본 `LOG`는 그래프의 부모·자식 관계를 지키는 위상 정렬을 사용한다.

```text
LOG
→ 부모가 자식보다 먼저 출력
```

정렬 옵션을 사용하면 선택한 필드의 값을 기준으로 모든 커밋을 정렬한다.

```text
LOG --sort-by=date
→ timestamp 기준 오름차순

LOG --sort-by=author
→ author 기준 오름차순
```

날짜·작성자 정렬은 부모 우선 순서를 별도로 보장하지 않는다. 기본 `LOG`의 위상 정렬과 목적이 다른 기능이다.

## 9. 병합 정렬을 사용하는 이유

과제에서는 Python의 표준 정렬 API를 사용할 수 없다.

```python
sorted()     # 사용 금지
list.sort()  # 사용 금지
```

따라서 Mini Git은 날짜와 작성자 정렬을 위해 병합 정렬을 직접 구현한다.

병합 정렬은 목록을 더 이상 나눌 수 없을 때까지 절반으로 나눈 뒤, 정렬된 작은 목록들을 하나로 합치는 알고리즘이다.

## 10. 병합 정렬의 동작

다음 목록을 오름차순으로 정렬한다고 가정한다.

```text
[4, 2, 3, 1]
```

### 10.1 분할

목록을 절반씩 나눈다.

```text
[4, 2, 3, 1]
→ [4, 2] [3, 1]
→ [4] [2] [3] [1]
```

원소가 하나인 목록은 이미 정렬된 상태다.

### 10.2 병합

두 정렬된 목록의 앞쪽 원소를 비교하여 더 작은 값을 결과에 넣는다.

```text
[4] + [2] → [2, 4]
[3] + [1] → [1, 3]

[2, 4] + [1, 3]
→ [1, 2, 3, 4]
```

분할할 때 약 `log V`개의 단계가 생기고 각 단계의 병합에서 전체 `V`개 원소를 처리한다.

- 평균 시간복잡도: `O(V log V)`
- 최악 시간복잡도: `O(V log V)`
- 추가 공간복잡도: `O(V)`

입력 목록이 이미 정렬되어 있거나 역순이어도 최악 시간복잡도가 `O(V log V)`로 유지된다.

## 11. 안정 정렬

안정 정렬은 정렬 기준이 같은 원소들의 기존 상대 순서를 유지하는 정렬이다.

예를 들어 작성자가 같은 두 커밋이 다음 순서로 들어 있다고 가정한다.

```text
c000001: Alice
c000003: Alice
```

작성자 기준이 같으므로 안정 정렬 후에도 `c000001`, `c000003`의 상대 순서가 유지된다.

현재 병합 구현은 두 원소의 키가 같을 때 왼쪽 목록의 원소를 먼저 선택한다.

```python
if key(left[left_index]) <= key(right[right_index]):
    result.append(left[left_index])
```

목록을 나누기 전 왼쪽에 있던 원소가 먼저 들어가므로 병합 정렬의 안정성이 유지된다.

## 12. 날짜와 작성자 정렬 기준

같은 병합 정렬 함수에 서로 다른 `key` 함수를 전달하여 정렬 기준을 바꾼다.

### 12.1 날짜 정렬

```python
key=lambda commit: (commit.timestamp, commit.sequence)
```

timestamp를 오름차순으로 비교하고, timestamp가 같으면 생성 순서인 `sequence`를 비교한다.

### 12.2 작성자 정렬

```python
key=lambda commit: (commit.author.lower(), commit.sequence)
```

작성자 이름을 소문자로 바꿔 오름차순으로 비교하고, 작성자가 같으면 `sequence`를 비교한다. 따라서 작성자 이름의 대소문자는 정렬 순서에 영향을 주지 않는다.

`sequence`는 주 정렬 기준이 같은 경우에도 출력 순서가 항상 일정하도록 만드는 동률 처리 기준이다. 병합 정렬 알고리즘 자체도 안정적이지만, 이 구현은 날짜와 작성자 정렬의 규칙을 `sequence`까지 포함해 명시한다.

## 13. 검색과 정렬 비교

| 기능 | 자료구조·알고리즘 | 목적 | 핵심 복잡도 |
| --- | --- | --- | --- |
| 키워드 검색 | 키워드 역색인과 posting list 교집합 | 메시지 토큰으로 커밋 찾기 | 현재 구현 `O(P + V)` |
| 작성자 검색 | 작성자 역색인 | 작성자 이름으로 커밋 찾기 | `O(K)` |
| 날짜 정렬 | 안정 병합 정렬 | timestamp 오름차순 로그 | `O(V log V)` |
| 작성자 정렬 | 안정 병합 정렬 | 작성자 이름 오름차순 로그 | `O(V log V)` |

여기서 `V`는 전체 커밋 수, `P`는 검색에 사용한 posting list 길이의 합, `K`는 검색 결과 수다.

## 15. 평가 전에 확인할 질문

- 역색인은 어떤 방향으로 데이터를 연결하는 자료구조인가?

- 여러 키워드 검색에서 posting list의 교집합을 사용하는 이유는 무엇인가?

- 현재 키워드 검색을 단순히 `O(K)`라고 설명할 수 없는 이유는 무엇인가?

- 기본 `LOG`와 `LOG --sort-by=date|author`는 어떤 차이가 있는가?

## 학습 문서 마무리

세 문서를 통해 Mini Git의 실행 방법, 커밋 그래프와 탐색, 역색인 검색과 병합 정렬을 살펴봤다. 이제 각 명령의 결과뿐 아니라 그 기능에 어떤 자료구조와 알고리즘을 사용했고 왜 선택했는지 설명할 수 있어야 한다.
