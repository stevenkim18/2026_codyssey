# 02. 커밋 그래프: DAG, LOG, PATH, ANCESTORS

## 이번 문서에서 배울 것

첫 번째 문서에서는 Mini Git을 실행하고 브랜치를 나눠 커밋을 만들었다. 이번에는 그 결과가 왜 그래프인지 살펴보고, 그래프를 사용하는 세 명령의 동작 원리를 공부한다.

- 커밋과 부모 관계를 그래프로 표현하는 방법
- 커밋 그래프가 DAG인 이유
- `LOG`가 부모를 먼저 출력하는 방법
- `PATH`가 두 커밋 사이의 최단 경로를 찾는 방법
- `ANCESTORS`가 모든 조상을 찾는 방법

## 1. 첫 번째 문서에서 만든 커밋 그래프

다음 명령을 실행했다고 가정한다.

```text
INIT "Alice Kim"
COMMIT "Initial commit"
BRANCH feature
SWITCH feature
COMMIT "Add login feature"
SWITCH main
COMMIT "Add payment feature"
```

결과는 다음과 같다.

```text
              ┌──→ c000002  [feature]
c000001 ──────┤
              └──→ c000003  [main]
```

그래프의 용어로 바꾸면 다음과 같다.

| 그래프 용어 | Mini Git에서 의미하는 것 |
| --- | --- |
| 노드(vertex) | 커밋 하나 |
| 간선(edge) | 부모 커밋과 자식 커밋의 연결 |
| 경로(path) | 간선을 따라 이동한 커밋의 순서 |
| 조상(ancestor) | 부모 방향으로 이동해 도달할 수 있는 커밋 |

커밋이 한 줄로만 이어진다면 연결 리스트처럼 보일 수 있다. 하지만 하나의 커밋에서 여러 브랜치가 갈라질 수 있고, merge commit은 부모를 여러 개 가질 수도 있다. 따라서 커밋 관계는 리스트보다 그래프로 표현하는 것이 적합하다.

현재 Mini Git은 merge 명령을 구현하지 않았지만, `parents`를 튜플로 정의하여 커밋이 여러 부모를 가질 수 있는 구조로 만들었다.

## 2. 커밋 그래프를 저장하는 방법

### 2.1 커밋 하나의 정보

커밋 하나는 `Commit` 데이터 클래스로 표현한다.

```python
@dataclass(frozen=True)
class Commit:
    hash: str
    message: str
    author: str
    timestamp: datetime
    parents: Tuple[str, ...]
    sequence: int
```

| 필드 | 역할 |
| --- | --- |
| `hash` | 커밋을 구분하는 세션 내 고유 식별자 |
| `message` | 커밋 설명이며 키워드 검색 대상 |
| `author` | 작성자 검색과 정렬에 사용하는 이름 |
| `timestamp` | 생성 시각이며 날짜 정렬 기준 |
| `parents` | 직접 연결된 부모 커밋의 hash 목록 |
| `sequence` | 생성 순서이며 hash 생성과 동률 처리에 사용 |

`frozen=True`이므로 커밋을 생성한 뒤 필드를 변경할 수 없다. 기존 커밋을 수정하지 않고 새 커밋을 추가한다는 커밋 모델에도 잘 맞는다.

`c000001`과 같은 값은 실제 Git의 암호학적 hash가 아니다. 이 구현에서는 증가하는 `sequence`로 만든, 실행 중 중복되지 않는 학습용 식별자다.

### 2.2 hash로 커밋 찾기

모든 커밋은 다음 형태의 딕셔너리에 저장한다.

```python
commits = {
    "c000001": Commit(...),
    "c000002": Commit(...),
    "c000003": Commit(...),
}
```

리스트에서 hash가 같은 커밋을 처음부터 찾으면 커밋 수에 비례해 시간이 걸린다. 딕셔너리를 사용하면 hash를 키로 커밋을 평균 `O(1)`에 조회할 수 있다.

### 2.3 부모와 자식 연결

각 커밋의 `parents`에는 자식에서 부모로 이동할 때 필요한 hash가 들어 있다.

```python
c000001.parents == ()
c000002.parents == ("c000001",)
c000003.parents == ("c000001",)
```

반대 방향으로 빠르게 이동하기 위해 `children` 딕셔너리도 함께 관리한다.

```python
children = {
    "c000001": ["c000002", "c000003"],
    "c000002": [],
    "c000003": [],
}
```

`parents`만 있다면 특정 커밋의 자식을 찾을 때 모든 커밋을 검사해야 한다. `children`을 함께 저장하면 부모에서 자식으로 바로 이동할 수 있다. `LOG`와 `PATH`가 이 정보를 사용한다.

### 2.4 브랜치와 현재 HEAD

브랜치는 각 브랜치의 마지막 커밋 hash를 저장한다.

```python
branches = {
    "main": "c000003",
    "feature": "c000002",
}
```

현재 구현은 별도의 HEAD 객체를 만들지 않는다. 대신 현재 브랜치 이름과 브랜치 딕셔너리를 조합한다.

```python
current_branch = "main"
head_hash = branches[current_branch]  # "c000003"
```

`SWITCH feature`는 `current_branch`만 `feature`로 바꾼다. `COMMIT`은 현재 HEAD를 새 커밋의 부모로 기록한 뒤, 현재 브랜치가 새 커밋을 가리키도록 이동시킨다.

## 3. 커밋 그래프가 DAG인 이유

DAG는 **Directed Acyclic Graph**, 즉 방향성 비순환 그래프다.

### Directed: 방향이 있다

부모와 자식 관계에는 방향이 있다. 이 문서에서는 로그의 선행 관계를 설명하기 위해 부모에서 자식 방향으로 표시한다.

```text
부모 커밋 ──→ 자식 커밋
```

코드에서는 양방향 탐색이 가능하도록 커밋의 `parents`와 저장소의 `children`을 모두 관리한다. 연결 정보를 양쪽에 저장하더라도 부모와 자식이라는 관계 자체의 방향이 없어지는 것은 아니다.

### Acyclic: 순환이 없다

새 커밋을 만들 때 부모는 이미 존재하는 현재 HEAD다. 새 커밋은 항상 과거 커밋 뒤에 추가되고, 기존 커밋의 부모는 바꾸지 않는다.

```text
c000001 → c000002 → c000003
```

따라서 부모를 계속 따라가도 자기 자신으로 돌아올 수 없다. 다음과 같은 순환은 만들어지지 않는다.

```text
c000001 → c000002 → c000003
    ↑                   │
    └───────────────────┘   불가능
```

### Graph: 분기와 여러 연결을 표현한다

하나의 부모에서 여러 자식이 만들어질 수 있다. merge를 구현하면 하나의 자식이 여러 부모를 가질 수도 있다. 이런 관계를 함께 표현하므로 커밋 이력은 그래프가 된다.

## 4. LOG: 부모를 먼저 출력하는 위상 정렬

위상 정렬은 **서로 의존 관계가 있는 항목을 선행 조건이 먼저 나오도록 나열하는 방법**이다. 숫자의 크기를 비교하는 일반 정렬과 달리, 어떤 항목이 다른 항목보다 먼저 처리되어야 한다는 관계를 기준으로 순서를 정한다.

예를 들어 `기초 학습 → 심화 학습`이라는 관계가 있다면 기초 학습을 먼저 배치해야 한다. 커밋 그래프에서는 부모 커밋이 선행 조건이고 자식 커밋이 그다음 항목이다.

```text
부모 커밋 → 자식 커밋
```

따라서 위상 정렬을 사용하면 모든 부모가 자식보다 먼저 나오도록 커밋을 나열할 수 있다. 선행 관계만 지키면 가능한 결과는 여러 개일 수 있다.

```text
가능:   c000001 → c000002 → c000003
가능:   c000001 → c000003 → c000002
불가능: c000002 → c000001 → c000003
```

마지막 순서는 자식인 `c000002`가 부모인 `c000001`보다 먼저 나왔으므로 위상 정렬 결과가 아니다. 위상 정렬은 방향을 따라 다시 자기 자신으로 돌아오는 사이클이 없는 DAG에서 모든 노드를 나열할 수 있다.

```text
mini-git> LOG
```

이 과제의 기본 `LOG`는 최신 커밋부터 보여 주는 대신 위상 정렬 결과를 출력한다.

```text
c000001
c000002
c000003
```

### 4.1 진입 차수

부모에서 자식 방향으로 보았을 때, 한 커밋으로 들어오는 간선 수를 진입 차수라고 한다. 커밋 그래프에서는 선택된 그래프 안에 존재하는 부모 수와 같다.

| 커밋 | 부모 | 진입 차수 |
| --- | --- | ---: |
| `c000001` | 없음 | 0 |
| `c000002` | `c000001` | 1 |
| `c000003` | `c000001` | 1 |

진입 차수가 0이면 먼저 출력해야 할 부모가 더 이상 없다는 뜻이다.

### 4.2 Kahn 방식의 진행 과정

구현은 다음 순서로 동작한다.

1. 각 커밋의 진입 차수를 계산한다.
2. 진입 차수가 0인 커밋을 준비 목록에 넣는다.
3. 준비 목록에서 커밋 하나를 꺼내 출력한다.
4. 그 커밋의 자식들의 진입 차수를 1씩 줄인다.
5. 진입 차수가 0이 된 자식을 준비 목록에 넣는다.
6. 모든 커밋을 출력할 때까지 반복한다.

예제에서는 다음처럼 진행된다.

```text
준비 목록 [c000001]
→ c000001 출력
→ c000002와 c000003의 진입 차수가 0이 됨
→ 준비 목록 [c000002, c000003]
→ c000002 출력
→ c000003 출력
```

동시에 출력할 수 있는 커밋이 여러 개면 생성 순서가 가장 빠른 커밋을 선택한다. 위상 정렬 결과는 하나가 아닐 수 있으므로, 이 규칙을 사용해 항상 같은 결과가 나오게 한다.

모든 커밋을 처리하기 전에 준비 목록이 비어 버리면 그래프에 사이클이 있다는 뜻이다. 구현은 이 경우 `ValueError`를 발생시킨다.

### 4.3 시간복잡도

일반적인 Kahn 알고리즘은 큐를 사용하면 `O(V + E)`에 동작한다. 현재 구현은 준비 목록에서 생성 순서가 가장 빠른 커밋을 찾기 위해 매번 목록을 순회한다.

- 현재 구현의 최악 시간복잡도: `O(V² + E)`
- 그래프를 저장하는 공간: `O(V + E)`
- 위상 정렬이 추가로 사용하는 공간: `O(V)`

여기서 `V`는 커밋 수, `E`는 부모와 자식 사이의 간선 수다.

## 5. PATH: BFS로 최단 경로 찾기

```text
mini-git> PATH c000002 c000003
Path: c000002 -> c000001 -> c000003
```

### 5.1 PATH에서는 간선을 무방향으로 본다

`c000002`에서 부모 방향으로 이동하면 `c000001`에 도착한다. 이후 다른 브랜치의 자식인 `c000003`으로 이동해야 한다.

```text
c000002 → c000001 → c000003
         부모 방향    자식 방향
```

부모 방향으로만 이동하면 다른 갈래의 자식으로 갈 수 없다. 따라서 `PATH`에서는 부모 연결을 무방향 간선으로 간주하고, 현재 커밋의 부모와 자식을 모두 이웃으로 사용한다.

### 5.2 BFS를 사용하는 이유

모든 간선의 이동 비용은 1이다. BFS는 시작점과 가까운 노드부터 차례대로 방문하므로 가중치가 없는 그래프의 최단 경로를 찾을 수 있다.

BFS는 먼저 발견한 커밋을 먼저 처리하기 위해 FIFO 큐를 사용한다. 현재 구현에서는 큐의 앞에서 빠르게 원소를 꺼낼 수 있는 `collections.deque`를 사용한다.

DFS는 한 갈래를 끝까지 먼저 탐색한다. 도착점을 처음 찾았더라도 그 경로가 가장 짧다는 보장이 없으므로 이 기능에는 적합하지 않다.

구현에서는 도착점에서 BFS를 실행해 각 커밋에서 도착점까지 남은 거리를 구한다.

| 커밋 | `c000003`까지 거리 |
| --- | ---: |
| `c000003` | 0 |
| `c000001` | 1 |
| `c000002` | 2 |

출발점 `c000002`에서 시작하여 남은 거리가 1씩 줄어드는 이웃을 선택하면 최단 경로를 만들 수 있다.

### 5.3 최단 경로가 여러 개라면

과제에서는 최단 경로가 여러 개일 때 다음 문자열이 사전순으로 가장 작은 경로를 선택해야 한다.

```text
hash1->hash2->hash3
```

현재 커밋에서 거리가 1 줄어드는 이웃이 여러 개라면 hash가 가장 작은 이웃을 선택한다. 이 과정을 목적지까지 반복하면 최단거리 조건을 지키면서 사전순으로 가장 작은 경로를 만들 수 있다.

### 5.4 시간복잡도

- 시간복잡도: `O(V + E)`
- 공간복잡도: `O(V)`

BFS는 각 커밋과 간선을 필요한 범위에서 한 번씩 확인한다. 두 커밋이 연결되지 않았다면 `No path`를 출력한다.

## 6. ANCESTORS: 부모 방향으로 모든 조상 찾기

```text
mini-git> ANCESTORS c000002
commit c000001 (Alice Kim, <실행 시각>)
Initial commit
```

조상은 대상 커밋에서 부모 방향으로 이동해 도달할 수 있는 모든 커밋이다.

```text
c000001 → c000002
  조상        대상
```

### 6.1 스택을 이용한 탐색

구현은 대상 커밋의 부모들을 스택에 넣고 하나씩 꺼내며 다시 그 부모들을 추가한다. 리스트의 마지막 원소를 꺼내므로 DFS와 같은 방식으로 깊은 부모를 먼저 탐색한다.

```text
대상 커밋의 부모를 스택에 추가
→ 부모 하나를 꺼냄
→ 방문 집합에 기록
→ 그 커밋의 부모를 스택에 추가
→ 스택이 빌 때까지 반복
```

최단거리를 계산할 필요 없이 도달 가능한 모든 조상을 찾는 것이 목적이므로 DFS 형태의 탐색으로 충분하다.

### 6.2 방문 집합이 필요한 이유

여러 경로가 같은 조상으로 이어질 수 있다. 이미 방문한 hash를 집합에 기록하면 같은 조상을 반복해서 처리하거나 출력하는 것을 막을 수 있다.

시작한 커밋은 조상에 포함하지 않는다. 루트 커밋처럼 부모가 없는 커밋을 조회하면 `No ancestors.`를 출력한다.

### 6.3 탐색 순서와 출력 순서는 다르다

스택으로 조상을 찾은 순서가 부모 우선 순서라는 보장은 없다. 구현은 먼저 모든 조상을 집합으로 수집한 뒤, 조상들로 이루어진 부분 그래프에 위상 정렬을 적용한다.

따라서 화면에는 상위 조상이 그 자손보다 먼저 출력된다. 이는 timestamp의 크기가 아니라 부모와 자식의 관계를 기준으로 정한 순서다.

### 6.4 시간복잡도

조상의 수를 `A`, 조상 부분 그래프의 간선 수를 `Eₐ`라고 하면, 조상 수집은 `O(A + Eₐ)`에 동작한다. 이후 출력 순서를 정하는 현재 위상 정렬 구현까지 포함하면 최악 `O(A² + Eₐ)`다.

## 7. 세 명령 비교

| 명령 | 사용하는 방향 | 알고리즘 | 목적 |
| --- | --- | --- | --- |
| `LOG` | 부모 → 자식 | Kahn 방식 위상 정렬 | 부모가 자식보다 먼저 나오도록 전체 커밋 출력 |
| `PATH` | 부모 ↔ 자식 | BFS | 두 커밋 사이의 최단 경로 탐색 |
| `ANCESTORS` | 자식 → 부모 | 스택을 이용한 DFS 형태 탐색 | 도달 가능한 모든 조상 수집 |

세 기능은 같은 커밋 그래프를 사용하지만, 목적에 따라 이동 방향과 알고리즘이 다르다.

## 9. 평가 전에 확인할 질문

- 커밋 이력을 리스트가 아니라 그래프로 표현하는 이유는 무엇인가?
- 커밋 그래프가 방향성을 가지면서도 순환하지 않는 이유는 무엇인가?
- `parents`가 있는데도 `children`을 별도로 저장한 이유는 무엇인가?
- `LOG`에 날짜 정렬이 아닌 위상 정렬이 필요한 이유는 무엇인가?
- `PATH`가 부모와 자식을 모두 이웃으로 사용하는 이유는 무엇인가?
- 최단 경로 탐색에 DFS가 아닌 BFS를 사용하는 이유는 무엇인가?
- `ANCESTORS`에서 방문 집합이 없다면 어떤 문제가 생길 수 있는가?
