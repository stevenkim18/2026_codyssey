## 1. 커밋 그래프가 DAG여야 하는 이유

### 평가 질문

> 커밋 그래프가 왜 DAG여야 하는지, 사이클이 생기면 어떤 문제가 발생하는지 설명할 수 있는가?

### 핵심 답변

> 커밋은 이미 존재하는 과거 커밋을 부모로 삼아 새 기록으로 추가되므로 부모-자식의 방향이 있고, 부모를 계속 따라가 자기 자신으로 돌아오면 안 됩니다. 그래서 커밋 이력은 방향성 비순환 그래프인 DAG여야 합니다. 사이클이 생기면 어느 커밋이 먼저인지 결정할 수 없어 부모 우선 `LOG`의 위상 정렬이 완성되지 않고, 조상이라는 시간적 의미도 깨집니다.

### DAG의 세 단어를 나누어 설명하기

#### Directed: 방향이 있다

커밋 관계에는 부모와 자식이라는 선후 관계가 있다.

```text
부모 커밋 ──→ 자식 커밋
```

코드의 `Commit.parents`는 자식에서 부모로 이동할 hash를 저장하고, `children`은 부모에서 자식으로 이동할 hash를 저장한다. 탐색을 위해 연결을 양쪽에 보관하더라도 **부모가 먼저 존재하고 그 뒤에 자식이 생성된다**는 관계의 방향은 유지된다.

#### Acyclic: 순환이 없다

정상적인 커밋 이력은 다음처럼 과거에서 미래로 진행한다.

```text
c000001 → c000002 → c000003
```

아래처럼 미래 커밋을 따라가 다시 과거의 자기 자신으로 돌아오는 구조는 허용하면 안 된다.

```text
c000001 → c000002 → c000003
    ↑                   │
    └───────────────────┘
```

#### Graph: 분기와 여러 부모를 표현한다

브랜치가 갈라지면 한 부모가 여러 자식을 갖는다. 현재 CLI에는 merge 명령이 없지만 `parents`를 튜플로 설계했으므로 데이터 모델은 여러 부모도 표현할 수 있다. 단순한 한 줄 목록보다 그래프가 이런 관계를 자연스럽게 표현한다.

### 현재 구현이 사이클을 만들지 않는 방법

새 커밋은 현재 HEAD처럼 **이미 존재하는 커밋만** 부모로 사용한다. 생성된 `Commit`은 `frozen=True`라 부모를 나중에 바꿀 수 없고, 새 커밋의 hash는 생성 전에는 부모 후보로 존재하지 않는다.

```text
기존 HEAD를 읽음
→ 기존 HEAD를 새 Commit의 parents에 저장
→ 새 Commit을 저장
→ 현재 브랜치를 새 Commit으로 이동
```

항상 과거 노드에서 새 노드로만 관계가 추가되므로 새 노드가 다시 자기 조상이 되는 사이클을 만들 수 없다.

### 사이클이 생겼을 때의 문제

1. **부모 우선 순서를 정할 수 없다.** A의 부모가 B이고 B의 부모가 A라면 A와 B 중 무엇을 먼저 출력해도 조건을 어긴다.
2. **Kahn 위상 정렬이 완료되지 않는다.** 사이클의 노드들은 진입 차수가 0이 되지 않아 준비 목록에 들어가지 못한다. 현재 구현은 결과 수가 대상 노드 수보다 적으면 `ValueError`를 발생시킨다.
3. **조상의 의미가 깨진다.** A를 따라가 B에 도달하고 다시 A로 돌아온다면 A가 자기 자신의 조상이 되는 모순이 생긴다.
4. **단순한 재귀 탐색은 무한 반복할 수 있다.** 현재 조상 탐색과 BFS는 방문 집합을 사용하므로 무한 반복은 막지만, 종료할 수 있다는 것과 올바른 커밋 이력이라는 것은 별개다.

## 2. `LOG`에서 부모를 먼저 출력하는 방법

### 평가 질문

> `LOG`에서 “부모가 먼저” 조건을 만족시키기 위해 어떤 접근(예: 위상 정렬 성격의 출력)을 적용했는지 설명할 수 있는가?

### 핵심 답변

> 기본 `LOG`에는 Kahn 방식의 위상 정렬을 적용했습니다. 각 커밋의 선택된 부모 수를 진입 차수로 계산하고, 진입 차수가 0인 커밋만 출력합니다. 커밋을 출력할 때 자식들의 진입 차수를 줄이고 0이 된 자식을 다음 후보로 추가하므로 모든 부모가 출력된 뒤에만 자식이 나옵니다.

### 예제 그래프

```text
              ┌──→ c000002 ──→ c000004
c000001 ──────┤
              └──→ c000003
```

초기 진입 차수는 다음과 같다.

| 커밋 | 선택된 부모 수 | 초기 진입 차수 |
| --- | ---: | ---: |
| `c000001` | 0 | 0 |
| `c000002` | 1 | 1 |
| `c000003` | 1 | 1 |
| `c000004` | 1 | 1 |

### Kahn 방식의 진행 과정

```text
1. ready = [c000001]
2. c000001 출력
   → c000002, c000003의 진입 차수를 0으로 감소
3. ready = [c000002, c000003]
4. 생성 순서가 빠른 c000002 출력
   → c000004의 진입 차수를 0으로 감소
5. ready = [c000003, c000004]
6. c000003 출력
7. c000004 출력
```

결과는 `c000001, c000002, c000003, c000004`이며 다음 선행 조건을 모두 만족한다.

- `c000001`은 자식 `c000002`, `c000003`보다 먼저 나온다.
- `c000002`는 자식 `c000004`보다 먼저 나온다.

위상 정렬 결과는 하나가 아닐 수 있다. 동시에 출력 가능한 커밋이 여러 개라면 현재 구현은 `sequence`가 작은 커밋을 선택해 실행할 때마다 같은 결과를 만든다.

### 왜 일반적인 날짜 정렬로는 부족한가?

날짜는 부모-자식 의존 관계 자체가 아니다. 시스템 시간의 정밀도·보정·동률 등의 영향을 받을 수 있고, 여러 부모가 있는 경우 모든 부모가 먼저 나왔는지를 직접 표현하지 못한다. 위상 정렬은 timestamp가 아니라 실제 `parents` 관계를 기준으로 조건을 보장한다.

### 현재 구현의 시간복잡도

일반적인 Kahn 알고리즘은 큐를 사용하면 `O(V + E)`다. 그러나 현재 구현은 동시에 준비된 커밋 중 가장 이른 `sequence`를 선택하기 위해 매번 `ready` 목록을 선형 탐색하고, 목록 중간에서 원소를 제거한다.

- 진입 차수 계산과 자식 간선 처리: `O(V + E)`
- 준비 목록에서 매번 최소 sequence 선택: 최악 `O(V²)`
- **현재 구현의 최악 시간복잡도: `O(V² + E)`**
- 추가 공간복잡도: `O(V)`

평가에서는 “Kahn 알고리즘은 언제나 `O(V + E)`”라고만 말하지 않고, 현재 구현의 후보 선택 비용을 함께 설명하는 것이 정확하다. 우선순위 큐를 사용하면 생성 순서 선택을 `O(log V)`로 줄여 전체를 `O((V + E) log V)` 수준으로 개선할 수 있다.

## 3. `PATH`의 BFS와 무방향 간선

### 평가 질문

> `PATH`에서 최단 경로를 찾기 위해 어떤 알고리즘(예: BFS)을 선택했고, 간선을 무방향으로 정의한 이유를 설명할 수 있는가?

### 핵심 답변

> 모든 부모-자식 간선의 이동 비용이 1인 비가중 그래프이므로 BFS를 선택했습니다. PATH는 조상만 찾는 명령이 아니라 두 커밋 사이의 연결을 찾는 명령입니다. 한 브랜치의 커밋에서 공통 조상까지 부모 방향으로 간 뒤 다른 브랜치의 자식 방향으로 이동할 수 있어야 하므로 부모 연결을 무방향 간선으로 해석합니다.

### 왜 무방향이어야 하는가?

다음처럼 하나의 루트에서 feature와 main이 갈라졌다고 가정한다.

```text
              ┌──→ c000002  [feature]
c000001 ──────┤
              └──→ c000003  [main]
```

`PATH c000002 c000003`의 기대 결과는 다음과 같다.

```text
c000002 → c000001 → c000003
           ↑ 부모       ↓ 자식
```

부모 방향만 허용하면 `c000002`에서 `c000001`까지는 갈 수 있지만 형제 갈래의 `c000003`으로 내려갈 수 없다. 반대로 자식 방향만 허용해도 출발점에서 공통 조상으로 갈 수 없다. 그래서 현재 커밋의 부모와 자식을 모두 이웃으로 취급한다.

### 왜 BFS인가?

- 모든 간선의 비용이 1이다.
- BFS는 거리가 0인 노드, 1인 노드, 2인 노드 순으로 방문한다.
- 따라서 처음 계산된 거리가 최소 간선 수다.
- `deque.popleft()`를 사용해 먼저 들어온 노드를 먼저 처리한다.

DFS는 한 갈래를 끝까지 탐색하므로 목적지를 처음 발견한 경로가 최단이라는 보장이 없다. 가중치가 없으므로 다익스트라 알고리즘까지 사용할 필요도 없다.

### 현재 구현의 두 단계

구현은 출발점에서 바로 경로를 저장하는 대신 목적지에서 BFS를 수행한다.

```text
1. 목적지에서 모든 도달 가능한 커밋까지의 최단거리 계산
2. 출발점에서 목적지로 이동하며 거리가 정확히 1씩 줄어드는 이웃 선택
```

예를 들어 목적지가 `c000003`이면 거리 정보는 다음과 같다.

| 커밋 | 목적지까지 거리 |
| --- | ---: |
| `c000003` | 0 |
| `c000001` | 1 |
| `c000002` | 2 |

`c000002`에서 남은 거리가 1인 `c000001`, 그다음 남은 거리가 0인 `c000003`을 선택하면 최단 경로가 복원된다.

최단 경로가 여러 개라면 남은 거리가 1 줄어드는 후보 중 hash가 가장 작은 이웃을 고른다. 출발 hash는 같으므로 첫 번째로 달라지는 다음 hash가 작은 경로가 전체 경로 문자열도 사전순으로 가장 작다.

### 경로가 없을 때

목적지에서 BFS를 마쳤는데 `distance_to_end`에 출발점이 없으면 두 커밋은 연결되지 않은 것이다. 이때 알고리즘은 `None`을 반환하고 명령 계층이 `No path`를 출력한다.

### 시간·공간복잡도

- BFS 거리 계산: `O(V + E)`
- 경로 복원: 경로에 포함된 이웃들을 확인하며 전체적으로 `O(V + E)` 범위
- **전체 시간복잡도: `O(V + E)`**
- 거리 딕셔너리와 큐: `O(V)`

## 4. 병합 정렬의 복잡도와 안정성

### 평가 질문

> 정렬 알고리즘의 평균/최악 시간복잡도와 안정 정렬 여부를 설명할 수 있는가?

### 핵심 답변

> Python 표준 정렬 API를 사용할 수 없어서 안정 병합 정렬을 직접 구현했습니다. 목록을 절반씩 나누고 정렬된 두 목록을 병합합니다. 약 `log V`개의 단계마다 전체 `V`개 원소를 처리하므로 평균과 최악 시간복잡도는 모두 `O(V log V)`이고 추가 공간은 `O(V)`입니다. 병합 중 키가 같으면 왼쪽 원소를 먼저 선택하므로 안정 정렬입니다.

### 분할과 병합

```text
[4, 2, 3, 1]
→ [4, 2] [3, 1]
→ [4] [2] [3] [1]
→ [2, 4] [1, 3]
→ [1, 2, 3, 4]
```

매번 입력 크기가 절반으로 줄어 재귀 깊이는 약 `log V`다. 각 깊이의 병합 작업을 모두 합하면 `V`개 원소를 처리하므로 `V × log V`가 된다.

| 구분 | 복잡도 |
| --- | ---: |
| 평균 시간 | `O(V log V)` |
| 최악 시간 | `O(V log V)` |
| 현재 구현의 최선 시간 | `O(V log V)` |
| 추가 공간 | `O(V)` |

현재 구현은 입력이 이미 정렬되어 있어도 계속 분할하고 병합하므로 최선도 `O(V log V)`다.

### 안정 정렬이란?

정렬 기준이 같은 두 원소의 기존 상대 순서를 유지하는 정렬이다.

```text
정렬 전: c000001(Alice), c000003(Alice)
정렬 후: c000001(Alice), c000003(Alice)
```

병합 과정에서 다음 조건처럼 키가 같을 때도 왼쪽 원소를 먼저 결과에 넣는다.

```python
if key(left[left_index]) <= key(right[right_index]):
    result.append(left[left_index])
```

원래 목록에서 앞쪽에 있던 원소가 분할 후 왼쪽에 있으므로 동률일 때 왼쪽을 먼저 선택하면 상대 순서가 유지된다. `<`가 아니라 `<=`를 사용하는 것이 안정성의 핵심이다.

### 날짜·작성자 정렬에 적용하는 방법

병합 정렬 함수에 비교 기준을 함수로 전달한다.

```text
날짜 정렬   key = (timestamp, sequence)
작성자 정렬 key = (author.lower(), sequence)
```

- `LOG --sort-by=date`: 생성 시각 오름차순, 같으면 생성 순서
- `LOG --sort-by=author`: 대소문자를 무시한 작성자 오름차순, 같으면 생성 순서

실제 로그의 키에는 `sequence`가 동률 처리 기준으로 포함되어 결과를 결정적으로 만든다. 동시에 병합 정렬 자체도 키가 완전히 같은 데이터를 안정적으로 처리하며, 테스트에서는 `sequence`를 키에서 제외한 동일 timestamp·author 데이터를 사용해 안정성을 확인한다.

## 5. 역색인이 순회 검색보다 빠른 이유

### 평가 질문

> 역색인이 순회 검색보다 빠른 이유를 자료구조/시간복잡도 관점에서 설명할 수 있는가?

### 핵심 답변

> 순회 검색은 질의할 때마다 전체 커밋의 메시지를 읽고 토큰을 비교해야 합니다. 역색인은 커밋 생성 시 `검색어 -> 관련 commit hash 목록`을 딕셔너리에 미리 저장합니다. 검색할 때는 검색어로 posting list를 평균 `O(1)`에 찾아 실제 후보만 가져오므로, 메시지 분석을 매번 반복하지 않습니다. 그 대신 커밋 생성 시 인덱싱 시간과 posting list를 저장할 메모리를 사용합니다.

### 순회 검색과 역색인의 자료구조 차이

순회 검색은 커밋 중심으로 데이터를 본다.

```text
c000001 → "Initial commit"
c000002 → "Add login feature"
c000003 → "Add payment feature"
```

`login`을 찾으려면 각 메시지를 하나씩 확인해야 한다.

역색인은 검색어 중심의 딕셔너리를 미리 만든다.

```text
"login"   → [c000002]
"feature" → [c000002, c000003]
"alice"가 아니라 작성자 전체 "alice kim" → [c000001, c000002, c000003]
```

검색어를 키로 연결된 hash 목록을 바로 얻는다. 이 결과 목록을 posting list라고 한다.

### 커밋 생성 시 선행 작업

메시지 토큰 수가 `T`라면 한 커밋을 추가할 때 다음 작업을 평균 `O(T)`에 수행한다.

1. 메시지를 공백 기준으로 나눈다.
2. 각 토큰을 소문자로 정규화한다.
3. `keyword_index[token]`에 commit hash를 추가한다.
4. 정규화한 전체 작성자 이름을 `author_index`에 추가한다.

한 메시지에 같은 토큰이 반복되면 `seen` 집합으로 한 번만 등록한다.

### 검색 시간복잡도 비교

#### 전체 순회 검색

커밋이 `V`개라면 매 검색마다 모든 커밋 메시지를 검사한다. 메시지 처리 비용을 단순화하면 최소 `O(V)`이고, 실제로는 각 메시지의 문자열·토큰 비교 비용도 추가된다.

#### 작성자 역색인 검색

작성자 키를 딕셔너리에서 평균 `O(1)`에 찾고 결과 `K`개를 커밋으로 변환한다.

- 평균 시간복잡도: `O(K)`
- 결과가 적을수록 전체 `V`개를 확인하는 순회 검색보다 유리하다.

#### 현재 키워드 역색인 검색

각 토큰의 posting list를 집합으로 바꾸고 교집합하여 후보를 얻는다. posting list 길이 합이 `P`라면 후보 계산은 평균 `O(P)`다.

현재 구현은 결과를 커밋 생성 순서로 반환하기 위해 마지막에 `commits` 딕셔너리의 hash들을 한 번 확인한다.

- 후보 계산: `O(P)`
- 현재 결과 순서 정리: `O(V)`
- **현재 키워드 검색 전체: `O(P + V)`**

따라서 현재 구현을 무조건 `O(K)`라고 설명하면 정확하지 않다. 그래도 역색인이 모든 커밋 메시지를 다시 토큰화하고 비교하는 비용을 없애고, 실제 후보 집합을 빠르게 만든다는 장점은 유지된다. posting list가 생성 순서로 저장된다는 성질을 이용해 교집합 결과를 직접 순서대로 만들도록 개선하면 전체 커밋 순회를 없애 `O(P + K)`에 가깝게 만들 수 있다.

### 역색인의 비용과 적합한 상황

| 구분 | 전체 순회 | 역색인 |
| --- | --- | --- |
| 커밋 추가 | 단순함 | 토큰화·인덱스 갱신 비용 발생 |
| 검색 | 매번 전체 메시지 검사 | posting list에서 후보 조회 |
| 추가 메모리 | 거의 없음 | 토큰·작성자별 hash 목록 필요 |
| 반복 검색 | 같은 검사를 계속 반복 | 미리 계산한 인덱스를 재사용 |

검색이 거의 없고 쓰기만 많은 경우에는 인덱스 유지 비용이 상대적으로 클 수 있다. 하지만 많은 커밋을 대상으로 키워드·작성자 검색을 반복하는 Mini Git 요구에는 검색 시 반복 작업을 줄이는 역색인이 적합하다.

## 6. 자주 나오는 꼬리 질문

### `parents`와 `children`을 둘 다 저장하면 그래프가 무방향이 되는가?

> 아닙니다. 원래 관계는 부모와 자식이라는 방향을 유지합니다. 두 방향의 조회를 빠르게 하기 위해 인접 정보를 양쪽에 저장한 것입니다. `LOG`는 부모→자식 방향을 사용하고, `ANCESTORS`는 부모 방향만 사용하며, `PATH`만 요구사항에 따라 둘을 합쳐 무방향으로 해석합니다.

### 위상 정렬 결과는 항상 하나인가?

> 아닙니다. 서로 선후 관계가 없는 형제 커밋은 어느 쪽이 먼저 나와도 유효합니다. 현재 구현은 생성 순서가 빠른 커밋을 먼저 골라 결과를 결정적으로 만듭니다.

### BFS에서 방문 집합이 필요한 이유는 무엇인가?

> 부모와 자식을 모두 이웃으로 보면 같은 간선을 반대 방향으로 다시 돌아갈 수 있습니다. 거리 딕셔너리를 방문 기록으로 사용해 각 커밋을 한 번만 큐에 넣지 않으면 중복 탐색이 계속 발생합니다.

### 병합 정렬에서 키가 같을 때 오른쪽을 먼저 선택하면 어떻게 되는가?

> 정렬 결과의 값 순서는 맞아도 원래 앞에 있던 동일 키 원소가 뒤로 밀릴 수 있으므로 안정 정렬이 아니게 됩니다.

### 역색인은 언제 갱신하는가?

> 검색할 때가 아니라 새 커밋을 저장할 때 작성자와 키워드 인덱스를 함께 갱신합니다. 검색 속도를 위해 쓰기 시점에 계산과 메모리 비용을 미리 지불하는 구조입니다.

## 7. 한 번에 마무리하는 답변

> 커밋은 과거 부모에서 새 자식으로만 추가되어야 하므로 방향이 있고 사이클이 없는 DAG입니다. 사이클이 있으면 부모 우선 순서를 만들 수 없어 위상 정렬이 완료되지 않고 조상 관계도 모순됩니다. 기본 `LOG`는 진입 차수를 이용한 Kahn 위상 정렬로 부모를 먼저 출력하며, 현재 후보 선택 구현까지 포함한 최악 시간복잡도는 `O(V² + E)`입니다. `PATH`는 비용이 모두 1인 간선을 부모·자식 양쪽으로 이동해야 하므로 무방향 BFS를 사용하며 `O(V + E)`입니다. 날짜·작성자 정렬은 직접 구현한 안정 병합 정렬로 평균과 최악 모두 `O(V log V)`이고, 동률일 때 왼쪽 원소를 먼저 골라 상대 순서를 유지합니다. 검색은 작성자와 키워드에서 commit hash로 가는 역색인을 커밋 생성 시 만들어 전체 메시지 재검사를 줄입니다. 작성자 검색은 `O(K)`, 현재 키워드 검색은 후보 교집합과 결과 순서 정리를 합쳐 `O(P + V)`입니다.
