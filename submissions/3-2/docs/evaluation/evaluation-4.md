# 3-2 평가 항목 4 답변 가이드

이 문서는 `evaluations/evaluation3-2.md`의 **항목 4**에서 묻는 확장·변경 상황에 답하기 위한 가이드다. 항목 4는 현재 코드를 설명하는 데서 끝나지 않고, 요구사항이 달라졌을 때 **결과가 어떻게 바뀌며 어떤 자료구조와 알고리즘을 수정할지** 논리적으로 제안하는 문항이다.

아래 개선안은 평가 질문에 대한 설계 답변이며 현재 코드에 실제로 반영된 기능은 아니다.

## 0. 답변할 때 사용할 기준

| 기호 | 의미 |
| --- | --- |
| `V` | 전체 커밋 수 |
| `E` | 부모-자식 간선 수 |
| `A` | 조회 대상의 조상 커밋 수 |
| `K` | 검색 결과 수 |
| `P` | 검색 토큰별 posting list 길이의 합 |

커밋 수가 10배가 되면 복잡도에 따라 대략 다음처럼 비용이 변한다.

| 복잡도 | 입력 10배 증가 시 경향 |
| --- | --- |
| `O(V)` | 약 10배 |
| `O(V log V)` | 10배보다 조금 더 증가 |
| `O(V²)` | 약 100배 |

정확한 시간은 데이터 분기 형태, 메시지 길이, 검색 빈도, 실행 환경에 따라 달라진다. 따라서 실제 개선 전후에는 같은 형태의 합성 데이터를 만들어 시간을 측정해야 한다.

## 1. 커밋 수가 10배 늘어났을 때의 병목과 개선

### 평가 질문

> 커밋 수가 10배 늘어났을 때 병목이 될 지점을 예측하고, 개선 방향(자료구조/알고리즘)을 설명할 수 있는가?

### 핵심 답변

> 가장 먼저 확인할 병목은 기본 `LOG`와 `ANCESTORS`의 출력용 위상 정렬입니다. 현재 준비 목록에서 가장 이른 sequence를 매번 선형 탐색하므로 최악 `O(V² + E)`이고, 커밋이 10배가 되면 이 부분은 약 100배까지 늘 수 있습니다. 준비 목록을 우선순위 큐로 바꾸면 `O((V + E) log V)`로 개선할 수 있습니다. 그다음은 키워드 검색의 마지막 전체 커밋 순회와 반복되는 로그 정렬이며, 정렬된 posting list 교집합과 변경 시 무효화하는 캐시를 적용할 수 있습니다.

### 현재 기능별 확장성 점검

| 기능 | 현재 시간복잡도 | 10배 증가 시 예상 | 판단 |
| --- | --- | --- | --- |
| hash 조회 | 평균 `O(1)` | 거의 일정 | 딕셔너리 구조 유지 |
| 커밋 추가 | 메시지 토큰이 `T`개면 평균 `O(T)` | 커밋 한 건 비용은 유사 | 전체 인덱스 메모리는 증가 |
| 기본 `LOG` | 최악 `O(V² + E)` | 최악 약 100배 | 가장 우선적인 개선 대상 |
| `ANCESTORS` 수집 | `O(V + E)` | 약 10배 | 탐색 자체는 적절함 |
| 조상 출력 정렬 | 최악 `O(A² + E)` | 조상이 많으면 크게 증가 | `LOG`와 같은 개선 필요 |
| `PATH` | `O(V + E)` | 최악 약 10배 | 단발성은 적절, 반복 질의는 개선 검토 |
| 날짜·작성자 정렬 | `O(V log V)` | 10배보다 조금 더 증가 | 반복 호출 시 캐시 검토 |
| 작성자 검색 | `O(K)` | 결과 수에 비례 | 양호 |
| 키워드 검색 | `O(P + V)` | posting list와 전체 순회 증가 | 마지막 `V` 순회 제거 가능 |
| 전체 로그 출력 | 최소 `O(V)` | 출력량도 10배 | 페이지 분할·스트리밍 검토 |

현재 CLI의 커밋은 부모가 최대 하나이므로 보통 `E`는 `V`와 같은 규모다. merge처럼 여러 부모를 허용하면 `E`가 더 커질 수 있으므로 노드 수뿐 아니라 간선 수도 함께 측정한다.

### 병목 1: 위상 정렬의 준비 목록 선택

현재 `topological_order()`는 진입 차수가 0인 hash들을 `ready` 리스트에 넣고, 매 반복마다 `_earliest_sequence_index()`로 전체 목록을 확인한다. 리스트 중간의 `pop()`도 뒤 원소 이동 비용이 발생한다.

```text
현재
ready 리스트 선형 탐색 + 중간 제거
→ 최악 O(V² + E)
```

개선 방법은 `(sequence, hash)`를 우선순위로 하는 최소 힙을 사용하는 것이다.

```text
개선
ready 최소 힙 push/pop
→ O((V + E) log V)
```

Python의 `heapq`를 사용하거나 학습 목적이라면 이진 최소 힙을 직접 구현할 수 있다. 진입 차수 계산과 각 간선 처리는 그대로 재사용한다. 이 개선은 전체 `LOG`와 조상 부분 그래프의 위상 정렬에 함께 적용된다.

현재 커밋 생성 규칙에서는 `sequence` 자체가 부모보다 항상 크므로 단순 생성 순서도 유효한 위상 순서가 된다. 하지만 위상 정렬을 유지하면 여러 부모, 부분 그래프, 외부에서 구성한 테스트 그래프에서도 부모 관계를 직접 검증하고 사이클을 감지할 수 있다는 장점이 있다.

### 병목 2: 키워드 검색 결과의 전체 순회

현재는 역색인으로 후보 집합을 만든 뒤 생성 순서를 맞추기 위해 모든 `commits` 키를 한 번 확인한다.

```python
return [commit_hash for commit_hash in self.commits if commit_hash in matching]
```

posting list는 커밋 생성 순서대로 hash가 추가된다. 이 성질을 이용하면 가장 짧은 posting list를 기준 목록으로 선택하고, 다른 posting list를 집합으로 만들어 포함 여부만 검사할 수 있다.

```text
1. 토큰별 posting list 조회
2. 가장 짧은 posting list를 기준으로 선택
3. 나머지 목록을 set으로 변환
4. 기준 목록을 순서대로 보며 모든 set에 포함된 hash만 출력
```

그러면 전체 `commits`를 훑지 않고도 생성 순서를 유지할 수 있으며 목표 복잡도는 `O(P + K)`에 가까워진다. 단일 키워드는 해당 posting list를 그대로 복사하면 `O(K)`다.

### 병목 3: 반복 정렬과 반복 경로 질의

`LOG --sort-by=date|author`는 호출할 때마다 전체 커밋을 다시 병합 정렬한다. 로그 조회가 잦고 커밋 추가가 드물다면 다음 캐시를 둘 수 있다.

```text
date_log_cache
author_log_cache
topological_log_cache
```

새 커밋·브랜치 관계 변경이 발생하면 관련 캐시를 무효화하고, 다음 조회 때 한 번만 다시 계산한다. 캐시는 읽기 속도를 높이지만 무효화 규칙이 복잡해지고 메모리를 더 사용하므로 실제 호출 빈도를 측정한 뒤 적용한다.

`PATH` 한 번의 `O(V + E)`는 비가중 그래프 최단 경로로 적절하다. 하지만 아주 큰 그래프에서 경로 질의가 많다면 양방향 BFS로 양쪽 탐색 범위를 줄이거나, 자주 조회하는 쌍의 결과를 그래프 버전과 함께 캐시할 수 있다. 양방향 BFS의 최악 복잡도는 여전히 `O(V + E)`지만 실제 탐색 범위를 줄일 수 있다.

### 병목 4: 출력량과 메모리

알고리즘이 빨라도 전체 `LOG`를 화면에 모두 출력하려면 최소 `O(V)`의 문자열 생성과 입출력이 필요하다. 커밋이 매우 많다면 다음 기능이 필요하다.

- `LOG --limit=<n>` 같은 페이지 크기 제한
- 한 번에 거대한 문자열을 만들지 않는 스트리밍 출력
- 다음 페이지를 이어서 조회할 cursor

메모리는 `commits`, `parents`, `children`, 작성자·키워드 posting list에 비례해 증가한다. `parents`와 `children`을 함께 저장하면 간선 정보를 양쪽에 보관하는 비용이 있지만 `LOG`와 `PATH`의 역방향 조회가 빨라진다. 메모리가 실제 병목이 될 때만 한쪽 연결을 계산형으로 바꾸거나 압축 식별자를 검토한다.

### 개선 우선순위

```text
1. 측정용 대규모 데이터와 기준 시간 준비
2. O(V²) 위상 정렬 준비 목록을 최소 힙으로 변경
3. 키워드 검색의 전체 commits 순회 제거
4. 호출 빈도가 높다면 로그 캐시·양방향 BFS 검토
5. 출력이 병목이면 페이지 분할·스트리밍 적용
6. 같은 데이터로 개선 전후 시간·메모리 회귀 테스트
```

## 2. `PATH`를 부모 방향만 허용하도록 바꾸는 경우

### 평가 질문

> `PATH`의 간선 정의를 “부모 방향만 허용”으로 바꾸면 결과가 어떻게 달라지고, 구현은 무엇을 바꿔야 하는지 설명할 수 있는가?

### 핵심 답변

> 현재 PATH는 부모와 자식을 모두 이웃으로 보므로 같은 연결 요소 안의 형제 브랜치 사이도 이동할 수 있습니다. 부모 방향만 허용하면 `PATH a b`는 `b`가 `a`의 조상일 때만 경로가 생깁니다. 조상에서 자식으로 내려가거나 공통 조상을 거쳐 형제 브랜치로 이동할 수 없게 됩니다. 구현에서는 경로 복원 시 `parents`만 이웃으로 사용해야 하며, 현재처럼 목적지에서 거리를 계산하려면 역방향 BFS는 `children`만 따라가도록 바꿔야 합니다.

### 결과가 달라지는 예

```text
              ┌──→ c000002  [feature]
c000001 ──────┤
              └──→ c000003  [main]
```

허용 방향을 `자식 → 부모`로 정의하면 결과는 다음과 같다.

| 명령 | 현재 무방향 결과 | 부모 방향만 허용한 결과 | 이유 |
| --- | --- | --- | --- |
| `PATH c000002 c000001` | 경로 있음 | 경로 있음 | 자식에서 부모로 이동 |
| `PATH c000001 c000002` | 경로 있음 | `No path` | 부모에서 자식으로 내려갈 수 없음 |
| `PATH c000002 c000003` | 공통 조상을 거쳐 경로 있음 | `No path` | 공통 조상에서 형제 자식으로 내려갈 수 없음 |
| `PATH c000002 c000002` | 자기 자신 | 자기 자신 | 이동할 필요가 없음 |

즉 부모 방향 PATH는 일반적인 두 커밋 사이 연결보다 **출발 커밋에서 특정 조상까지 가는 최단 부모 경로**에 가까운 의미가 된다.

### 단순히 `_neighbors()`에서 자식만 제거하면 부족한 이유

현재 구현은 목적지에서 BFS를 시작해 각 노드의 `목적지까지 거리`를 구한다. 무방향 그래프에서는 간선을 반대로 따라도 같은 연결이므로 문제가 없다. 그러나 부모 방향 그래프에서 허용되는 간선은 다음과 같다.

```text
자식 → 부모
```

목적지에서 같은 부모 방향을 따라가면 “목적지로 올 수 있는 자식”이 아니라 “목적지보다 더 오래된 부모”를 방문하게 된다. 따라서 현재 BFS의 시작 방향까지 함께 바꿔야 한다.

### 권장 구현 전략

현재의 사전순 최소 경로 복원 방식을 유지하려면 다음처럼 변경한다.

#### 1. 목적지에서 역방향 BFS

허용 간선 `자식 → 부모`의 반대 방향은 `부모 → 자식`이다. 목적지에서 `children`만 따라가며 BFS하면 어떤 자식들이 목적지에 도달할 수 있는지와 그 거리를 계산할 수 있다.

```text
distance_to_end = reverse_bfs_from_end(end_hash, children)
```

#### 2. 출발점에서 부모만 따라 경로 복원

현재 커밋의 `parents` 중 목적지까지의 거리가 1 작은 부모만 후보로 선택한다. 후보가 여러 개면 hash가 가장 작은 부모를 고른다.

```text
candidate ∈ commits[current_hash].parents
distance_to_end[candidate] = distance_to_end[current_hash] - 1
```

이 방식은 다음 세 조건을 모두 만족한다.

- 부모 방향으로만 이동한다.
- 거리 값이 1씩 줄어 최단 경로가 된다.
- 여러 최단 부모 경로 중 hash 문자열 기준 사전순 최소 경로를 고른다.

대안으로 출발점에서 `parents`만 따라 일반 BFS를 실행하고 predecessor를 저장할 수도 있다. 다만 사전순 최소 경로까지 보장하려면 같은 깊이의 부모 처리 순서를 명시하거나 모든 최단 predecessor를 고려해야 한다.

### 변경할 함수와 테스트

| 현재 요소 | 변경 방향 |
| --- | --- |
| `_neighbors()` | 무방향 이웃 대신 부모 이웃과 역방향 자식 이웃을 역할별로 분리 |
| `_breadth_first_distances()` | 목적지에서 `children`만 따라가는 역방향 거리 계산으로 변경 |
| `shortest_path()` 복원 | `_neighbors()` 대신 `commits[current].parents`만 검사 |
| docstring | “무방향 최단 경로”를 “부모 방향 최단 경로”로 변경 |
| 테스트 | 조상 방향 성공, 자손 방향 실패, 형제 방향 실패, 자기 자신, 다중 부모 사전순 선택 추가 |

시간복잡도는 각 노드와 관련 간선을 한 번씩 확인하므로 여전히 `O(V + E)`, 공간복잡도는 `O(V)`다. 실제로는 목적지의 자손 영역만 방문하므로 그래프 전체보다 적게 탐색할 수 있다.

## 3. 작성자 정렬에 부모-자식 선후 조건이 추가되는 경우

### 평가 질문

> `LOG --sort-by=author` 요구사항이 “부모-자식 선후도 유지”로 강화된다면, 어떤 전략으로 해결할지 설명할 수 있는가?

### 핵심 답변

> 작성자를 기준으로 전체 커밋을 먼저 정렬하면 자식이 부모보다 앞에 올 수 있습니다. 강화된 요구사항에서는 부모 우선을 필수 조건으로 두고, 현재 출력 가능한 커밋들 사이에서만 작성자 이름을 우선순위로 사용해야 합니다. Kahn 위상 정렬의 ready 집합을 `(author.lower(), sequence, hash)` 기준 최소 힙으로 관리하면 부모 관계를 지키면서 가능한 범위에서 작성자 순서를 적용할 수 있습니다.

### 단순 작성자 정렬이 실패하는 예

```text
c000001: author=Zoe   부모
    ↓
c000002: author=Alice 자식
```

작성자만 오름차순으로 정렬하면 `Alice`가 `Zoe`보다 앞이므로 자식 `c000002`가 먼저 나온다. 부모 우선 조건과 작성자 전체 정렬이 충돌하는 예다.

따라서 두 조건을 다음 우선순위로 해석해야 한다.

```text
1순위: 모든 부모가 자식보다 먼저 나온다.  필수 제약
2순위: 현재 출력 가능한 커밋 중 author가 작은 것을 먼저 고른다.  우선순위
3순위: author가 같으면 sequence, hash로 결과를 결정한다.
```

작성자 정렬은 전체 목록에 대한 절대 정렬이 아니라 **위상 정렬이 허용하는 선택지 안에서 사용하는 tie-breaker**가 된다.

### 우선순위 위상 정렬 과정

```text
1. 각 커밋의 진입 차수를 부모 수로 계산한다.
2. 진입 차수가 0인 커밋을 ready 최소 힙에 넣는다.
3. (author.lower(), sequence, hash)가 가장 작은 커밋을 꺼내 출력한다.
4. 그 커밋의 자식들의 진입 차수를 1씩 줄인다.
5. 진입 차수가 0이 된 자식을 ready 힙에 넣는다.
6. 모든 커밋을 처리할 때까지 반복한다.
7. 결과 수가 V보다 작으면 사이클 오류로 처리한다.
```

부모 `Zoe`가 출력되기 전에는 자식 `Alice`의 진입 차수가 1이므로 ready 힙에 들어갈 수 없다. 따라서 author가 더 작아도 부모보다 먼저 선택되지 않는다.

### 재사용 가능한 설계

`topological_order()`에 우선순위 함수를 전달하도록 일반화할 수 있다.

```text
topological_order(..., priority_key=lambda commit: commit.sequence)
topological_order(..., priority_key=lambda commit: (
    commit.author.lower(),
    commit.sequence,
    commit.hash,
))
```

- 기본 `LOG`: 생성 순서를 우선순위로 사용
- 강화된 `LOG --sort-by=author`: 작성자, 생성 순서, hash를 우선순위로 사용
- `ANCESTORS`: 필요에 따라 기본 생성 순서 우선순위를 재사용

표준 정렬 API 금지 조건은 목록을 `sorted()`로 정렬하는 것을 막는다. 최소 힙은 정렬 결과 전체를 미리 만드는 대신 현재 가능한 최솟값을 반복해서 선택하는 자료구조다. 허용 범위를 보수적으로 해석한다면 외부 그래프·정렬 라이브러리 대신 이진 최소 힙을 직접 구현할 수 있다.

### 복잡도와 테스트

최소 힙의 삽입·삭제가 `O(log V)`이므로 다음과 같다.

- 진입 차수 계산과 간선 처리: `O(V + E)`
- 각 커밋의 힙 삽입·삭제: `O(V log V)`
- 전체 시간복잡도: `O((V + E) log V)`
- 추가 공간복잡도: `O(V)`

추가할 테스트는 다음과 같다.

1. 작성자 이름이 작은 자식이 작성자 이름이 큰 부모보다 뒤에 나오는지 확인한다.
2. 부모 관계가 없는 두 커밋은 작성자 순서로 나오는지 확인한다.
3. 작성자가 같으면 sequence 순서가 유지되는지 확인한다.
4. 여러 부모가 있는 자식은 모든 부모가 출력된 뒤에 나오는지 확인한다.
5. 사이클 입력이 감지되는지 확인한다.

## 4. hash 생성 방식을 카운터와 난수 사이에서 바꾸는 경우

### 평가 질문

> 해시 생성 방식을 카운터 기반 ↔ 난수 기반으로 바꿀 때 테스트/재현성/디버깅에 미치는 영향을 설명할 수 있는가?

### 핵심 답변

> 카운터 방식은 `c000001`처럼 값과 생성 순서를 예측할 수 있어 테스트·시연·디버깅이 쉽고 단일 세션에서 중복이 발생하지 않습니다. 난수 방식은 값이 덜 예측 가능하고 중앙 카운터 의존을 줄일 수 있지만 충돌 가능성이 0이 아니므로 `commits`에 이미 존재하는지 확인하고 재생성해야 합니다. 테스트는 고정 hash 문자열에 의존하지 않도록 바꾸거나 hash 생성기를 주입해야 하며, 재현 가능한 테스트에서는 결정적인 가짜 생성기를 사용합니다.

### 방식별 비교

| 관점 | 카운터 기반 | 난수 기반 |
| --- | --- | --- |
| 예시 | `c000001`, `c000002` | `a7f3c91d`, `42be108a` |
| 유일성 | 단일 세션에서 카운터를 재사용하지 않으면 보장 | 충분히 큰 공간에서는 확률이 낮지만 충돌 검사 필수 |
| 재현성 | 같은 명령 순서면 같은 hash | 실행할 때마다 달라짐 |
| 테스트 | 정확한 기대 hash를 쓰기 쉬움 | 속성 검증 또는 생성기 주입 필요 |
| 디버깅 | 생성 순서가 눈에 보여 추적이 쉬움 | 별도 sequence·timestamp와 함께 봐야 함 |
| 예측 가능성 | 다음 값을 쉽게 추측 가능 | 일반적으로 추측하기 어려움 |
| 분산 생성 | 공유 카운터 동기화 필요 | 각 실행 주체가 독립 생성 가능 |
| 충돌 처리 | 단일 카운터에서는 불필요 | 기존 키 조회 후 재시도 필요 |

### 카운터에서 난수로 바꿀 때의 구현

난수 hash를 한 번 만들고 바로 저장하면 안 된다. 같은 값이 이미 있을 경우 기존 커밋을 덮어쓸 수 있기 때문이다.

```text
반복:
    candidate = 충분히 긴 난수 hash 생성
    candidate가 commits에 없으면 선택
    이미 있으면 새 candidate 생성
```

난수 공간은 예상 커밋 수보다 충분히 커야 한다. 가능한 값의 수가 작거나 커밋 수가 많아지면 생일 문제 때문에 충돌 확률이 증가한다. 운영 코드에서는 재시도 횟수 제한과 생성 실패 처리도 정한다.

현재 `Commit`에는 hash와 별도로 `sequence`가 있다. 따라서 hash를 난수로 바꿔도 날짜·작성자 정렬의 동률 처리와 기본 생성 순서는 `sequence`로 유지할 수 있다. 다만 최단 경로가 여러 개일 때 hash 사전순으로 경로를 선택하는 요구사항은 난수값에 영향을 받으므로, 같은 그래프라도 실행마다 선택되는 동률 경로가 달라질 수 있다.

### 테스트를 바꾸는 방법

현재 테스트에는 `c000001`, `c000002` 같은 정확한 값을 기대하는 부분이 있다. 난수 방식으로 바꾸면 다음 전략을 사용한다.

#### 1. hash 생성기 의존성 주입

```text
운영: RandomHashGenerator
테스트: SequenceHashGenerator(["h1", "h2", "h3"])
```

`MiniGit` 생성자에 시계처럼 hash 생성기도 주입하면 운영에서는 난수를 사용하고 테스트에서는 결과를 고정할 수 있다. 충돌 재시도 테스트에는 `h1, h1, h2`를 반환하는 가짜 생성기를 넣어 두 번째 `h1`을 거부하고 `h2`를 선택하는지 확인한다.

#### 2. 정확한 문자열 대신 속성을 검증

- 두 커밋의 hash가 서로 다른가?
- hash가 빈 문자열이 아닌가?
- 생성된 hash가 `commits`의 키로 조회되는가?
- 브랜치와 부모가 실제 반환된 hash를 가리키는가?
- 많은 커밋을 생성해 중복이 없는가?

#### 3. CLI 테스트는 출력에서 hash를 캡처

후속 명령에서 `c000001`을 하드코딩하지 않고 `COMMIT` 결과에서 실제 hash를 추출해 사용한다. 또는 저장소 계층 테스트에서 반환된 hash를 변수에 보관한다.

난수 생성기의 seed를 고정하는 방법도 있지만 난수 알고리즘이나 호출 횟수가 바뀌면 테스트가 깨질 수 있다. 명시적인 가짜 생성기 주입이 테스트 의도를 더 잘 보여 준다.

### 재현성과 디버깅에 미치는 영향

카운터 hash는 번호만 보고도 대략 생성 순서를 알 수 있어 로그를 읽기 쉽다. 난수 hash는 시연 문서의 예상 출력과 버그 보고서가 실행마다 달라진다. 따라서 난수 방식에서는 다음 정보를 함께 남기는 것이 좋다.

- 별도의 `sequence`
- 정확한 `timestamp`
- 부모 hash
- 현재 브랜치 이름
- 재현에 사용한 입력 명령
- 테스트라면 주입한 생성기 값 또는 seed

난수 hash를 사용해도 실패한 실행의 실제 hash를 기록하면 그 세션 안의 디버깅은 가능하다. 어려워지는 부분은 같은 명령을 다시 실행했을 때 동일한 식별자를 자동으로 얻지 못한다는 점이다.

### 난수에서 카운터로 바꿀 때 주의할 점

단일 프로세스의 메모리 저장소에서는 `_next_sequence` 증가만으로 유일성을 쉽게 보장할 수 있다. 하지만 데이터 영속성이나 여러 프로세스를 추가한다면 다음 문제가 생긴다.

- 재시작 후 카운터를 1로 초기화하면 기존 hash와 중복될 수 있다.
- 여러 프로세스가 같은 번호를 동시에 읽으면 중복될 수 있다.
- 저장된 최대 번호를 복구하거나 원자적으로 증가하는 공유 카운터가 필요하다.

현재 과제는 단일 프로세스·메모리 기반이므로 이런 동기화 비용이 없고, 재현성과 학습 편의성이 큰 카운터 방식이 적합하다.

## 5. 자주 나오는 꼬리 질문

### 커밋이 10배 늘어나면 딕셔너리를 다른 자료구조로 바꿔야 하는가?

> hash 조회는 이미 딕셔너리로 평균 `O(1)`이므로 우선 교체 대상이 아닙니다. 실제 병목은 `O(V²)` 위상 정렬 후보 선택, 반복 정렬, 전체 결과 순회와 출력입니다. 측정 결과 없이 잘 동작하는 딕셔너리를 먼저 바꾸는 것은 효과가 작을 수 있습니다.

### 최소 힙으로 바꾸면 위상 정렬이 `O(V + E)`가 되는가?

> 우선순위가 필요하면 각 커밋의 heap push/pop에 `O(log V)`가 들어가므로 `O((V + E) log V)` 수준입니다. 단순 FIFO 큐라면 `O(V + E)`지만 생성 순서나 작성자 우선순위를 보장하려면 추가 전략이 필요합니다.

### 부모 방향 PATH에서도 BFS가 필요한가?

> 필요합니다. merge commit처럼 여러 부모를 허용하면 목적지 조상까지 가는 부모 경로가 여러 개일 수 있습니다. 모든 간선 비용이 1이므로 최단 부모 경로에는 여전히 BFS가 적합합니다.

### 작성자 정렬과 부모 우선 조건을 둘 다 완벽한 전체 정렬로 만족할 수 있는가?

> 두 조건이 충돌할 수 있으므로 작성자 전체 오름차순을 항상 만족할 수는 없습니다. 부모 우선을 필수 제약으로 두고, 현재 위상 정렬상 선택 가능한 커밋끼리만 작성자 순서를 적용한다고 요구사항의 우선순위를 명확히 해야 합니다.

### 난수 hash가 보안상 더 좋은가?

> 예측하기 어렵다는 장점은 있지만 난수 식별자만으로 보안이 완성되지는 않습니다. 접근 제어와 인증이 별도로 필요합니다. 이 로컬 학습용 프로그램에서는 보안보다 유일성·재현성·설명 가능성이 더 중요해 카운터 방식이 합리적입니다.

## 6. 한 번에 마무리하는 답변

> 커밋이 10배 늘면 현재 `O(V² + E)`인 위상 정렬의 ready 목록 선형 선택이 가장 먼저 커지므로 최소 힙으로 바꿔 `O((V + E) log V)`로 개선하겠습니다. 키워드 검색은 posting list 순서를 활용해 마지막 전체 커밋 순회를 제거하고, 반복 로그에는 변경 시 무효화하는 캐시를 검토하겠습니다. PATH가 부모 방향만 허용되면 도착점이 출발점의 조상일 때만 경로가 생기며, 목적지에서 children을 따라 역방향 거리를 계산한 뒤 출발점에서는 parents만 따라 복원해야 합니다. 작성자 정렬이 부모 우선도 지켜야 하면 Kahn 위상 정렬의 ready 집합을 author 우선 최소 힙으로 관리합니다. hash를 난수로 바꾸면 충돌 검사와 재시도가 필요하고 테스트는 생성기 주입이나 속성 검증으로 바꿔야 합니다. 별도 sequence를 유지하면 정렬과 디버깅에 필요한 생성 순서는 보존할 수 있습니다.

## 7. 문항별 최종 체크리스트

- [ ] 10배 증가 시 `O(V²)` 작업이 약 100배까지 커질 수 있다고 설명했다.
- [ ] 위상 정렬의 ready 리스트를 최소 힙으로 바꾸는 개선안을 제시했다.
- [ ] 키워드 검색의 마지막 전체 순회와 개선 방법을 설명했다.
- [ ] 반복 정렬 캐시와 출력 페이지 분할은 사용 패턴을 측정한 뒤 적용한다고 설명했다.
- [ ] 부모 방향 PATH에서는 조상으로만 이동할 수 있고 형제·자손 방향은 `No path`라고 설명했다.
- [ ] 목적지 역방향 BFS는 children, 실제 경로 복원은 parents를 사용한다고 설명했다.
- [ ] 부모 우선을 필수 제약, 작성자를 ready 후보의 우선순위로 정의했다.
- [ ] author 우선 최소 힙을 사용하는 Kahn 위상 정렬을 설명했다.
- [ ] 카운터와 난수 hash의 유일성·재현성·디버깅 차이를 설명했다.
- [ ] 난수 충돌 검사, 생성기 주입, 속성 기반 테스트 방법을 설명했다.
