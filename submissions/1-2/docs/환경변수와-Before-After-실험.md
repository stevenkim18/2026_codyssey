# 환경변수와 Before/After 실험

환경변수는 프로그램을 실행하기 전에 전달하는 설정값이다. 소스 코드를 직접 수정하지 않아도 실행 조건을 바꿔 같은 앱을 다르게 동작하게 만들 수 있다.

이 과제에서는 환경변수가 장애를 재현하거나 피하기 위한 설정값으로 사용된다.

## 과제에서 사용하는 환경변수

| 환경변수 | 하는 일 | 장애와의 관계 |
| --- | --- | --- |
| `MEMORY_LIMIT` | 앱이 메모리 사용량을 판단하는 기준 | 낮으면 메모리 한계와 보호 종료를 빨리 관찰할 수 있고, 높이면 더 오래 실행되거나 내부 정리 동작을 관찰할 수 있다. |
| `CPU_MAX_OCCUPY` | `CpuWorker`의 허용 작업량에 영향을 주는 설정 | 높으면 CPU 작업량이 계속 증가해 임계치에 도달할 수 있고, 낮으면 cooldown을 통해 부하를 낮추며 실행된다. |
| `MULTI_THREAD_ENABLE` | 여러 스레드를 동시에 실행할지 결정 | `true`면 공유 자원 경쟁으로 Deadlock이 재현될 수 있고, `false`면 해당 경쟁 경로를 피할 수 있다. |

## Before/After 실험의 목적

Before/After 비교의 목적은 설정 하나가 장애에 영향을 준다는 가설을 검증하는 것이다.

예를 들어 메모리 문제가 의심될 때 `MEMORY_LIMIT`만 128MB에서 512MB로 변경하고 CPU와 멀티스레드 설정은 그대로 둔다. 두 실행의 결과가 달라졌다면 메모리 한계 설정이 증상에 영향을 주었다고 판단할 근거가 생긴다.

한 번의 실험에서는 가능한 한 **환경변수 하나만 변경**해야 한다. 여러 값을 동시에 바꾸면 어떤 변경이 결과를 만들었는지 알 수 없기 때문이다.

## 실험 진행 순서

1. **장애 재현 조건**에서 실행한다.
   - 메모리 한계를 낮추거나, CPU 허용량을 높이거나, 멀티스레드를 활성화해 장애가 나타나는 조건을 만든다.
2. **우회 조건**에서 환경변수 하나를 변경한다.
   - 메모리 한계를 높이고, CPU 허용량을 낮추고, 또는 멀티스레드를 비활성화한다.
3. 같은 항목을 수집하고 비교한다.
   - 생존 시간
   - CPU와 RSS 변화
   - 애플리케이션 로그
   - PID와 스레드 상태
   - 종료했다면 종료 주체와 이유

## 장애별 비교 예시

| 장애 | 장애 재현 조건 | 우회 조건 | 비교할 결과 |
| --- | --- | --- | --- |
| 메모리 누적 / OOM | 낮은 `MEMORY_LIMIT` | 높은 `MEMORY_LIMIT` | RSS 증가 추세, `MemoryGuard` 로그, 생존 시간 |
| CPU 과점유 | 높은 `CPU_MAX_OCCUPY` | 낮은 `CPU_MAX_OCCUPY` | CPU 또는 `Current Load` 추세, 임계치 로그, cooldown 여부 |
| Deadlock | `MULTI_THREAD_ENABLE=true` | `MULTI_THREAD_ENABLE=false` | `WAITING`/`BLOCKED` 로그, 스레드 대기 상태, 로그 진행 여부 |

## 종료 원인도 구분한다

프로세스가 종료됐다는 사실만으로 원인을 알 수는 없다. 애플리케이션 로그와 Docker 상태를 함께 봐야 한다.

- 앱 로그에 `MemoryGuard` 또는 CPU 임계치 관련 메시지가 있다면 앱 내부 보호 정책의 동작을 의심한다.
- Docker 상태의 `OOMKilled=true`는 Docker cgroup 메모리 한계 때문에 종료됐다는 중요한 단서다.
- 관찰 시간이 끝나 실행 스크립트가 컨테이너를 정리한 경우에는, 그 종료를 장애의 결과로 해석하지 않는다.

## 임시 조치와 근본 해결

환경변수 변경은 주로 장애를 피하거나 생존 시간을 늘리는 **임시 조치**다.

- `MEMORY_LIMIT`을 높이는 일은 메모리 누적 자체를 없애지 않는다.
- `CPU_MAX_OCCUPY`를 낮추는 일은 CPU 작업의 설계를 개선하지 않는다.
- 멀티스레드를 끄는 일은 동시 실행의 장점을 포기하고 Deadlock 경로를 피하는 방법이다.

근본 해결은 코드와 설계를 고치는 일이다. 예를 들어 불필요한 메모리 참조를 해제하고, CPU 작업을 작게 나누어 백오프를 적용하고, 모든 스레드가 같은 순서로 락을 획득하도록 바꾸는 방법이 있다.

> 문서에서 `Before`와 `After`가 모호하다면, **장애 재현 조건**과 **우회 조건**을 함께 표기한다. 특히 CPU 설정처럼 과제 계획표의 실행 순서와 실제 우회 조치의 방향이 다를 수 있을 때 혼동을 줄일 수 있다.
