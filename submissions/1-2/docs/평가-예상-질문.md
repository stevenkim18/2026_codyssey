# 평가 예상 질문과 답변

이 문서는 1-2 과제의 결과물과 증거를 바탕으로, 평가에서 설명할 수 있어야 하는 질문과 답변을 정리한다. 답변할 때는 결론만 말하지 않고 관측한 증거를 함께 제시한다.

## 프로세스가 살아 있는데 왜 Deadlock이라고 판단했나요?

프로세스의 PID가 존재하는 것은 종료되지 않았다는 뜻일 뿐, 작업이 진행된다는 뜻은 아닙니다. Deadlock Before 실행에서는 두 워커가 각각 락을 획득한 뒤 상대 락을 기다리는 `WAITING ... BLOCKED` 로그가 마지막으로 기록됐습니다. 이후 로그가 진행되지 않았고, CPU와 RSS가 거의 변하지 않았으며, `top -H`와 `ps -L`에서 스레드가 sleeping 또는 `futex` 대기 상태였습니다. 이 증거들을 함께 사용해 살아 있지만 진행하지 못하는 Deadlock이라고 판단했습니다.

## Deadlock의 4대 조건은 무엇이고, 이번 사례에서 어떻게 성립했나요?

상호 배제, 점유 대기, 비선점, 순환 대기입니다. Thread-1은 `Shared_Memory_A`를, Thread-2는 `Socket_Pool_B`를 각각 배타적으로 점유했습니다. 두 스레드는 가진 락을 놓지 않은 채 상대 락을 기다렸고, 상대 락을 강제로 빼앗을 수 없었습니다. 마지막으로 Thread-1이 B를, Thread-2가 A를 기다려 순환 대기가 형성됐습니다.

## 앱 내부 메모리 보호 종료와 Docker/OS OOM Kill은 어떻게 구분했나요?

앱 내부 종료는 애플리케이션 로그의 `MemoryGuard`와 `Self-terminating` 메시지로 확인했습니다. Docker OOM Kill 여부는 컨테이너 상태의 `OOMKilled` 값으로 확인했습니다. 제출한 OOM Before 실행은 `OOMKilled=false`이면서 `MemoryGuard` 로그가 있었으므로, Docker cgroup이 종료한 것이 아니라 앱 내부 보호 정책이 종료한 것으로 판단했습니다.

## RSS가 증가하면 무조건 메모리 누수인가요?

아닙니다. RSS 증가는 프로그램이 작업을 위해 일시적으로 메모리를 확보하는 정상적인 상황에서도 나타날 수 있습니다. 영구적 메모리 누수 여부는 소스 코드에서 객체나 버퍼의 참조와 해제 시점을 확인해야 확정할 수 있습니다. 이번 과제에서는 RSS가 증가해 앱의 메모리 보호 정책에 도달한 자원 고갈 경로를 증거로 제시했고, 소스 없이 영구적 누수라고 단정하지 않았습니다.

## CPU 사용률과 앱의 `Current Load`가 왜 다른가요?

CPU 사용률은 `ps`, `top`, `monitor.sh` 등이 운영체제 관점에서 특정 시점 또는 구간의 CPU 사용을 측정한 값입니다. `Current Load`는 앱의 `CpuWorker`가 내부 작업량을 나타내기 위해 기록한 지표입니다. 측정 주체와 계산 방식이 다르므로 값이 같을 필요는 없습니다. 이번 분석에서는 두 값을 같은 의미로 취급하지 않고, 부하 증가 추세와 CPU 임계치 로그를 함께 근거로 사용했습니다.

## `CPU_MAX_OCCUPY`는 Docker의 CPU quota인가요?

아닙니다. 이번 관측에서 `CPU_MAX_OCCUPY`는 앱의 `CpuWorker`가 허용 작업량을 결정하는 내부 설정으로 보입니다. Docker CPU quota를 설정하는 값이라면 컨테이너의 cgroup CPU 제한을 직접 바꿔야 하지만, 이 실험에서는 앱의 환경변수만 변경했습니다.

## 환경변수 변경이 왜 근본 해결이 아닌가요?

환경변수 변경은 장애가 발생하는 조건을 완화하거나 위험한 실행 경로를 피하는 임시 조치입니다. `MEMORY_LIMIT`을 높여도 불필요한 메모리 누적이 사라지지는 않고, `CPU_MAX_OCCUPY`를 낮춰도 CPU 작업 자체가 효율적으로 바뀌지는 않습니다. `MULTI_THREAD_ENABLE=false`는 Deadlock 경로를 피하지만 동시 실행 기능도 포기합니다. 근본 해결은 메모리 해제, CPU 작업 분할·백오프, 전역 락 획득 순서 통일 같은 코드와 설계의 수정입니다.

## 왜 로그만 보지 않고 OS 도구도 함께 사용했나요?

로그는 앱 내부의 판단과 작업 진행을 보여 주지만, 실제 프로세스·스레드 상태와 자원 사용량을 보장하지는 않습니다. 반대로 OS 도구는 CPU, RSS, PID, 스레드 상태를 보여 주지만 앱이 어떤 정책으로 판단했는지는 알 수 없습니다. 따라서 로그, `monitor.sh`, `ps`, `top -H`, `ps -L`, Docker 상태를 교차 검증해 결론의 신뢰도를 높였습니다.

## 관찰 종료 후 컨테이너를 정리한 ExitCode 143은 장애인가요?

아닙니다. 실행 스크립트가 정해 둔 관찰 시간이 끝난 뒤 컨테이너를 stop하면 `SIGTERM`에 해당하는 ExitCode 143이 나타날 수 있습니다. 이 경우 종료 코드만으로 장애라고 판단하지 않고, 종료 직전 로그와 실행 스크립트의 관찰 종료 시점을 함께 확인합니다.

## Deadlock을 근본적으로 해결하려면 어떻게 하나요?

모든 코드 경로에서 락을 획득하는 순서를 하나로 통일합니다. 예를 들어 항상 A를 먼저 획득하고 B를 다음에 획득하도록 정하면 순환 대기를 막을 수 있습니다. 추가로 `try-lock` 또는 timeout을 사용해 무한 대기를 피하고, 대기 중인 자원과 소유자를 로그로 남겨 진단할 수 있게 합니다.
