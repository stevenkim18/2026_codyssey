# 1-2 평가 항목 답변 가이드

이 문서는 [1-2 평가 문항](../../../evaluations/evaluation1-2.md)을 `submissions/1-2`의 실제 실행 결과와 연결해 정리한 발표·평가용 가이드다. 각 항목은 결론만 말하지 않고, **관측값 → 앱 로그 → 환경변수 변경 결과** 순서로 설명한다.

## 답변할 때 지킬 기준

- PID와 타임스탬프는 실행마다 달라진다. 아래 숫자는 리포트에 정리한 대표 실행의 값이므로, 평가 중에는 링크된 원본 로그의 값과 함께 제시한다.
- RSS 증가만으로 영구적인 메모리 누수라고 단정하지 않는다. 이 결과물에서 확인한 사실은 RSS/힙이 누적되고 앱의 `MemoryGuard`가 종료한 **자원 고갈 경로**다.
- OS 도구의 CPU 사용률과 앱 로그의 `Current Load`는 측정 주체와 계산 방식이 다르다. 두 값을 같은 수치로 취급하지 않고, 증가 추세와 CPU 임계치 로그를 함께 해석한다.
- 관찰 시간이 끝난 뒤 `run_case.sh`가 컨테이너를 정리하면 `ExitCode=143`이 나타날 수 있다. 이 값만으로 장애 종료라고 판단하지 않는다.
- 환경변수 변경은 재현 조건을 바꾸는 임시 조치다. 메모리 해제, CPU 작업 분할, 락 순서 통일 같은 코드·설계 수정이 근본 해결이다.

## 항목 1 — 결과물과 증거

### 1. OOM: 메모리 증가 후 강제 종료 패턴

**답변 요지:** 대상 워커 PID 8의 RSS가 같은 실행 안에서 `16.4MB → 66.5MB → 91.5MB → 141.5MB`로 증가했다. 앱 로그도 `Current Heap: 25MB`부터 25MB 단위로 증가하다가 `150MB >= 128MB`에서 `MemoryGuard`의 자기 종료를 기록했다.

- 관제값은 [Before observations.log](../evidence/oom/before/20260915-140016-61131/observations.log)에 5초 간격으로 남아 있다.
- 종료 직전의 [Before application.log](../evidence/oom/before/20260915-140016-61131/application.log)에는 `Memory limit exceeded`와 `Self-terminating process 8`가 같은 시각에 기록돼 있다.
- [container-inspect.json](../evidence/oom/before/20260915-140016-61131/container-inspect.json)의 `OOMKilled=false`도 함께 확인했다. 즉 Docker cgroup OOM Kill이 아니라 앱 내부 `MemoryGuard`의 종료라는 근거다.

### 2. OOM: `MEMORY_LIMIT` 변경 전후 비교

**답변 요지:** 다른 조건은 고정하고 `MEMORY_LIMIT`만 `128MB → 512MB`로 바꿨다. 128MB에서는 약 17초 후 `MemoryGuard`가 종료했지만, 512MB에서는 525MB까지 증가한 뒤 `Starting cleanup...`과 함께 힙이 25MB로 회복했고 관찰 시간 동안 생존했다.

| 항목 | 장애 재현 조건 | 우회 조건 |
| --- | --- | --- |
| 설정 | `MEMORY_LIMIT=128` | `MEMORY_LIMIT=512` |
| 관측 | RSS 16.4MB에서 141.5MB까지 증가 | RSS 516.7MB까지 증가 후 66.7MB로 감소 |
| 앱 로그 | `150MB >= 128MB`, `MemoryGuard` 종료 | `525MB`, `Starting cleanup`, 이후 `25MB` |
| 결과 | 약 17초 뒤 앱 내부 종료 | 약 2분 15초 관찰 중 생존 |

이 변경은 누적 할당 자체를 없앤 것이 아니라, 정리 루틴이 실행될 여유를 준 임시 조치다. 상세 수치와 로그는 [OOM 리포트](../reports/oom.md)의 Before/After 표에서 확인한다.

### 3. CPU: 임계치 초과와 보호 종료 패턴

**답변 요지:** `CPU_MAX_OCCUPY=100`에서 앱의 `CpuWorker`가 기록한 `Current Load`가 `5.00% → 50.99%`까지 올라갔고, 약 27초 뒤 `CPU Threshold Violated! (50.99%)`가 기록됐다. 이는 특정 앱의 CPU 작업량과 그에 대한 앱 내부 보호 정책을 확인한 것이다.

- [100% application.log](../evidence/cpu/after/20260915-141620-67680/application.log)에 `CpuWorker` 시작, 부하 증가, 임계치 위반 로그가 연속으로 있다.
- [100% observations.log](../evidence/cpu/after/20260915-141620-67680/observations.log)의 `ps -L`, `top -H`, `docker stats`는 대상 PID/스레드와 컨테이너 수준의 CPU를 보조 확인하는 자료다.
- `Current Load=50.99%`를 `ps`의 순간 CPU 사용률과 같은 뜻으로 말하면 안 된다. 앱 내부 부하 지표의 증가와 실제 관측값을 교차 검증했다는 점이 핵심이다.

### 4. CPU: `CPU_MAX_OCCUPY` 변경 전후 비교

**답변 요지:** 이 바이너리에서는 값이 높을수록 CPU 작업량이 계속 올라가 임계치에 도달한다. 따라서 `10% → 100%`는 과제 계획표대로 **정상 조건과 장애 재현 조건을 비교**한 실행이고, 실제 우회 조치 검증은 `100% → 10%`이다.

| 구분 | `CPU_MAX_OCCUPY=100` | `CPU_MAX_OCCUPY=10` |
| --- | --- | --- |
| 앱 로그 | `Current Load` 증가 후 `CPU Threshold Violated!` | 5~10% 범위에서 `Peak reached`와 `Cooldown complete` 반복 |
| 생존 | 약 27~28초 뒤 임계치 도달 | 35초 이상 관찰 중 정상 진행 |
| 의미 | 장애 재현 조건 | CPU 부하를 제한한 우회 조건 |

계획표의 `10 → 100` 비교와 우회의 `100 → 10` 비교를 혼동하지 않는다. 근거는 [CPU 리포트의 계획표 비교](../reports/cpu.md)와 [100% 재현 로그](../evidence/cpu/before/20260915-140355-62651/application.log), [10% 우회 로그](../evidence/cpu/after/20260915-140458-63304/application.log)다.

### 5. Deadlock: PID는 존재하지만 작업이 멈춘 상태

**답변 요지:** Deadlock Before에서 PID 7과 자식 PID 8은 계속 존재했다. 그러나 PID 8의 RSS는 16.4MB에서 16.5MB 근처로 정체됐고 CPU는 0.0~0.5%였으며, 앱 로그는 `WAITING ... BLOCKED` 이후 더 진행되지 않았다.

- `top -H -p 8`에서는 `3 threads, 0 running, 3 sleeping`이 관측됐다.
- `ps -L -p 8`에서는 TID 8/166/167이 모두 `futex_wait_queue` 대기 상태였다.
- 따라서 PID 존재만으로 정상이라고 판단하지 않고, **PID 유지 + 자원 사용량 정체 + 로그 정지 + 스레드 대기**를 함께 근거로 Deadlock이라고 판단했다.

원본은 [Deadlock Before 관제 로그](../evidence/deadlock/before/20260915-140644-64188/observations.log)와 [앱 로그](../evidence/deadlock/before/20260915-140644-64188/application.log)에 있다.

### 6. Deadlock: `MULTI_THREAD_ENABLE` 변경 전후 비교

**답변 요지:** `MULTI_THREAD_ENABLE=true`에서는 두 워커가 서로 가진 락을 기다리며 멈췄다. `false`로 변경하면 해당 동시 락 획득 경로를 피하므로, `Scheduler` 완료와 이후 워커 로그가 계속 기록됐다.

| 항목 | Before: `true` | After: `false` |
| --- | --- | --- |
| 핵심 로그 | 두 워커의 `WAITING ... BLOCKED` | `Scheduler] All tasks completed.` |
| 진행 여부 | 이후 로그 정지 | `MemoryWorker`와 `CpuWorker` 로그가 계속 추가 |
| 스레드 상태 | 전부 sleeping, `futex_wait_queue` | Scheduler가 정상 완료 |
| 의미 | Deadlock 재현 | 멀티스레드 경로를 끈 임시 회피 |

멀티스레드를 끄는 것은 성능·동시성의 장점을 포기하는 우회책이다. 근본 해결은 락 획득 순서와 대기 정책을 고치는 일이다. 자세한 증거는 [Deadlock 리포트](../reports/deadlock.md)에 있다.

### 7. 세 리포트의 GitHub Issue 구조

세 리포트 [OOM](../reports/oom.md), [CPU](../reports/cpu.md), [Deadlock](../reports/deadlock.md)은 모두 다음 구조를 따른다.

1. `Description`: 어떤 조건에서 어떤 현상이 발생했는지
2. `Evidence & Logs`: 관제 로그, 앱 로그, Docker 상태, 비교 캡처
3. `Root Cause Analysis`: 관측 증거로부터 추론한 기술적 원인과 OS 동작
4. `Workaround & Verification`: 환경변수 조치, Before/After, 근본 해결 제안

따라서 평가에서는 각 리포트가 **현상 → 증거 → 원인 → 조치**의 흐름을 갖는다고 설명하면 된다.

### 8. PID·타임스탬프·핵심 로그가 담긴 증거

- `observations.log`에는 수집 시각, PID/PPID, 경과 시간, CPU, MEM, RSS, 상태, 포트가 기록된다.
- `application.log`에는 Docker 타임스탬프와 애플리케이션 타임스탬프, `MemoryGuard`, `CpuWorker`, `WAITING/BLOCKED` 같은 핵심 메시지가 기록된다.
- `container-inspect.json`에는 `ExitCode`, `OOMKilled`, cgroup 메모리 제한을 남긴다.
- 세 리포트는 원본 로그와 [비교 캡처](../evidence/captures/)를 함께 링크한다.

## 항목 2 — 도구 선택과 판단 흐름

### 1. `monitor.sh`로 메모리 증가를 추적한 방법

`docker/monitor.sh`은 시스템 전체 메모리 대신 대상 앱 프로세스를 찾고, 각 PID의 RSS를 반복 기록한다.

1. `ps -eo pid=,args=`의 결과를 `awk`로 필터링해 `/opt/agent/agent-app-linux-arm64`를 실행한 PID만 찾는다.
2. `ss -ltnH`로 앱 포트 `15034`가 실제로 LISTEN 중인지 먼저 확인한다.
3. 각 PID에 `ps -p "$pid" -o pid=,ppid=,etime=,pcpu=,pmem=,rss=,vsz=,stat=,comm=`를 실행한다.
4. `read`로 출력 필드를 나누고, `awk`로 `rss_kb / 1024`를 계산해 MB 단위 RSS를 만든다.
5. 타임스탬프와 함께 `CPU`, `MEM`, `RSS`, `STAT`을 `monitor.log`와 표준 출력에 남긴다.

`pmem`은 전체 메모리 대비 비율이고, `rss`는 해당 프로세스가 실제 물리 메모리에서 차지하는 크기다. 이 과제의 메모리 추세 판단에는 같은 워커 PID의 RSS를 시간 순으로 비교하는 것이 더 직접적이다. 구현은 [monitor.sh](../docker/monitor.sh)에서 확인할 수 있다.

### 2. CPU 도구와 옵션을 선택한 이유

| 도구 | 사용한 형태 | 확인하는 대상 | 선택 이유 |
| --- | --- | --- | --- |
| `monitor.sh` / `ps` | `ps -p PID -o ...pcpu...` | 대상 프로세스의 CPU와 RSS | 시스템 전체가 아닌 앱 PID를 지속적으로 기록한다. |
| `top` | `top -H -b -n 1 -p PID` | PID 내부 스레드별 CPU·상태 | `-H`는 스레드를 보이고, `-b`는 캡처 가능한 batch 모드, `-n 1`은 한 번의 스냅샷, `-p`는 대상 PID로 범위를 제한한다. |
| `ps` | `ps -L -p PID -o pid,tid,stat,pcpu,pmem,wchan:32,comm` | TID, 상태, CPU, 대기 채널 | `-L`로 각 스레드를 분리해 CPU 작업 또는 대기 상태를 확인한다. `wchan`은 `futex` 같은 대기 단서를 보여 준다. |
| `docker stats` | `--no-stream` | 컨테이너 cgroup의 순간 CPU·메모리 | 앱 PID 관측값과 다른 컨테이너 범위의 보조 지표로 사용한다. |

앱 로그의 `Current Load`는 `CpuWorker`가 기록하는 내부 작업량이다. OS CPU 수치가 예상보다 작아도 값이 모순이라고 단정하지 않고, 수집 시점·범위가 다름을 설명한다.

### 3. “살아있지만 멈춘 상태”의 진단 순서

1. `monitor.sh`와 `ps -ef`로 PID가 존재하는지 확인한다. 없으면 종료 원인부터 찾는다.
2. 같은 PID의 여러 시점 관측값을 비교해 CPU와 RSS가 계속 변하는지 확인한다.
3. `application.log`의 마지막 메시지와 그 이후 로그 진행 여부를 확인한다.
4. 정체됐다면 `top -H`와 `ps -L`로 모든 스레드가 sleeping 또는 `futex` 대기인지 확인한다.
5. `WAITING/BLOCKED`와 락 소유 로그를 연결해 순환 대기인지 확인한다.
6. `MULTI_THREAD_ENABLE=false`로 한 변수만 바꿔 다시 실행하고, 로그 진행 여부가 회복되는지 비교한다.

단일 스냅샷만으로 Deadlock이라고 결론 내리지 않는다. 이 순서는 [장애별 진단 흐름](장애별-진단-흐름.md)에도 정리돼 있다.

## 항목 3 — OS 원리 설명

### 1. 메모리 보호 정책이 프로세스를 종료하는 이유

프로세스가 메모리를 계속 확보하면 남은 메모리가 줄어들어 다른 프로세스와 운영체제까지 압박받을 수 있다. 응답 지연, 할당 실패, swap 증가, 최종적으로 OS/Docker OOM Kill 같은 더 큰 장애로 이어질 수 있다. 그래서 이 과제의 `MemoryGuard`는 설정 한계에 도달한 **해당 프로세스**를 먼저 종료해 전체 시스템의 가용성을 보호한다.

이번 결과에서는 `OOMKilled=false`와 `MemoryGuard` 로그를 함께 확인했으므로, Docker가 사후에 종료한 경우와 구분할 수 있다.

### 2. CPU 과점유 시 단일 프로세스를 제한·종료하는 이유

CPU를 하나의 프로세스가 오래 점유하면 다른 요청 처리, 시스템 데몬, 모니터링 자체가 CPU를 받을 기회를 잃어 전체 지연이 커질 수 있다. 문제가 된 프로세스를 제한하거나 종료하면 나머지 작업에 CPU 시간을 돌려줄 수 있으므로, 전체 서비스의 가용성을 보호하는 격리 조치가 된다.

다만 종료는 비용이 큰 조치다. 운영 환경에서는 작업 분할·속도 제한·백오프·CPU quota·우선순위 조정 같은 완화 수단을 먼저 설계하고, 임계치 초과 시에는 안전한 중단과 재시작 정책을 둔다.

### 3. 상호 배제와 순환 대기로 Deadlock 설명하기

- **상호 배제**: 한 번에 한 스레드만 락을 가질 수 있다. 여기서는 한 워커가 `Shared_Memory_A`, 다른 워커가 `Socket_Pool_B`를 각각 보유한다.
- **순환 대기**: Thread-1은 B를, Thread-2는 A를 기다려 대기가 원형으로 이어진다. 누구도 다음 단계로 가지 못한다.

여기에 점유 대기(가진 락을 놓지 않고 다른 락을 기다림)와 비선점(다른 스레드의 락을 강제로 빼앗을 수 없음)까지 성립해 Deadlock의 네 조건이 모두 갖춰진다.

### 4. 로그에서 A → B, B → A를 파악한 과정

로그의 시간 순서를 따라 읽는다.

1. `Worker-Thread-1`이 `Shared_Memory_A`를 `LOCK ACQUIRED`한다.
2. `Worker-Thread-2`가 `Socket_Pool_B`를 `LOCK ACQUIRED`한다.
3. Thread-1이 `WAITING for [Socket_Pool_B]`를 기록한다. 즉 A를 보유한 채 B를 기다린다.
4. Thread-2가 `WAITING for [Shared_Memory_A]`를 기록한다. 즉 B를 보유한 채 A를 기다린다.

따라서 `Thread-1(A 보유) → B → Thread-2(B 보유) → A → Thread-1`의 고리가 완성된다. 이후의 로그 정지와 `futex_wait_queue`는 이 추론을 강화하지만, 로그만 보고 락 구현 내부를 단정하지는 않는다.

## 항목 4 — 운영 환경에서의 판단과 개선안

### 1. 실제 운영 서버용 `monitor.sh` 개선안

현재 스크립트는 PID별 CPU/RSS의 순간값을 잘 남긴다. 장애 전에 메모리 누적을 탐지하려면 다음을 추가한다.

- 동일 PID의 최근 N개 RSS를 보관해 `RSS_DELTA_MB`, 분당 증가량, 연속 증가 횟수를 계산한다.
- 단발성 증가가 아닌 “최근 5회 중 4회 이상 증가” 같은 추세 조건과 경고 임계치를 둔다.
- PID 재시작 시점을 구분하기 위해 PID뿐 아니라 시작 시각 또는 프로세스 시작 ID를 함께 기록한다.
- 앱 RSS와 컨테이너 cgroup 메모리 사용량/한도를 함께 수집하고, 임계치 근접·포트 미응답·프로세스 재시작을 알림으로 보낸다.
- 경고마다 타임스탬프, 설정값, 최근 샘플을 보존해 재시작 뒤에도 원인을 추적할 수 있게 한다.

알림은 “한 번 RSS가 높았다”가 아니라 **증가 추세 + 여유 메모리 감소 + 서비스 상태**를 조합해 발생시켜야 오탐을 줄일 수 있다.

### 2. 실제 서비스에서 가장 치명적인 장애와 예방안

판단은 서비스 특성에 따라 달라진다. 이 결과물의 답변 예시로는 **OOM/메모리 누적**을 가장 치명적인 장애로 볼 수 있다. 메모리 고갈은 해당 프로세스만 느리게 하는 데 그치지 않고 같은 호스트·컨테이너의 다른 작업, 관제, 재시작까지 연쇄적으로 불안정하게 만들 수 있기 때문이다.

이번 실험은 `MemoryGuard`가 먼저 종료해 범위를 제한했지만, 운영 환경에서 통제되지 않은 누적은 OS/Docker OOM Kill과 반복 재시작으로 커질 수 있다. 예방은 다음과 같다.

- 캐시·버퍼·큐의 상한과 만료 정책을 둔다.
- 작업 완료 뒤 참조를 해제하고, 메모리 증가 회귀 테스트와 부하 테스트를 둔다.
- RSS 증가율, cgroup 여유 메모리, 재시작 횟수에 경고를 건다.
- 서비스별 메모리 limit와 재시작 정책을 두되, limit 상향만으로 해결됐다고 판단하지 않는다.

Deadlock이 금전 거래나 핵심 요청 경로를 전면 차단하는 서비스라면 Deadlock을 더 치명적으로 판단할 수도 있다. 중요한 것은 장애 유형의 이름보다 영향 범위·복구 가능성·데이터 정합성을 근거로 판단하는 것이다.

### 3. OOM과 Deadlock이 동시에 발생했을 때의 트러블슈팅 순서

1. 짧은 시간 안에 현재 시각, PID, RSS/CPU, cgroup 메모리, 마지막 앱 로그와 스레드 상태를 보존한다.
2. 호스트 또는 컨테이너의 메모리 여유가 위험하면 OOM을 먼저 격리한다. 트래픽을 줄이고, 비핵심 작업을 중지하거나, 필요하면 문제 프로세스를 재시작해 전체 시스템을 보호한다.
3. 재시작 전에 확보한 `top -H`, `ps -L`, 락 대기 로그로 Deadlock 증거를 보존한다. 재시작부터 하면 순환 대기 증거가 사라진다.
4. 메모리 안정화 뒤에는 누적 원인과 Deadlock의 락 순서 문제를 각각 재현 가능한 환경에서 분리 분석한다.

메모리 고갈은 관제와 접근 자체를 막을 수 있어 우선 안정화 대상이다. 단, 앱이 이미 OOM으로 종료됐다면 같은 PID에서 Deadlock을 계속 관찰할 수는 없으므로, 동일 장애인지 별도 프로세스의 동시 장애인지 먼저 구분한다.

### 4. 코드 수정이 가능할 때의 근본 개선

| 장애 | 코드·설계 개선 |
| --- | --- |
| 메모리 누적/OOM | 객체·버퍼·캐시의 소유권과 수명을 명확히 하고 작업 완료 시 참조를 해제한다. 큐와 캐시에 최대 크기·만료·백프레셔를 두고, 임계치 직전이 아니라 여유 구간에서 정리한다. |
| CPU 과점유 | 긴 계산을 작은 작업 단위로 나누고 취소·시간 제한·백오프를 둔다. 워커 수와 큐 길이를 제한해 한 요청이 CPU를 독점하지 못하게 하고, 과부하 지표를 기준으로 속도를 낮춘다. |
| Deadlock | 모든 경로의 락 획득 순서를 하나로 통일한다. 락 보유 범위를 줄이고 `try-lock` 또는 timeout으로 무한 대기를 피하며, 대기 자원과 소유자를 로그로 남겨 회복·재시도 정책을 마련한다. |

### 5. 미션을 다시 수행한다면 다르게 할 점

1. 정상 baseline을 먼저 수집해 PID, RSS, CPU, 로그의 평상시 변화 범위를 기록한다.
2. 장애별 가설과 관측 항목을 실행 전에 정하고, 한 실행에서는 환경변수 하나만 변경한다.
3. PID·포트·스레드·Docker 상태·앱 로그를 같은 시각대에 수집해 증거 간 시간 차이를 줄인다.
4. 종료 코드만 보지 않고 `OOMKilled`, 앱의 종료 로그, 관찰 스크립트의 정리 시점을 구분한다.
5. 재현 조건과 우회 조건을 문서 제목·표에 함께 적어 `Before`/`After`의 의미가 뒤바뀌지 않게 한다.
