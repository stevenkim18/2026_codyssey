# 장애 진단 도구와 지표 기초

장애를 분석할 때 로그 한 줄이나 CPU 수치 하나만으로 원인을 단정하면 안 된다. 앱이 실제로 살아 있는지, 자원을 얼마나 쓰는지, 내부 작업이 진행되는지를 여러 증거로 함께 확인해야 한다.

이 문서는 `agent-leak-app`의 OOM, CPU 과점유, Deadlock을 판단할 때 사용하는 관측 대상과 도구를 초보자 관점에서 설명한다.

## 무엇을 확인하는가

| 확인 대상 | 쉽게 말하면 | 확인 도구 |
| --- | --- | --- |
| 프로세스 | 앱 자체가 아직 살아 있는가 | `ps`, `monitor.sh` |
| CPU | 앱이 계산을 얼마나 많이 하는가 | `monitor.sh`, `ps`, `top` |
| RSS | 앱이 실제 메모리를 얼마나 쓰는가 | `monitor.sh`, `ps` |
| 스레드 | 앱 내부 작업자들이 무엇을 하는가 | `top -H`, `ps -L` |
| 앱의 판단 | 앱이 종료 또는 대기한 이유는 무엇인가 | 애플리케이션 로그 |

## 프로세스와 PID

프로세스는 실행 중인 프로그램 하나를 뜻한다. 운영체제는 각 프로세스에 PID(Process ID)라는 번호를 붙인다. `ps` 또는 `monitor.sh`에서 PID가 보이면 프로세스가 아직 종료되지 않았다는 뜻이다.

그러나 **PID가 존재한다고 앱이 정상적으로 일하고 있다는 뜻은 아니다.** Deadlock에서는 프로세스가 살아 있는 채로 내부 작업이 멈출 수 있다. 따라서 CPU, 메모리, 로그 진행 여부도 함께 확인해야 한다.

## CPU 사용률

CPU는 프로그램의 계산을 처리하는 작업자다. CPU 사용률은 대상 프로세스 또는 스레드가 작업자를 얼마나 사용하고 있는지 보여 준다.

- CPU 사용률이 높게 지속되면 CPU 과점유를 의심할 수 있다.
- 순간 수치 하나보다 시간에 따른 변화가 중요하다.
- 이 과제에서는 OS 도구의 CPU 수치와 앱 로그의 `Current Load`를 함께 본다.

`monitor.sh`와 `ps`는 운영체제 관점의 CPU 사용량을 보여 주고, 애플리케이션 로그는 앱 내부에서 측정한 작업량과 보호 정책의 판단을 보여 준다. 두 수치는 측정 기준이 다를 수 있으므로, 같은 값이어야 한다고 기대하기보다 함께 해석한다.

## RSS와 메모리 사용량

RSS(Resident Set Size)는 프로세스가 실제 물리 메모리에서 차지하는 크기다. 쉽게 말하면, 프로그램이 지금 컴퓨터의 메모리 공간을 얼마나 사용하고 있는지 보여 주는 값이다.

OOM 또는 메모리 누적 사례에서는 RSS가 시간이 지날수록 계속 증가하는지를 확인한다. RSS 상승과 애플리케이션의 메모리 한계 로그가 함께 나타나면, 앱이 메모리 한계에 도달한 경로를 판단하는 근거가 된다.

## 스레드 상태

스레드는 하나의 프로세스 안에서 동시에 일을 수행하는 작업자다. `top -H`와 `ps -L`은 프로세스 전체뿐 아니라 스레드별 상태도 확인할 수 있게 해 준다.

- 실행 중인 스레드가 있는지 확인한다.
- 모든 스레드가 sleeping 또는 락 대기 상태인지 확인한다.
- `futex` 대기는 Linux에서 락이나 조건 변수 같은 동기화 도구를 기다릴 때 나타날 수 있는 단서다.

특히 Deadlock에서는 여러 스레드가 대기 상태에 머물고, CPU와 RSS가 거의 변하지 않으며, 애플리케이션 로그도 더 이상 진행되지 않을 수 있다.

## 애플리케이션 로그

운영체제 도구가 앱의 겉으로 보이는 상태를 보여 준다면, 애플리케이션 로그는 앱 내부에서 어떤 작업과 판단이 있었는지 알려 준다.

- `MemoryGuard` 로그는 앱의 메모리 보호 정책이 동작했는지 확인하는 근거다.
- `CpuWorker`와 임계치 로그는 CPU 작업량과 보호 정책을 확인하는 근거다.
- `WAITING ... BLOCKED` 로그는 스레드가 서로 가진 자원을 기다리는 Deadlock의 단서다.

로그만으로는 실제 프로세스 또는 스레드 상태를 알 수 없으므로, 반드시 `ps`, `top`, `monitor.sh` 결과와 함께 사용한다.

## 장애별 판단 방법

| 장애 유형 | 함께 확인할 증거 |
| --- | --- |
| 메모리 누적 / OOM | RSS가 계속 증가하는지, 메모리 한계 또는 종료 로그가 있는지, Docker의 `OOMKilled` 상태는 무엇인지 |
| CPU 과점유 | CPU 또는 앱 내부 부하가 증가하는지, CPU 임계치 초과 로그가 있는지 |
| Deadlock | PID가 유지되는지, CPU/RSS와 로그 진행이 멈췄는지, 스레드가 대기 상태인지 |

## 핵심 원칙

관제값은 **겉으로 보이는 현상**, 애플리케이션 로그는 **앱 내부의 설명**, 스레드 상태는 **멈춘 이유의 단서**다. 세 가지를 교차 검증해야 장애 원인을 더 정확하게 판단할 수 있다.
