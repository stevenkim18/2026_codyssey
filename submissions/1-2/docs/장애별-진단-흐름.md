# 장애별 진단 흐름

장애를 진단한다는 것은 처음부터 원인을 아는 일이 아니다. 관찰한 증상에서 시작해 가능한 원인을 하나씩 좁혀 가는 과정이다.

이 과제에서는 먼저 프로그램이 종료됐는지, 살아 있지만 멈췄는지를 구분한다. 그다음 로그, CPU, RSS, 스레드 상태를 함께 확인해 OOM, CPU 과점유, Deadlock을 판단한다.

## 공통 진단 순서

1. **프로세스가 존재하는지 확인한다.**
   - `ps` 또는 `monitor.sh`에서 PID가 보이면 앱은 아직 종료되지 않았다.
2. **프로세스가 없다면 종료 주체와 이유를 확인한다.**
   - 애플리케이션 로그의 메모리 또는 CPU 보호 정책 메시지를 찾는다.
   - Docker 상태의 `OOMKilled`를 확인해 Docker cgroup OOM Kill인지 구분한다.
3. **프로세스가 있다면 실제 작업이 진행되는지 확인한다.**
   - CPU, RSS, 애플리케이션 로그가 시간에 따라 변하는지 본다.
4. **작업이 진행되지 않는다면 스레드 상태를 확인한다.**
   - `top -H`, `ps -L`로 스레드가 실행 중인지, 락 대기 상태인지 확인한다.
5. **환경변수 하나를 바꿔 가설을 검증한다.**
   - 동일한 관측 항목을 다시 수집해 장애 재현 조건과 우회 조건을 비교한다.

## 전체 흐름

~~~text
증상 발생
  |
  +-- PID가 존재하는가?
  |     |
  |     +-- 아니오 --> 앱 로그와 OOMKilled를 확인한다.
  |     |               MemoryGuard / CPU 임계치 / Docker OOM Kill을 구분한다.
  |     |
  |     +-- 예 --> CPU, RSS, 로그가 계속 변하는가?
  |                   |
  |                   +-- 예 --> 메모리 또는 CPU 부하 추세를 분석한다.
  |                   |
  |                   +-- 아니오 --> top -H, ps -L로 스레드 대기 상태를 확인한다.
  |                                  WAITING/BLOCKED와 락 대기가 있으면 Deadlock을 의심한다.
~~~

## 1. 메모리 누적 / OOM 진단

1. `monitor.sh`에서 RSS가 시간에 따라 계속 증가하는지 확인한다.
2. 애플리케이션 로그에서 `MemoryGuard` 또는 메모리 한계 초과 메시지를 찾는다.
3. Docker 상태에서 `OOMKilled` 값을 확인한다.
   - `OOMKilled=true`면 Docker cgroup 메모리 한계에 따른 종료를 의심한다.
   - `OOMKilled=false`이고 앱 로그에 보호 정책 메시지가 있다면 앱 내부 종료를 의심한다.
4. `MEMORY_LIMIT`만 변경해 다시 실행한다.
5. 종료 시점, RSS 변화, 메모리 정리 여부, 생존 시간을 비교한다.

판단의 핵심은 **RSS 증가 추세와 종료 관련 로그를 함께 보는 것**이다. RSS 증가만으로 영구적 메모리 누수라고 단정하지 않고, 종료 주체도 별도로 확인한다.

## 2. CPU 과점유 진단

1. `monitor.sh`, `ps`, `top`에서 CPU 사용량 또는 시간에 따른 변화를 확인한다.
2. 애플리케이션 로그에서 `CpuWorker`의 `Current Load`와 CPU 임계치 관련 메시지를 확인한다.
3. `CPU_MAX_OCCUPY`만 변경해 다시 실행한다.
4. 높은 설정에서는 부하 증가와 임계치 도달 여부를, 낮은 설정에서는 cooldown과 생존 여부를 비교한다.

운영체제 도구의 CPU 수치와 앱의 `Current Load`는 측정 기준이 다를 수 있다. 따라서 수치를 하나만 보지 않고, 부하 추세와 보호 정책 로그를 함께 해석한다.

## 3. Deadlock 진단

1. `ps` 또는 `monitor.sh`에서 PID가 계속 존재하는지 확인한다.
2. 마지막 애플리케이션 로그가 `WAITING` 또는 `BLOCKED`인지 확인한다.
3. CPU와 RSS가 오랫동안 거의 변하지 않는지 확인한다.
4. `top -H` 또는 `ps -L`에서 스레드가 sleeping 또는 `futex` 대기 상태인지 확인한다.
5. `MULTI_THREAD_ENABLE=false`로 바꿔 재실행한다.
6. `WAITING`/`BLOCKED` 로그가 사라지고, Scheduler 또는 워커 로그가 계속 진행되는지 비교한다.

판단의 핵심은 **PID가 살아 있어도 작업이 멈출 수 있다**는 점이다. PID 존재, 로그 정지, CPU/RSS 정체, 스레드 락 대기 증거를 함께 확인해야 한다.

## 진단 결과를 설명하는 방법

진단 결과는 다음 순서로 설명하면 명확하다.

1. 어떤 현상을 관찰했는가
2. 어떤 도구와 로그로 증거를 수집했는가
3. 증거가 왜 특정 장애 유형을 가리키는가
4. 어떤 환경변수를 바꿨는가
5. 변경 전후에 무엇이 달라졌는가
6. 임시 조치와 근본 해결은 각각 무엇인가

> 한 가지 수치나 로그만으로 결론 내리지 않는다. 프로세스, 자원 사용량, 스레드 상태, 애플리케이션 로그를 교차 검증하는 것이 이 과제의 핵심이다.
