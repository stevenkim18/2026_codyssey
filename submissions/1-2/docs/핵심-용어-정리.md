# 핵심 용어 정리

이 문서는 1-2 과제의 장애 분석 리포트와 평가 설명에서 자주 사용하는 용어를 정리한다.

## 프로세스, PID, 스레드, TID

- **프로세스(Process)**: 실행 중인 프로그램 하나다. 운영체제는 프로세스마다 PID(Process ID)를 부여한다.
- **PID**: 실행 중인 프로세스를 구분하는 번호다. `ps`와 `monitor.sh`로 확인한다.
- **스레드(Thread)**: 하나의 프로세스 안에서 실행되는 작업 단위다. 하나의 앱은 여러 스레드를 가질 수 있다.
- **TID**: 스레드를 구분하는 번호다. `top -H`, `ps -L`로 스레드별 상태를 확인한다.

PID가 존재한다는 것은 프로세스가 종료되지 않았다는 뜻일 뿐, 앱의 작업이 정상 진행 중이라는 뜻은 아니다. Deadlock에서는 프로세스가 살아 있는 채로 스레드가 모두 대기할 수 있다.

## Heap과 RSS

- **Heap(힙)**: 프로그램이 실행 중에 동적으로 확보하는 메모리 영역이다. 앱 로그가 표시하는 내부 메모리 사용량은 힙 기준일 수 있다.
- **RSS(Resident Set Size)**: 프로세스가 실제 물리 메모리에서 차지하는 크기다. `monitor.sh`와 `ps`에서 관찰할 수 있다.

힙과 RSS는 측정 대상과 시점이 달라 정확히 같은 값일 필요가 없다. 메모리 장애는 한 번의 수치보다 RSS가 시간에 따라 계속 증가하는 추세와 앱 로그를 함께 보고 판단한다.

## 메모리 누적, OOM, OOM Kill

- **메모리 누적**: 프로그램이 확보한 메모리가 시간에 따라 계속 늘어나는 현상이다.
- **메모리 누수(Memory Leak)**: 더 이상 필요하지 않은 메모리에 대한 참조가 남아 해제·재사용되지 않는 결함이다. RSS 증가만으로는 영구적 메모리 누수라고 단정할 수 없다.
- **OOM(Out Of Memory)**: 필요한 메모리를 더 확보할 수 없는 상태다.
- **OOM Kill**: 운영체제 또는 Docker cgroup이 메모리 부족 상황에서 프로세스를 강제 종료하는 동작이다.
- **`OOMKilled`**: Docker가 cgroup 메모리 부족으로 종료했다고 판단한 상태 값이다.

이번 과제에서는 앱 로그의 `MemoryGuard`와 Docker의 `OOMKilled`를 함께 확인해, 앱 내부 보호 정책 종료와 Docker OOM Kill을 구분한다.

## CPU 사용률과 Current Load

- **CPU 사용률**: 운영체제 관점에서 프로세스 또는 스레드가 CPU를 사용한 비율이다. `ps`, `top`, `monitor.sh`에서 확인한다.
- **Current Load**: 이 앱의 `CpuWorker`가 내부적으로 기록하는 작업량 지표다.

둘은 측정 기준과 수집 시점이 다르므로 같은 숫자가 아닐 수 있다. CPU 과점유는 OS 도구의 추세, 앱의 `Current Load`, CPU 임계치 관련 로그를 함께 해석한다.

## Lock과 futex

- **lock(락)**: 여러 스레드가 공유 자원에 동시에 접근해 데이터가 깨지는 일을 막는 동기화 장치다.
- **락 획득**: 스레드가 공유 자원을 사용할 권한을 얻는 일이다.
- **락 대기**: 다른 스레드가 가진 락이 해제되기를 기다리는 상태다.
- **futex(Fast Userspace Mutex)**: Linux에서 락이나 조건 변수 대기에 활용되는 동기화 메커니즘이다. `futex_wait_queue`는 스레드가 동기화 대기 중일 수 있는 단서다.

## Deadlock과 4대 조건

**Deadlock(교착상태)**은 여러 스레드가 서로 가진 자원을 기다리느라 아무도 작업을 진행하지 못하는 상태다. 다음 네 조건이 동시에 성립하면 발생할 수 있다.

| 조건 | 뜻 | 이번 과제의 로그에서 확인하는 모습 |
| --- | --- | --- |
| 상호 배제 | 한 번에 한 스레드만 락을 사용할 수 있다. | 각 Worker가 서로 다른 락을 획득해 보유한다. |
| 점유 대기 | 이미 가진 락을 놓지 않고 다른 락을 기다린다. | Thread-1은 A를 가진 채 B를, Thread-2는 B를 가진 채 A를 기다린다. |
| 비선점 | 다른 스레드가 가진 락을 강제로 빼앗을 수 없다. | 어느 스레드도 상대방의 락을 강제로 해제하지 못한다. |
| 순환 대기 | 자원 대기가 고리처럼 이어진다. | Thread-1 → B → Thread-2 → A → Thread-1의 대기 고리가 생긴다. |

## 종료 코드

- **ExitCode 137**: 일반적으로 프로세스가 `SIGKILL`로 종료됐을 때 나타날 수 있다.
- **ExitCode 143**: 일반적으로 프로세스가 `SIGTERM`을 받았을 때 나타날 수 있다.

종료 코드 하나만으로 종료 주체를 단정하면 안 된다. 앱 로그, `OOMKilled`, 실행 스크립트가 관찰 종료 후 컨테이너를 정리했는지까지 함께 확인해야 한다.

## 장애 재현 조건과 우회 조건

- **장애 재현 조건**: 장애가 나타나는 환경변수 조합이다.
- **우회 조건**: 환경변수를 바꿔 장애를 피하거나 생존 시간을 늘린 조건이다.
- **임시 조치**: 설정 변경으로 증상을 피하는 방법이다.
- **근본 해결**: 메모리 해제, CPU 작업 분할, 락 순서 통일처럼 코드와 설계를 고치는 방법이다.

`Before`와 `After`만으로 조건의 의미가 모호할 때는 장애 재현 조건과 우회 조건을 함께 표기한다.
