# AWS 클라우드 과제 평가 항목별 설명 가이드

이 문서는 평가 항목마다 **무엇을 확인해야 하는지**와 **어떻게 설명하면 되는지**를 정리한 자료다.

평가에서 중요한 것은 단순히 AWS 리소스를 만들어 놓는 것이 아니라,

> **“내가 왜 이렇게 구성했고, 문제가 생기면 어떻게 확인하는지”**

를 자신의 말로 설명할 수 있는 것이다.

---

# 항목 1 — 실제로 구축했는가?

## 1-1. VPC, Public Subnet, Internet Gateway, Route Table이 구성되어 있는가?

### 무엇을 확인하는가?

AWS 네트워크의 기본 구조를 실제로 만들었는지 확인한다.

구조는 다음과 같다.

```text
Internet
   │
   ▼
Internet Gateway
   │
   ▼
VPC
   │
   ▼
Public Subnet
   │
   ▼
EC2
```

그리고 Public Subnet의 Route Table에는 다음 경로가 있어야 한다.

```text
0.0.0.0/0 → Internet Gateway
```

### 이렇게 설명하면 된다

> VPC는 AWS 안에서 사용하는 제 전용 네트워크 공간입니다.  
> 그 안에 Public Subnet을 만들고 EC2를 배치했습니다.  
> 외부 인터넷과 통신할 수 있도록 Internet Gateway를 VPC에 연결했고, Public Subnet의 Route Table에 `0.0.0.0/0 → IGW` 경로를 추가했습니다.
>
> 그래서 VPC 내부 목적지가 아닌 인터넷 방향의 트래픽은 Internet Gateway를 통해 나갈 수 있습니다.

### 핵심 키워드

```text
VPC
Subnet
Route Table
Internet Gateway
0.0.0.0/0
```

---

# 1-2. EC2에 SSH로 접속 가능하며 웹 서버가 실행 중인가?

### 무엇을 확인하는가?

EC2 서버가 실제로 실행되고 있고, 원격으로 접속해서 관리할 수 있는지 확인한다.

또한 Nginx 같은 웹 서버가 실행되고 있어야 한다.

### 이렇게 설명하면 된다

> Public Subnet 안에 EC2를 생성했습니다.  
> EC2에는 Public IP가 있고, 제 컴퓨터에서 SSH 22번 포트를 이용해 접속할 수 있습니다.
>
> EC2 내부에는 Nginx를 설치했고 실행 상태를 확인했습니다.  
> 서버 내부에서 `curl http://localhost`를 실행했을 때 200 응답이 오는 것도 확인했습니다.

### 핵심 흐름

```text
내 컴퓨터
   │
   │ SSH :22
   ▼
EC2
   │
   ▼
Nginx :80
```

# 1-3. Security Group이 필요한 포트만 허용하는가?

### 무엇을 확인하는가?

서버를 필요 이상으로 인터넷에 노출하지 않았는지 확인한다.

이번 과제에서는 일반적으로 다음과 같이 설정한다.

```text
HTTP 80
Source: 0.0.0.0/0

SSH 22
Source: 내 IP/32
```

### 이렇게 설명하면 된다

> 웹 서비스는 외부 사용자가 접속해야 하기 때문에 HTTP 80번 포트는 `0.0.0.0/0`으로 허용했습니다.
>
> 하지만 SSH는 서버 관리 목적으로 저만 사용하기 때문에 22번 포트는 제 IP에서만 접근할 수 있도록 제한했습니다.
>
> 사용하지 않는 포트나 전체 포트는 열지 않았습니다.

### 중요한 한 문장

> **서비스에 필요한 포트만 필요한 범위에 공개했습니다.**

# 1-4. 외부 접속이 정상적으로 되는가?

두 방법 중 하나를 선택한다.

## 방법 A — 브라우저

```text
http://<Public-IP>
```

### 이렇게 설명하면 된다

> 저는 A 방식인 브라우저 접속을 선택했습니다.
>
> EC2에서 Nginx를 80번 포트로 실행하고 Security Group에서도 HTTP 80을 외부에 허용했습니다.
>
> EC2의 Public IP로 브라우저에서 접속했을 때 Nginx 페이지가 정상적으로 표시되는 것을 확인했습니다.

---

## 방법 B — `/health`

```text
GET http://<Public-IP>/health
```

### 이렇게 설명하면 된다

> 저는 B 방식인 `/health` API 확인을 선택했습니다.
>
> 서버에 `/health` 요청이 들어오면 고정된 `OK` 응답을 반환하도록 구성했습니다.
>
> 외부에서 Public IP의 `/health` 주소로 요청했을 때 HTTP 200과 `OK` 응답이 오는 것을 확인했습니다.

---

# 1-5. 리소스를 제대로 정리했는가?

### 무엇을 확인하는가?

실습 이후 불필요한 비용이 발생하지 않도록 만든 AWS 리소스를 삭제했는지 확인한다.

최소 확인 대상:

```text
EC2
EBS
Elastic IP
Internet Gateway
VPC
```

### 이렇게 설명하면 된다

> 실습에서 생성한 리소스를 이름과 태그를 기준으로 추적했습니다.
>
> 실습 종료 후 EC2를 종료하고 EBS와 Elastic IP가 남아 있는지 확인했습니다.
>
> 이후 Internet Gateway를 분리하고 삭제한 뒤 Subnet과 VPC도 삭제했습니다.
>
> 마지막으로 Billing 화면에서 예상하지 못한 과금이 없는지도 확인했습니다.

# 항목 2 — 내가 만든 구조를 설명할 수 있는가?

# 2-1. 외부 → IGW → Subnet → EC2 흐름 설명

### 이렇게 설명하면 된다

> 사용자가 EC2의 Public IP로 HTTP 요청을 보내면 요청이 인터넷을 통해 AWS 네트워크로 들어옵니다.
>
> VPC에는 Internet Gateway가 연결되어 있어 인터넷과 통신할 수 있습니다.
>
> Public Subnet의 Route Table에는 `0.0.0.0/0 → IGW` 경로가 있어서 외부와 통신할 수 있는 경로가 만들어져 있습니다.
>
> 요청이 EC2까지 도달하면 Security Group에서 해당 포트를 허용하는지 확인하고, 허용되어 있다면 EC2의 Nginx가 요청을 처리합니다.

### 한 줄로 줄이면

```text
사용자 → Internet → IGW → Public Subnet → SG → EC2 → Nginx
```

---

# 2-2. Security Group을 어떤 기준으로 최소화했는가?

### 이렇게 설명하면 된다

> 포트별로 실제 사용 목적이 있는지 기준으로 허용했습니다.
>
> HTTP 80은 웹 서비스를 제공하기 위해 누구나 접근할 수 있도록 허용했고, SSH 22는 관리자만 필요하기 때문에 제 IP에서만 접근하도록 제한했습니다.
>
> DB 포트나 사용하지 않는 포트는 외부에 공개하지 않았습니다.

### 핵심 기준

```text
이 포트가 정말 필요한가?
        ↓
누가 접근해야 하는가?
        ↓
최소 범위만 허용
```

# 2-3. 외부 접속 검증을 어떻게 구성했는가?

### A 선택 시

> 브라우저 접속 방식으로 확인했습니다.
>
> Nginx가 80번 포트에서 실행되도록 하고, Security Group에서 80번 포트를 허용했습니다.
>
> 이후 EC2 Public IP로 브라우저에서 접속해 정상 페이지가 출력되는 것을 확인했습니다.

### B 선택 시

> `/health` 방식으로 확인했습니다.
>
> `/health` 요청에 항상 일정한 값을 반환하도록 서버를 구성한 뒤, 외부에서 요청해 200 응답과 고정 응답을 확인했습니다.

# 2-4. 리소스를 어떻게 추적했는가?

### 이렇게 설명하면 된다

> 실습 리소스마다 이름 규칙과 태그를 사용했습니다.
>
> 예를 들어 `Project=cloud-mission`, `Owner=student01` 같은 태그를 붙여 이번 실습에서 만든 리소스를 구분했습니다.
>
> 마지막에는 cleanup checklist를 기준으로 하나씩 삭제 여부를 확인했습니다.

### 예시

```text
Name: cloud-mission-ec2
Name: cloud-mission-vpc

Project = cloud-mission
Owner = student01
```

# 항목 3 — 왜 그렇게 구성했는가?

# 3-1. 왜 `0.0.0.0/0 → IGW`가 필요한가?

### 이렇게 설명하면 된다

> `0.0.0.0/0`은 특정 내부 네트워크가 아닌 모든 IPv4 목적지를 의미합니다.
>
> Route Table에서 이 트래픽을 Internet Gateway로 보내도록 설정해야 Public Subnet의 인스턴스가 인터넷과 통신할 수 있습니다.
>
> 이 경로가 없으면 Internet Gateway가 연결되어 있어도 인터넷 방향으로 패킷을 어디로 보낼지 알 수 없습니다.

### 핵심

> **IGW는 인터넷 출입구이고, Route Table은 그 출입구로 가는 길을 알려준다.**

---

# 3-2. Security Group과 IAM 차이

### 이렇게 설명하면 된다

> Security Group은 네트워크 접근을 제어합니다.
>
> 예를 들어 어떤 IP가 EC2의 80번 또는 22번 포트에 접근할 수 있는지를 결정합니다.
>
> 반면 IAM은 AWS 안에서 어떤 작업을 할 수 있는지를 제어합니다.
>
> 예를 들어 사용자가 EC2를 생성하거나 VPC를 삭제할 수 있는지 같은 AWS API 권한을 관리합니다.

### 쉽게 비교

| Security Group | IAM |
|---|---|
| 네트워크 접근 | AWS 작업 권한 |
| EC2 80번 접근 가능? | EC2 생성 가능? |
| SSH 접근 가능? | VPC 삭제 가능? |

---

# 3-3. 최소 권한은 왜 필요한가?

### 이렇게 설명하면 된다

> 계정이나 서버가 실수 또는 공격으로 잘못 사용되더라도 피해 범위를 최소화하기 위해서입니다.
>
> EC2와 VPC 실습만 필요한 사용자에게 S3나 RDS까지 모든 권한을 줄 필요는 없습니다.
>
> 그래서 필요한 작업에 필요한 권한만 부여하는 최소 권한 원칙을 적용했습니다.

### 핵심

```text
필요한 사람에게
필요한 권한만
필요한 기간 동안
```

---

# 3-4. SSH 또는 DB 포트를 `0.0.0.0/0`로 열면 안 되는 이유

### 이렇게 설명하면 된다

> `0.0.0.0/0`으로 허용하면 인터넷의 모든 IP에서 해당 포트에 접근할 수 있습니다.
>
> SSH 같은 관리 포트는 무차별 로그인 시도 등의 공격 대상이 될 수 있고, DB 포트도 외부에 직접 노출할 필요가 없는 경우가 대부분입니다.
>
> 그래서 SSH는 관리자 IP만 허용하고 DB는 가능하면 Private Subnet이나 특정 Security Group에서만 접근하도록 제한하는 것이 좋습니다.

### 예

```text
❌ SSH 22
0.0.0.0/0

✅ SSH 22
내 IP/32
```

---

# 3-5. 왜 가설 → 검증 순서로 트러블슈팅하는가?

### 이렇게 설명하면 된다

> 문제가 발생했을 때 설정을 무작정 여러 개 변경하면 실제 원인이 무엇이었는지 알기 어렵습니다.
>
> 그래서 먼저 증상을 확인한 뒤 가능한 원인을 하나씩 가설로 세우고, 설정이나 로그를 통해 검증했습니다.
>
> 검증된 원인만 수정하고 결과를 다시 확인했습니다.

### 예

```text
증상
외부 접속 안 됨

↓

가설
SG에서 80번이 막혀 있을 수 있음

↓

검증
SG 규칙 확인

↓

조치
80번 허용

↓

결과
외부 접속 성공
```

### 로그를 사용하는 이유

> 로그는 단순 추측이 아니라 **실제로 어떤 요청이나 오류가 발생했는지 보여주는 근거**이기 때문입니다.

# 항목 4 — 새로운 문제가 생겼을 때 해결할 수 있는가?

# 4-1. 외부 접속이 안 될 때 어떤 순서로 확인하는가?

평가에서는 이 순서를 기억하면 좋다.

```text
① Routing
↓
② Security Group
↓
③ Public IP / DNS
↓
④ Server Process
↓
⑤ Log
```

### 이렇게 설명하면 된다

> 먼저 네트워크 경로가 존재하는지 확인합니다.
>
> Public Subnet의 Route Table에 `0.0.0.0/0 → IGW`가 있는지와 IGW가 VPC에 연결되어 있는지 확인합니다.
>
> 다음으로 Security Group에서 필요한 포트가 허용되어 있는지 확인합니다.
>
> 그 다음 EC2에 Public IP가 있는지, DNS를 사용한다면 올바른 IP를 가리키는지 확인합니다.
>
> 마지막으로 EC2 내부에서 Nginx 같은 서버 프로세스가 실행 중인지 `curl localhost`로 확인하고, 그래도 해결되지 않으면 서버 로그를 확인합니다.

---

# 4-2. IAM 권한 부족 오류가 발생하면?

### 잘못된 방법

```text
AccessDenied
↓
AdministratorAccess 추가
```

이렇게 하면 안 된다.

### 올바른 방법

```text
AccessDenied
↓
실패한 Action 확인
↓
어떤 Resource인지 확인
↓
현재 Policy 확인
↓
필요한 권한만 추가
↓
재시도
```

### 이렇게 설명하면 된다

> 먼저 오류 메시지에서 어떤 Action이 거부되었는지 확인합니다.
>
> 그 다음 현재 IAM Policy에서 해당 Action이 빠져 있는지 확인하고, 작업에 정말 필요한 권한인지 판단합니다.
>
> 필요한 경우 해당 Action과 Resource 범위만 추가합니다.
>
> 단순히 AdministratorAccess를 부여하지 않고 최소 권한을 유지합니다.

# 4-3. EC2를 2대로 늘려야 한다면?

### 현재 구조

```text
Internet
   │
   ▼
 EC2 1대
```

### 문제

EC2 하나가 모든 요청을 처리하기 때문에 그 인스턴스가 병목이 될 수 있다.

또 서버가 장애가 나면 서비스 전체가 멈춘다.

### 확장

```text
             Internet
                │
                ▼
               ALB
             /     \
            ▼       ▼
         EC2 #1   EC2 #2
```

### 이렇게 설명하면 된다

> 현재는 사용자의 요청이 EC2 한 대로 모두 들어가기 때문에 트래픽이 많아지면 해당 인스턴스가 병목이 됩니다.
>
> EC2를 두 대로 늘린다면 사용자 요청을 두 서버에 나누어 전달할 구성요소가 필요합니다.
>
> HTTP 서비스라면 ALB를 앞에 두고 요청을 여러 EC2에 분산할 수 있습니다.
>
> 이렇게 서버 수를 늘리는 방식을 Scale Out이라고 합니다.

### 추가로 말하면 좋은 것

> 실제 운영에서는 EC2를 서로 다른 Availability Zone에 배치하면 한쪽 장애에도 대응할 수 있습니다.

# 4-4. 예상하지 못한 Billing이 발생했다면?

### 확인 흐름

```text
Billing
↓
어떤 AWS 서비스?
↓
어느 Region?
↓
어떤 Resource?
↓
Tag / 이름 확인
↓
필요 여부 판단
↓
삭제
```

### 이렇게 설명하면 된다

> 먼저 Billing Dashboard에서 어떤 서비스에서 비용이 발생하고 있는지 확인합니다.
>
> 이후 해당 서비스와 Region으로 이동해 실행 중인 리소스를 찾습니다.
>
> 이름이나 Tag를 이용해 이번 실습에서 만든 리소스인지 확인합니다.
>
> 불필요한 리소스라면 삭제하고 이후 Billing에서 비용이 더 발생하는지 다시 확인합니다.

### 우선 확인할 리소스

```text
EC2
EBS
Elastic IP
NAT Gateway
ALB
RDS
```

특히 **NAT Gateway, Load Balancer, 사용하지 않는 EBS/EIP 등**이 남아 있지 않은지 확인한다.

# 평가 항목 전체를 한 번에 설명한다면

평가 마지막에 전체 구조를 설명하라고 하면 아래 흐름으로 이야기하면 된다.

> 먼저 VPC를 만들고 그 안에 Public Subnet을 구성했습니다.  
> VPC에 Internet Gateway를 연결하고 Public Subnet의 Route Table에 `0.0.0.0/0 → IGW` 경로를 설정해서 인터넷과 통신할 수 있도록 했습니다.
>
> Public Subnet에는 EC2를 생성하고 Nginx 웹 서버를 실행했습니다. EC2에는 Public IP가 있고 외부에서 HTTP로 접근할 수 있습니다.
>
> Security Group에서는 서비스에 필요한 HTTP 80번만 전체 인터넷에 허용하고, 관리용 SSH 22번은 제 IP로 제한했습니다.
>
> AWS 리소스를 관리하는 IAM 권한도 AdministratorAccess를 사용하지 않고 필요한 EC2/VPC 관련 작업만 사용할 수 있도록 최소 권한을 적용했습니다.
>
> 외부 접속에 문제가 생기면 라우팅, Security Group, Public IP, 서버 프로세스, 로그 순서로 가설을 세우고 하나씩 검증합니다.
>
> 트래픽이 늘어나면 ALB와 여러 EC2를 이용한 Scale Out 구조를 고려할 수 있고, 실습이 끝난 뒤에는 EC2, EBS, EIP, IGW, VPC 등 생성한 리소스를 삭제하고 Billing을 확인합니다.

# 평가 직전 암기해야 할 핵심 문장

평가 직전에는 아래 정도는 바로 말할 수 있으면 좋다.

**VPC**

> AWS 안에서 만드는 논리적으로 격리된 나만의 네트워크입니다.

**Subnet**

> VPC의 IP 범위를 더 작은 네트워크로 나눈 것입니다.

**Internet Gateway**

> VPC와 인터넷을 연결하는 출입구 역할을 합니다.

**Route Table**

> 네트워크 트래픽을 어디로 보낼지 결정합니다.

**`0.0.0.0/0 → IGW`**

> 인터넷 방향의 기본 트래픽을 Internet Gateway로 보내기 위한 경로입니다.

**EC2**

> AWS에서 사용하는 가상 서버입니다.

**Security Group**

> EC2 등에 대한 네트워크 접근을 제어하는 가상 방화벽입니다.

**IAM**

> AWS에서 누가 어떤 리소스에 어떤 작업을 할 수 있는지 관리합니다.

**Security Group vs IAM**

> SG는 네트워크 접근을 제어하고, IAM은 AWS 작업 권한을 제어합니다.

**최소 권한**

> 필요한 사용자에게 필요한 작업에 필요한 권한만 부여하는 원칙입니다.

**SSH 보안**

> SSH는 관리자용 포트이므로 `0.0.0.0/0`으로 공개하지 않고 관리자 IP만 허용합니다.

**트러블슈팅**

> 증상을 확인하고 가설을 세운 뒤 로그와 설정을 통해 하나씩 검증합니다.

**외부 접속 장애**

> 라우팅 → Security Group → Public IP/DNS → 서버 프로세스 → 로그 순으로 확인합니다.

**Scale Out**

> 서버 한 대가 병목이 되면 ALB 앞에 여러 EC2를 두고 요청을 분산할 수 있습니다.

**Billing**

> 비용이 발생한 서비스와 Region을 먼저 찾고, Tag와 이름으로 리소스를 추적한 뒤 불필요한 리소스를 삭제합니다.
